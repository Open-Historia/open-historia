# Advisor conversation UI — scoped visual contract

Status: Advisor conversation visual redesign is merged in Beta source via PR #952 (merge `13aadc1e`, 2026-11-05). Multi-Action-fence parsing was subsequently integrated through PR #957. The 2026-11-06 Action queue-state and cancellation improvement described below is a separate local candidate, not yet committed, merged, or released.

## Purpose and ownership

The Advisor drawer is a flexible **conversation workspace**, not a mandatory government-briefing mode. It supports short advice, ministers and officials, public-only civilian or fictional characters, free-form narrative/roleplay, and long Markdown replies. Never infer a genre, split natural-language dialogue into speakers using regex, fabricate named participants, or rewrite a message into briefing sections for display.

Implementation is owned by `src/Game/GameUI/advisor.jsx`, `AdvisorRecipients.jsx`, and their scoped stylesheet `advisorDossier.css`. The styling is rooted under `.oh-advisor-drawer` and intentionally separate from the Country dossier. The shared `markdown.jsx` renderer is unchanged; this UI adjusts only the Advisor's Markdown typography locally.

## Visual behavior

- The drawer, header and composer use a restrained dark navy palette with subtle blue/cyan accents and rectangular controls. Preserve desktop resizing and current phone safe-area geometry.
- The selected recipient remains visible in the collapsed picker. The expanded contact list is a compact ledger with a subtle selected row and still-visible Edit, Retire, Restore and contact-creation actions. Choosing a conversation collapses the picker. Existing confirmation, archived-state, office binding and public-only status notices remain unchanged.
- Advisor, minister and character replies appear as open long-form text with a narrow left rail, not one large filled grey speech bubble. User messages remain visually distinct, compact, right-aligned blue-toned messages. Errors, document notices and pending-response indicators retain distinct treatments.
- The message body is presented verbatim through the existing Markdown component. Paragraphs, headings, blockquotes, lists, emphasis, inline/fenced code, tables, original dialogue punctuation, draft buttons and charts are still rendered by the original components. No extra titles or authoring conventions are imposed.
- The bottom composer keeps textarea auto-height, Enter/Shift+Enter mechanics, loading/disabling and save/load guards. The old rocket glyph is replaced with an accessible conventional arrow, with appropriate focus/disabled colors and reduced-motion treatment.

## Non-negotiable boundaries

- **One recipient per Advisor thread remains canonical.** The existing `advisorThreads.js` recipient records and `threadId` ownership are unchanged. Native multi-person Advisor conversations (distinct participant identities, separate memories and per-participant information visibility) are **explicitly deferred**; do not merge them into this UI feature.
- Ordinary dialogue involving multiple characters may be written within a single model response, but that response retains its existing Advisor-thread identity. Never infer an independent speaker or grant access to another recipient's private history from text.
- Preserve recipient-type permission and government-knowledge separation. Non-minister characters receive only public scenario context and their own conversation. Never change `advisorRecipientForReply`, the AI prompt dispatch, or thread storage to make the visual redesign work.
- Preserve `React.memo(AdvisorMessageRow)` and `React.memo(AdvisorMessageList)`, lazy mounting of earlier messages, stable callback ownership, streaming, draft and approval controls, charts and error/report actions. No chat-history reparsing on composer keystrokes.
- No canonical game-state mutations, AI prompt changes, new mode preferences or schema changes are part of this patch.

## 2026-11-05 — multiple fenced Advisor Action proposals (merged PR #957)

A provider can emit several separate ```actions JSON arrays in one reply, even though the prompt asks for a single array. Previously `parseAdvisorReply` stripped only the first `actions` fence and `advisor.jsx` independently extracted that same first block when constructing persistent proposal attachments. Later Action arrays were displayed as raw horizontal-scrolling JSON code instead of reviewable cards. This is a parser contract bug, not a consequence of the Advisor visual stylesheet or a change in the Actions simulation.

`src/Game/GameUI/advisorReply.js` now uses the existing fenced JSON extractor repeatedly for Action blocks, preserving source order and leaving all other named block types on their existing routes. It hides completed raw Action fences and unfinished trailing `actions` content while streaming or on finalization. Malformed, non-list or truncated Action blocks do not yield partial speculative Action proposals, and the failure is reported in `actionBlockProblems`. `advisor.jsx` derives the stored proposals and error receipts from that same parse result; it no longer independently extracts only the first block. The existing `actionProposalsFromReply` validation, 24-proposal total limit, stable reply-bound IDs, per-proposal Discuss/Proceed confirmation, board writer, idempotency, recipient permissions and game-turn boundaries are unchanged. **No Action is auto-queued.**

Existing persisted Advisor messages are not rewritten or silently reinterpreted as newly authorized proposals. Future replies can show all accepted Action cards; old messages with missing proposal attachments cannot safely be auto-backfilled without a separate migration/authority decision. The reporter supplied screenshots (Gemma4:31b; Cold War scenario), not the underlying raw model transcript; the repeated correctly labeled fence diagnosis is reproduced in native tests, while alternate raw fence labels or malformed provider syntax have not been independently observed in that live report.

Regression evidence: `src/Game/GameUI/advisorReply.test.js` reproduces three separate Action arrays with two subsequent raw-code leaks, verifies stable proposal identities across the complete sequence, preserves the global 24-proposal bound across separate fences and rejects malformed/incomplete secondary blocks. The full project suite, production builds and user-facing retest must be recorded as separate gates before release.

## 2026-11-06 - Advisor Action queue state and cancellation (local candidate)

A live Russia campaign revealed a false failure after Proceed / Queue. Four Action proposals were correctly written to the planned Actions queue and all four queued receipts were durably saved in advisor.json, yet their Advisor cards continued to display Proposed and the error "The original Advisor Action proposal is no longer available." The failure came from a second, strict attempt to stamp that already-persisted receipt onto the in-memory visible transcript. It could throw when the displayed conversation was stale or different, even though both canonical writes had succeeded. The error was misleading; no campaign repairs or speculative resubmissions are justified.

The repair separates canonical authorization/receipt writes from non-authoritative local view synchronization. The native approval service continues to validate the stored message, recipient type, proposal source index, stable Action ID and native queue inside existing mutation locks. The local view merger updates only a matching displayed message and otherwise leaves a stale view untouched without turning successful persistence into a failure. The card also subscribes to the actual Actions queue, so it shows Queued whenever that exact proposal-created Action remains planned, independently of whether the receipt has reached the component.

For CREATE proposals, a confirmed pending item displays Discuss and Cancel, rather than another Proceed / Queue. Cancel removes only the unchanged, exact, still-planned native Action and records a cancelled receipt. It rejects resolved, modified, non-Advisor, duplicate-ID, unit-backed, forged or shared-game Actions without changing them. A cancelled CREATE may be queued again with the original deterministic Action ID and the native receipt transitions back to queued. Resolved Actions never offer destructive Cancel; approved edits/removals retain their own completed status.

Discuss remains a deliberate, editable Advisor-composer handoff, not an automatic AI message or a new queued Action. On a still-queued CREATE, it first cancels that exact order through the same native safeguard and only then prepares the discussion prompt in the Advisor composer. If cancellation fails, it neither claims the Action was withdrawn nor silently dispatches a discussion. The player's draft is retained. No new model call, canonical simulation operation, permission bypass or additional receipt authority is introduced.

Focused regression coverage: advisorActionLifecycle.test.js covers the live saved-queue/stale-view failure class, Queued/Cancelled/Resolved status, cancellation/requeue/idempotency, same-ID identity and provenance protection, malformed queue rejection, authority boundaries, and UI wiring. Existing Advisor approval and review tests still enforce preapproval, host authority, unit reversion, receipt persistence and retry invariants. Record full-suite/build/installed-app acceptance separately; this checkpoint is not a released feature.

## 2026-11-06 - Receipt preservation and stale edit targets (same Advisor PR, local until pushed)

Read-only inspection of the installed Russia campaign separated two failures. A CREATE submission could commit both the Actions entry and its canonical Advisor receipt and then show a false local synchronization error (already fixed earlier in this branch). Other replies offered EDIT operations against resolved or nonexistent order IDs; the native planner correctly refused those edits. A further native state-integrity weakness was reproduced with synthetic data: a subsequent full-thread save from a stale React snapshot could replace the saved reply record and erase an acknowledged receipt, or omit the acknowledged reply entirely.

The correction resides in src/runtime/advisorThreads.js, at the **canonical thread-save boundary**. replaceAdvisorThread merges current persisted receipt metadata into matching messages by stable reply ID and proposal identity, without accepting a new or changed approval from a generic conversation save. Duplicate reply IDs, forged receipts or altered acknowledged proposal identities fail closed. A stale snapshot that omits an acknowledged reply preserves that native receipt-bearing reply; the explicit full-conversation clear remains allowed. Interleaved native notices, other recipients' messages, original order and prior recipient/office privacy contracts remain intact. Queue/Cancel/requeue receipt transitions are still controlled only by the native Advisor approval service, not by the transcript renderer.

The Advisor card now observes the native Actions board for existing EDIT/REMOVE target IDs, not only Actions originally created by the Advisor. Proposed edits/removals of resolved or absent orders show a truthful unavailable status, no Proceed button, and an optional Discuss composer handoff that asks for a *new* proposed Action if the work is genuinely new. No Action is automatically created, no invalid target is silently rewritten and no resolved Action is mutated. A target that changes between render and click is still rejected by the existing native planned-status validation.

New regressions in src/runtime/advisorThreads.test.js and src/Game/GameUI/advisorActionLifecycle.test.js cover stale receipts, missing entire acknowledged replies, clear behavior, ID/proposal integrity, recipient separation, live target statuses and disabled stale Proceed. The English catalog adds three labels; translated language packs were not regenerated. The AI model may still suggest outdated Action IDs; the UI and native engine now make those proposals non-executable rather than masking the failure. Treat model-side stale-ID generation as a distinct future improvement only if new evidence warrants it.

This checkpoint is a source-level fix pending verification/build/release status. Do not state that the installed Electron app or production Beta is updated merely because the localhost source passes tests.

## 2026-11-06 — Adjacent Advisor payload arrays and Projects recovery (Beta bugfix sweep)

A Russia-campaign report showed two distinct extraction failures: an Actions block that was invalid JSON, and a Projects block for Strategic Energy Autonomy and Asset Recovery containing adjacent JSON arrays (the boundary looked like `}] [{`). The generic fenced JSON parser used to reject the Actions block and treated the second Projects array as broken/trailing data during salvage, incorrectly reporting a partial board update. `advisorBlocks.js` now accepts consecutive **fully closed, strictly parseable JSON arrays** inside one `actions` or `projects` fence as a single ordered sequence. It scans strings/escapes/nested containers rather than replacing bracket text; it rejects any non-array trailing text or malformed component. This is not permission to salvage partial Actions or queue them automatically. Existing proposal review limits and native Project application rules are unchanged. `advisorBlocks.test.js` and `advisorReply.test.js` reproduce both variants and the fail-closed case.

The Projects warning formerly offered a global `Ask for the next batch` composer shortcut even on old messages and on malformed-but-not-truncated replies. Its canned text incorrectly claimed the previous output was cut off, then invited a general historical backfill: in the reported campaign the next reply opened seven new records from historical frameworks and reviews. The new **Retry missing entries** shortcut refers only to operations lost from the immediately previous response; it cautions against inventing new historical initiatives and allows the advisor to say no identifiable work remains. The button is offered only for the newest problematic message. This is a UX/recovery-scope guard, **not** a machine-verifiable guarantee that the advisor will never propose an unjustified project; project provenance remains a separate possible engine improvement. Source wiring and localization coverage are regression-tested in `advisorProjectRecoveryArchitecture.test.js` and `i18nCatalog.test.js`. The English catalog was augmented without rearranging existing entries.

These repairs do not rewrite existing campaign saves, infer the real state of historic projects, change who is authorized to mutate the Projects board, or bypass Action approval. Multiple separate `projects` fences within the same answer remain a distinct watch item: this patch addresses adjacent complete arrays inside a single fenced block, not an unproven alternate format.

**2026-11-06 upstream Beta reconciliation:** Beta `2f2711d4` separately added `closeObjectsBeforeList`, which narrowly repairs an Action array whose final object omitted its closing brace. The consolidated bugfix branch preserves that upstream repair as a fallback after parsing fully valid adjacent arrays, while retaining the existing prohibition on salvaging truncated Action batches. Both regression cases run together; this paragraph records the merge contract without replacing either fix.
