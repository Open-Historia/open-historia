# Prompt-Making Guide

Every LLM call the game makes is a template in `src/Game/AI/defaultPrompts.json` filled with runtime game state, then hardened by call-time directives, then validated against a JSON Schema tool. This page is the single reference for anyone editing prompts: it enumerates every `${PLACEHOLDER}`, every template variable and where it is computed, every AI task and its output schema, exactly how a final prompt is assembled, how a scenario or game edits the guidance inside them, and how to add a new variable or task. When in doubt, the code paths are all in `src/Game/AI/` and `src/runtime/`.

## 2. The three prompt "kinds" and how they are stored

`defaultPrompts.json` has exactly three top-level buckets:

| Kind | JSON key | Contains | Rendered by |
|---|---|---|---|
| Root: **advisor** | `advisor` (string) | Chief-advisor side-panel chat | `buildAdvisorSystemPrompt` (`main.jsx`) |
| Root: **leader** | `leader` (string) | AI diplomacy — polities replying in a chat | `buildDiplomaticSystemPrompt` (`main.jsx`) |
| **tasks** | `tasks.<key>` (strings) | 13 structured JSON tasks (below) | `runJsonTask` (`gameplay.js`) |
| Helper map | `helpers` (object) | `${PLACEHOLDER}` → `${templateVar}` indirection | `resolveHelperValues` (`promptContext.js`) |

### Storage model: guidance only (since 2026-09-16)

Every prompt is a fixed **technical template** — the placeholders that inject the world, the output contracts, the map rules — with a few passages of **guidance** inside it: the role, the tone, what to simulate and how much, what makes a good event. Only the guidance is stored and editable.

- `src/Game/AI/promptGuidance.js` declares the passages: per section (`advisor`, `leader`, or a task key) an ordered list of segments `{ id, label, start, end, hint }`, each located in the default text by a `start` and an `end` anchor copied verbatim from `defaultPrompts.json`. Anchors must be unique and in order (`promptGuidance.test.js` checks every one, that no passage carries a code block or a JSON contract, and that an unedited pack renders the shipped text byte for byte). A prompt with no entry has no guidance and never appears in the editor — the curator, the directors, the resolver, the stat sheet, the spy desks, the board and the next-speaker pick are technical end to end.
- A stored pack (`details.data.prompts`, served to the active game at `JSON_URLS.prompts` = `/api/runtime/json/prompts` and read by `loadPromptCatalog` in `gameplay.js` and `ensurePromptsLoaded` in `main.jsx`) is `{ "promptModel": 2, "guidance": { "advisor": { segmentId: text }, "leader": {…}, "tasks": { "jumpForward": {…}, … } } }` — the author's edits alone, trimmed, with blank and default-identical passages dropped (`normalizePackGuidance`). Nothing else is ever written.
- `normalizePromptPack` (`gameplayPrompts.js`) composes the runtime pack at load time: for every section it takes the **current** default text and replaces each edited segment's default passage with the author's text (`composePrompt`), then hands back the same `{ advisor, leader, helpers, tasks }` the renderers always used, plus `promptModel` and `guidance` for the editor. Helpers are always the defaults. Composition happens before rendering, so a `${PLAYER_POLITY}` inside an author's passage fills in like any other.
- **A pack in the old shape — whole prompt strings — is ignored.** Those packs froze the technical text at the time of the save; every scenario and game that has one now runs the current defaults (with no guidance edits, since the old model kept none apart). The built-in seed ships `{ "promptModel": 2, "guidance": {} }`, and `scripts/presets/build-preset.mjs` writes the same for a preset.
- **When the defaults change** (a release edits `defaultPrompts.json`): every scenario and game composes the new text on its next load. A passage the author edited keeps the author's text — edits are keyed by segment id, so a release that rewords a passage updates that segment's anchors in `promptGuidance.js` and the edit stays attached — and every passage they did not edit, plus all the technical text, follows the new default. A pack with no edits is always the current default in full (`promptGuidance.test.js`: "when the defaults change…").
- **A copied default is not an edit.** "Export all prompts" writes every passage (`materializePromptPack`), so a scenario that imported such a file (or a hub bundle made from one) stored the defaults of the version that wrote it as if its author had written them — and kept them after the game changed its defaults. `normalizePackGuidance` drops any stored passage identical, whitespace aside, to a default that any version has shipped, in English or in a shipped translation (`isShippedGuidanceDefault`): `src/Game/AI/shippedGuidance.js` holds their fingerprints (`guidanceFingerprint`, cyrb53), seeded on 2026-09-26 with every passage alpha, beta and main had shipped since packs became guidance-only and every translation of one. So a scenario like that, and every game played from it, runs the current defaults on its next load. The list only grows: after changing a default passage or a prompt pack, run `node scripts/prompts/record-shipped-guidance.mjs` (`promptGuidance.test.js` fails until you do). **Every branch must recognise every branch's defaults**, so a player on main whose scenario holds a copy of beta's or alpha's old defaults moves to main's current ones when that code is promoted: the list is one fingerprint per line and `.gitattributes` merges it with git's `union` driver, so merging alpha into beta or beta into main keeps both sides' entries; after such a merge run `node scripts/prompts/record-shipped-guidance.mjs --history`, which reads every version of the defaults and of the prompt packs in alpha's, beta's and main's histories (as `origin/<branch>`) and adds whatever the merged list lacks. Only stored packs are read this way — `composePrompt` takes the translated defaults as passages — and a passage its author changed by even a word stays theirs.
- `PROMPT_SECTION_DEFINITIONS` still lists every section with its `label`, `type` (`root` | `task`) and description (what a prompt is composed from is `DEFAULT_PROMPTS.helpers` and its template, not this list); `PROMPT_EDITOR_SECTIONS` is the subset with guidance, and it is what the Prompts tab shows — one textarea per passage, "Reset to default" per passage and per section, and under each a live counter, "N / max characters".

### The length limit (since 2026-11-07)

The owner, 2026-11-07: "add a character limit to prompts so they can at most be 20% larger than the built in defaults". The editable unit is the guidance passage, so the limit is per passage, keyed by section and segment id; with every passage within its own limit, a whole composed prompt is within 120% of its default too.

- **The limit** (`guidanceCharLimit`, `promptGuidance.js`): `ceil(1.2 × L)`, where `L` is the length of the **longest built-in version** of the same passage: the English default or any shipped translation of it (`public/lang/prompts/<code>.json`). The translations' lengths are in `src/Game/AI/guidanceLengths.js`, keyed by the English passage's `guidanceFingerprint` and written by `node scripts/prompts/record-shipped-guidance.mjs` (the same run that records the shipped fingerprints; `promptLimit.test.js` fails while it is stale; `.gitattributes` merges it with `union`, and a key that appears twice counts its longest). Measured against the longest rather than the player's language, so the limit is the same for every player (a scenario written in French is within it for a player who reads English) and a translated default, which runs up to about 40% longer than the English in some languages, always passes. The English length is read live from `defaultPrompts.json`, so the limit grows with the defaults and a default always passes (`promptLimit.test.js` checks every English and translated default).
- **How a passage is counted** (`promptCharCount`): line endings normalised to one character, the ends trimmed (as the pack stores it), every other character as it is; a placeholder such as `${PLAYER_POLITY}` counts its 16 characters. No placeholder is excluded: those inside a passage are guidance like the rest of it and an author may delete any of them, while the ones the game cannot do without sit in the technical template, which is never edited or counted against an author. The default is counted the same way, so keeping or dropping a placeholder costs what it looks like.
- **No built-in default**: a passage with no default (an unknown segment id, or a segment whose anchors no longer match) has a limit of 0. An unknown id never reaches a pack (`normalizeSectionGuidance`), and one whose default cannot be found has nowhere to go in its prompt. Authors cannot add prompts or passages, so no other rule is needed.
- **The editor** (`PromptSectionEditor`, `libraryBar.jsx`): typing is never blocked and a paste never cut (no `maxLength`). The counter turns red past the limit with "N characters over the limit: shorten it to save.", the section's button gets a red border, and **Save** is disabled with "A prompt passage is longer than its limit. Shorten it or reset it in the Prompts tab to save." (`handleSave` refuses too). Export is refused the same way, so a file never carries the default in place of the author's text without their knowing.
- **Load and import**: `normalizePackGuidance` (given the defaults, as `normalizePromptGuidance` always does) leaves an over-limit passage out **whole** and the default runs in its place. Nothing is ever truncated, so the AI never follows half an instruction. `normalizePromptPack` lists them in `overLimit` (`overLimitPromptPassages`, with the tab's section and passage names). The game's loaders (`loadPromptCatalog`, `ensurePromptsLoaded`) hand that list to `notePromptsOverLimit` (`src/runtime/promptLimitNotice.js`), and `PromptLimitNotice` (`GameUI/promptLimitNotice.jsx`) says once, per passage and text on this device, that the AI uses the built-in passage, and names it. The editor builds its form with `editablePromptPack`, which puts the over-limit text back in its textarea, so the author sees it in red and can shorten it; until then the scenario keeps it as it was stored and the game does not use it. "Import all prompts" does the same and says so in its status line. A hub download or a scenario file goes through the same `normalizePromptPack` when its game or editor opens.
- **Suggested changes**: `promptChangeOverLimit` (`suggestionApply.js`). The review does not accept an over-limit prompt passage and says why, and `buildDetailSave` (given `guidanceDefaults`) leaves one out.
- **The final guard**: `composePrompt` never places an over-limit passage (a shipped default, such as a translation, always goes in), and where a template is rendered for a request (`buildTaskSystemPrompt` in `gameplay.js`, the advisor and the leaders in `main.jsx`) `guardPromptTemplate` checks the composed template against `promptTemplateLimit` (the default template plus every passage's allowance; a technical prompt's own default length) and sends the default template if it is over.

### The frozen-prompt era, and the call-time directives it left behind

Before the guidance model a save carried a **frozen copy** of every prompt, so an edit to `defaultPrompts.json` never reached an existing campaign. That is why rules were **appended at call time in `runJsonTask`** (§6). The reason is gone — a rule written into `defaultPrompts.json` now reaches every scenario and game the next time it loads its prompts — and the time skip no longer appends any (§6a): its rules are in its template and its live records are rendered into it. New rules belong in the template; a call-time block is only for text that depends on runtime state.

## 3. How a final prompt is assembled, end to end

### 3a. Task path (`runJsonTask`, `gameplay.js`)

Order of concatenation onto the system prompt:

1. **Load pack** — `loadPromptCatalog` → `normalizePromptPack(readJson(JSON_URLS.prompts))` (the current defaults with the pack's guidance edits composed in, §2).
2. **Resolve helpers** — `helperValues = resolveHelperValues(prompts.helpers, variables)` (`promptContext.js`). Two passes so a helper that references another helper resolves.
3. **Render task text** — `systemPrompt = renderTemplate(prompts.tasks[taskKey], {...variables,...helperValues })` (`gameplay.js`). `renderTemplate` (`promptContext.js`) replaces `${key}` with `variables[key]` (missing/`null` → empty string). Both uppercase `${PLACEHOLDER}` keys (from `helperValues`) and lowercase `${var}` keys (from `variables`) are in scope.
4. **+ Difficulty directive** — `\n\n${difficultyDirective(game.difficulty, scope)}` for every task that decides an outcome (`taskReadsDifficultyDirective`, `difficulty.js`: not a time skip, not a task in `TASKS_WITHOUT_DIFFICULTY`, and not one that carries out what an event already decided, `TASKS_CARRYING_OUT_THE_RECORD`: the unit, structure and territory directors and the stat sheet); scope by `difficultyScopeForTask`: `diplomacy` for `idleDiplomacy` and the group-chat batch `chatActions`, `interactive` for the interactive tasks, else `simulation`. A time skip reads the simulation directive in its template instead (`${DIFFICULTY_DESCRIPTION_JUMP_FORWARD}`, §5), once. The difficulty's **priority block** is not added here: `callAI` puts it in FRONT of whatever was built (below).
5. **Time skips** render their standing rules (`${JUMP_STATIC_RULES}`) and their live records (`${JUMP_LIVE_STATE}`) into the template (§6a) instead of steps 4 and 6: nothing is appended after a jump's template.
6. **+ International Reputation** — only `actions`, `interactiveCreation`, `interactiveExecutor` (`gameplay.js`).
7. **Call `callAI(systemPrompt, [{role:"user", parts:[{text: userMessage}]}], { tool, maxTokens: 8192,... })`.** Inside `callAI` (`main.jsx`): **+ Language directive** `\n\n${languageDirective}` when the UI language ≠ English.
8. **Provider layer** (`main.jsx`): native tool-use providers (Anthropic/OpenAI/Gemini) pass `tool.schema` as a tool; the JSON-schema fallback path appends `\n\nReturn only one JSON object matching this JSON Schema…\n${JSON.stringify(tool.schema)}` (`main.jsx`). `maxTokens` is floored at 8192 by capped providers; Gemini ignores it.

So the final task system prompt is:

```
[PRIORITY — Difficulty: <level>] + the level's line + what holds at every level   (added by callAI; see "Difficulty leads every prompt")
\n\n<rendered task text>
\n\n<difficulty directive>
(a time skip: its template, with its standing rules at ${JUMP_STATIC_RULES} and the live records at ${JUMP_LIVE_STATE}, and nothing after it)
[\n\n[International Reputation]…] (5 tasks only)
\n\n<language directive> (non-English only)
[\n\n Return only one JSON object … <schema>] (json-schema fallback providers only)
```

**The user message, for a jump.** `runJumpSegments` builds it as `[<application receipt>, <changes made outside the simulation>, <political decision context>, buildSegmentInstruction(…), <scripted beats>, WRITING_REMINDER]`, joined by a blank line, each empty part left out, so the request ends on how an event is written. The receipt is `[APPLICATION RESULT FROM YOUR LAST TURN]` (`runtime/applicationReceipt.js`): what the engine dropped, withheld or changed in the previous turn's answer, plus what it applied. The second block is `[CHANGES MADE OUTSIDE THE SIMULATION SINCE YOUR LAST TURN]` (`runtime/gmChanges.js`): every change the Game Master made by hand in the round this skip starts from — told once, because the round moves on when the skip lands, and again after a rollback. Both go in the **user** message, not the system prompt, so the cacheable static prefix is untouched; both are repeated on every segment, because each segment is a separate request. See [AI overview](ai-overview.md#the-application-receipt-what-salvage-did-told-to-the-next-turn) and [the Game Master's hand](ai-overview.md#the-game-masters-hand-changes-made-outside-the-simulation-and-standing-reminders).

Retry (`gameplay.js`): each task gets **two output attempts**. On attempt-1 failure the model's raw answer plus a corrective user turn are appended to `history`, and attempt 2 runs against the same system prompt. `validatePayload` receives `{ attempt, finalAttempt }`; `finalAttempt` (attempt 2) switches validators from *strict* (return a corrective string) to *salvage* (repair in place). If both attempts fail, the deterministic `fallback` runs (or, for tasks with no fallback, it throws). A user `signal` abort propagates and cancels rather than falling back.

### 3b. Advisor / leader path (`main.jsx`)

These do **not** go through `runJsonTask` or `buildTemplateVariables`; they build variables directly from `buildPromptContext` (`buildPromptVariables`, `main.jsx`, with `eventLimit: 16`), demand-gated like the tasks (`chatPromptDemand` → `promptVariableDemand`, §5.1).

- **Advisor** (`buildAdvisorSystemPrompt`, `main.jsx`): `renderTemplate(promptPack.advisor, {...variables,...helperValues })` → `callAI`, which opens it with the difficulty's priority block (task `advisor`) and adds the language directive. No longer difficulty directive, no schema (free-form text reply). Called by `sendMessage` (`main.jsx`) with a rolling `advisorHistory`.
- **Leader** (`buildDiplomaticSystemPrompt`, `main.jsx`): `renderTemplate(promptPack.leader, …)`; the difficulty's **diplomacy** directive is in the template (`${DIFFICULTY_DESCRIPTION_CHATS}`), once, and nothing is appended for it; `callAI` opens the prompt with the priority block (task `diplomacy`). Then `sendDiplomaticMessage` (`main.jsx`) appends a per-turn user instruction telling the model to speak as one specific polity and optionally emit a trailing `REACTION:<emoji>` line (`main.jsx`), which `parseReaction` strips. `callAI` adds the language directive.

Because the advisor/leader path skips `buildTemplateVariables`, the military-feasibility doctrine (§5) is **not** appended to their unit text. Reputation, the intelligence rating and the Stats sheet reach them through `standingContext.js` instead, built from the world as the player has seen it (`viewAsSeen`):

- **The advisor** gets `[Our Country's Figures]` (`describeOurFigures`), right after its political and diplomatic context: the reputation and intelligence lines the tasks read (`describeReputationStanding`, `describeIntelligenceStanding`), then the government's Stats sheet in full, the `[Official National Statistics]` block (`describeCountryStatsForAdvisor` in `runtime/countryStats.js`, built by `describePlayerStatsForAdvisor` in `main.jsx`): government, leader and capital, stability, the strategic indices or a custom sheet's sections under the scenario's own labels and units, population, the economy with GDP per capita, the sector shares, and the recorded trend from `world.countryStatsHistory` for a chart. That block tells it to quote the figures as they stand and to estimate only what is not listed. The sheet stands in the prompt once: until 2026-10-06 the same figures were also given a second time, on one line with six history rows, which is what `describeOurFigures` still writes for a caller that hands it no sheet. Without a sheet the advisor is told to estimate and say so. The template's `[Other Guidelines]` passage says the same (the old wording, from before stat sheets, told it to extrapolate every statistic from historical records).
- **A leader** gets `[Standing]` (`describeLeaderStanding`) after its intelligence block: the player's reputation and its own, a line on what reputation means for trust, and its own government's figures — never the player's. The group-chat batch (`runChatActionBatch`) carries the same block in its user message with every AI participant's reputation and no government's figures, since they all read one request.
- **Both** get `[Occupied and Contested Regions]` (`describeTerritoryForConversation` → `describeTerritoryFor`) when it has anything to say: the rows of the same ledger the jump and the Game Master read (`territorialControlRows`, from `regionOwnershipOverrides`, `regionSovereigntyOverrides` and `regionClaimants`, read through `normalizeWorldState` as the jump reads them, so an owner filed under a GADM code or an era display name is folded onto its name; `buildTerritorialControlContext` formats the same rows; a world with none of those ledgers skips the region catalog), bounded to 24 — for the advisor the rows in which the player is sovereign, controller or claimant, for a leader those involving it or the player, and for the group-chat batch any participant. Names match exactly. Before, both only had the world summary's list of changes of control: nothing on claims, and nothing to tell occupation from sovereignty.

**The conversation is sent once, as the turns.** `ALL_ADVISOR_MESSAGES` (advisor) and `THIS_CHAT_HISTORY` (leader) used to render the transcript into the system prompt as well as sending it as the message turns — the same conversation twice, and, because it sat near the end of the system prompt, everything after it changed with every message, so no provider's prefix cache could reuse it. Both variables now render `CONVERSATION_IN_TURNS` (`main.jsx`), a pointer the templates' own sentences read naturally around, and a leader's own thread is also left out of the digest of its other chats (`buildDiplomaticSystemPrompt(…, { chatId })`). Measured on the Fault Lines save (the probe `conversation-anatomy.mjs`, in the private lab, not in this repo): an advisor message 124.4 K → 103.7 K characters with its system prompt identical from one message to the next (was 59%); a leader 70.2 K → 67.3 K, 100% (was 88%). Checked live: an advisor still recalls a code word from three exchanges back. The group-chat batch (`runChatActionBatch`) always sent its thread once.

**A player's message can carry a catch-up note** (`AI/conversationCatchUp.js`): written by the advisor panel when the world moved on since the last exchange — what became of the advisor's last reply (a chart not drawn, a block that half landed), the time that passed and the newest events since, and the Game Master's changes by hand. It rides ahead of what the player typed, is stored on the message, and is sent with it again after a reload (`loadHistory`).

**A leader's thread carries one too** (`buildThreadCatchUp`): the chat panel writes it onto the player's line when the world moved on since the thread's last dated line — the span, the newest events on the public record since, the borders they moved and the polities they renamed, founded or dissolved, and in a group the votes cast since the player's last turn. It rides ahead of the player's words (`withCatchUp`) in `sendDiplomaticMessage({ catchUp })` and in the group batch's user message (`runChatActionBatch({ catchUp })`), and is stored on the message (`catchUp`, `catchUpLabel`) so a reload or a retry sends the same words.

**Both get the Game Master's reminders** (`renderReminders`, `runtime/gmChanges.js`): the advisor among its directives before the formatting rules, a leader after its intelligence block.

**The advisor keeps a durable memory of the conversation** (`AI/advisorMemory.js`), as a diplomacy thread does: `[Your Memory of This Conversation]`, the last directive, asks every reply to end with `ADVISOR_MEMORY:<memory>` — one line under 1,200 characters, the COMPLETE memory carried forward (preferences, rejected ideas, what was agreed or promised in talk; not what the game already shows). `sendMessage` splits it off (`splitAdvisorMemory`) before the reply joins `advisorHistory`, and sends the newest ahead of the turns (`advisorMemoryContextEntry`); the panel strips it from the bubble, streaming included, and stores it on the message as `memory`, which `loadHistory` restores (`latestAdvisorMemory`). It rides on the reply already being written, so it costs no request.

**Only the advisor gets the player's standing goal** (`runtime/playerGoal.js`): `[Our Standing Goal]`, after the documents and before the reminders — the government's aim, to weigh advice by and to say plainly when an order works against it. A leader is never told it.

**The advisor's diplomatic options are cut a row at a time** (`advisorPoliticalDiplomacyContextCore.js`): `[Current Diplomatic & Institutional Options]` sends its capability manifest and the advisor's authority boundary first and whole, whatever the campaign holds. Its three lists (institutions, pending lifecycle cases, threads) share what is left of `ADVISOR_DIPLOMACY_OPTIONS_MAX_CHARS` (7,600, never under 1,500): each row in full while it fits (twelve at most), then a one-line short form (an institution's name, id, standing and `vote pending`; a case's kind and status; a thread's identity and participants), then `N more … omitted from this brief`. The builder passes every pending lifecycle case and counts the threads past the 18 it reads. The advisor has no institution lookups, so the brief never tells it to use them.

**Both read the documents file** (`world.reports`), bounded to eight, each body cut to 220 characters: the advisor `[Documents Our Government Holds]` — every paper the player's government can read, saying how it came by each (held with whom, ours alone, published, or a copy its agents took, which the holders do not know it has; `describeDocumentsForAdvisor`, `runtime/reportDelivery.js`); a leader `[Documents Your Government Holds]` — its own, the published ones and those its own agents stole (marked as obtained covertly), by the audience rule (`audienceSeesReport`, `audience.js`), never who else stole a copy.

## 4. Placeholder → variable helper map

`defaultPrompts.json` → `helpers`. Task/root text uses the uppercase `${PLACEHOLDER}`; the helper maps it to a lowercase `${var}` computed in `buildPromptContext`. "Used by" lists the prompts whose **default text** actually contains the placeholder: `advisor`, `leader` and `tasks.*` in `defaultPrompts.json`, except that for `gameMaster` it is `NATIVE_GAME_MASTER_PROMPT` (`gameplayPrompts.js`), which `runJsonTask` renders in place of `tasks.gameMaster`.

### 5.1 Context envelope and demand-driven construction

The save remembers everything; a task is shown a bounded, deterministic slice of it (`promptContext.js` + `contextDiagnostics.js`):

- **Demand.** `buildTemplateVariables(bundle, { taskKey })` resolves which variables the ACTUAL loaded prompt pack can reach (the task text, the helpers it references, and the live directives `runJsonTask` appends for that task — `LIVE_RUNTIME_VARIABLE_KEYS` in `contextDiagnostics.js`) plus the two the runner itself reads (`RUNNER_VARIABLE_KEYS`: `worldBeforeRoundOne` and `simulationRules`, which the de-duplication of the briefing needs), and passes them as `requiredKeys`; `buildPromptContext` then builds only those, so the region catalog, world summary, chats and border geometry are skipped when a task never renders them. Every task call site passes its task key (`generateCountryStats`, which is not a pack task, passes the five keys its briefing reads); the advisor and the leaders pass `promptVariableDemand` over their own templates, plus the keys their directives read, less the ones they overwrite with the conversation's turns — so a leader's reply no longer builds the force posture, the city catalog or the markers. A caller without a task key, or an unresolvable demand, gets the full build. `resolveHelperValues` renders only reachable helpers. A variable a live directive reads that is missing from `LIVE_RUNTIME_VARIABLE_KEYS` is silently never built (the Game Master's Projects board was, until it was listed), so `contextDemand.test.js` reads `buildTaskSystemPrompt` and `buildJumpLiveState` and fails on any on-demand variable a task's directives read that its list does not name.
- **Budgets.** `buildEventHistoryText`, `buildDetailedChatHistoryText` and `buildConsolidatedHistoryText` accept `maxChars`; whole records are kept and every omission is declared in the text. Jumps run under the world-simulation envelope: 24k chars of consolidated history selected for **coverage** (newest continuity, the campaign foundation, evenly spread middle blocks), and once the full history exceeds 24k, up to 6k chars / 18 **permanent historical anchors** chosen from the consolidated past by provenance (critical events, the origin events of active wars, agreements and storylines, durable structural changes: a polity created, restored, renamed or dissolved, a sovereignty transfer, an occupation (`regionControlOps` control), or a group founded or dissolved). Each event in the recent-events text carries compact notes of its territorial shifts, control changes (`Control:`), group changes (`Groups:`), polity changes and political changes. Variables: `consolidatedHistory`, `historicalAnchors`, `historicalAttentionStatus`, and `recentEventsLong` (which embeds both).
- **Diplomatic memory.** A chat message may carry `memorySummary` (rolling durable memory of the thread); `diplomaticContinuity` renders the latest memory per thread with a short verbatim tail. A time skip without the lookup functions gets each thread once instead: `chatHistoryLong` gives each thread's memory and then its last words, followed by the older threads that still carry a memory (`buildDetailedChatHistoryText` `memoryThreads`), and `diplomaticContinuity` is empty (a chat kept on file is in none of them: its binding word and excerpts follow, §5.3); with the lookup functions on, the short chat view keeps the separate `[Diplomatic Memory]` block. `chatHistory` and `chatSummary` show the memory line too.
- **Marker attention.** `markersSummary` is a bounded, deterministic subset of world features (recently touched, under construction or damaged, named in recent events, the player's queued orders (status `planned`; answered ones are ignored) or chats, plus a rotating background sample), sized per task.
- **Diagnostics.** Set `globalThis.__OH_CONTEXT_DIAGNOSTICS__ = true` in DevTools: every structured request logs its demand, constructed-versus-required variables and sizes (`logContextDiagnostics`), and `buildTemplateVariables` logs its build time. Observational only.

### 5.2 Related past events (since 2026-11-07, beta)

Always on (the model ships with the game; no setting), a time skip (`jumpForward`, `autoJumpForward`) carries a fourth part in `recentEventsLong`: up to six past events found on the player's device as nearest to the turn's pending orders, live wars, live storylines and the powers in focus, one line each (date, title, the event's `digest` or the first 200 characters of its description), in date order, within 2,000 characters, under a header that ranks them below the ledgers and the newer events. Only events folded into the history are eligible while the skip lists every other event since the story so far (the "also recent" lines, lookups off); with the lookup functions on, so are those older than the oldest event the window of recent events shows. None is sent twice. `simulateTimelineJump` asks for the candidates (`findRelatedForSkip`, `relatedEventsSearch.js`) before `buildTemplateVariables` and passes them as the `relatedEvents` option; the search makes no request and gives up after 1.5 s, and without it the history is exactly as before. Once the model has loaded, every task with lookups also gets `similar_events` (`lookupTools.js`), a search of the whole timeline by meaning. The model, the index and the timings: [runtime-services.md](runtime-services.md#related-past-events--srcgameairelatedeventsjs).

### 5.3 Older conversations kept on file (since 2026-11-07, beta)

The owner's rule: a chat that has not been used in more than one game year **and** was last used at least four time skips ago is stored as vectors on the player's device and retrieved only when relevant; every other chat is sent as before. `chatArchive.js` `isArchivedChat(chat, ctx)`: the chat's last use is the game date of its latest message or log event (`chatLastUsed`); "more than a year" is that date plus twelve months still before the game date (`moreThanAYearBefore`); the skips since are the entries of `world.simulationHistory` (the last twelve) that began on or after it, never more than `game.round` (`skipsSince`; a skip's own letters are dated the day it ended, so the skip that wrote them is not counted). A chat with no dated word is never archived. **Never archived** (`archiveExemption`), however old: the conversation the player has open (`runtime/openConversation.js`, set by the Diplomacy panel), a chat with a demand still open or countered, a chat with an open peace offer (its own, or one between the player and a partner), a chat with any power on either side of a live war the player is in (the enemy peace is made with, the ally the war is planned with: `frontPrompt.js` reads allied plans from the talks), an institution's open lifecycle negotiation, and a group chat with a vote some member (the player included) has not cast. A chat folded into the history (`consolidatedHistory` `chatIds`) is neither sent nor kept on file, as before.

`buildPromptContext` splits the chats it may show (after the visibility filter) with `partitionChats` once, so every chat-derived variable agrees: `chatHistoryLong`, `chatSummary`, `diplomaticContinuity` and `chat` carry the active chats only; `chatsToConsolidate` (the fold's own fallback) still reads every unfolded chat. After the active threads, `chatHistoryLong` carries (`renderArchivedChats`):

1. one line: "N older conversations kept on file (with A; B)", naming the lookups when the task has them (`past_talks`, `similar_events`, `chat_history`); a large table is named by its title and size ("United Nations (198 members)");
2. `STANDING WORD FROM OLDER TALKS`: of each archived chat, the sentences of its standing memory that agree, promise, threaten, warn, refuse, owe or hold a grudge (`bindingSentences`), 320 characters a chat and 1,500 in all, so a promise or a treaty is never lost while it is not recalled; a chat whose memory the excerpts quote is not repeated here;
3. `PAST DIPLOMACY (older talks that bear on now)`: the chunks nearest to the task (below), with who they were with and when, within 2,500 characters, best first, grouped by chat; a chunk is never shown twice, and two neighbouring chunks read as one passage without the lines they share.

**Chunks** (`chatChunks`): the chat's latest standing memory, then each message as `[date] speaker: text`, packed into chunks of at most 800 characters with up to 150 carried over from the chunk before, cut between messages (a message longer than a chunk at its sentences, a sentence longer than that at its words). What is embedded is `Talks between <player> and <partners>: <chunk>`, read to 256 word pieces (`CHAT_CHUNK_MAX_TOKENS`, the model's tuned length; an event is read to 128).

**The search** (`relatedEventsSearch.js` `findPastTalks`): one query each (at most 12, `buildPastTalksQueries`) for the request's own words (a leader's thread's last three lines, the advisor's question), the leaders being addressed, the player's pending orders, the live wars, what the three most recent active chats last said, and the powers in view (`rankFocusPowers`, which carries idle diplomacy's relevant countries: `promptFocus.js`), ranked as related events are (`relatedScores`, cosine 0.25 and above, 30 candidates), only among the archived chats the prompt may show. A time skip runs it beside `findRelatedForSkip` (`Promise.all`), each within 1.5 s; the advisor (`buildAdvisorSystemPrompt`) and a leader's reply (`buildDiplomaticSystemPrompt`, over the chats that leader was in) run it too, without the powers in view. Slower, failed, or nothing indexed: the excerpts are left out, and the count and the binding word stay. Once the model has loaded and some chat is kept on file, tasks with lookups get `past_talks` (`lookupTools.js` `PAST_TALKS_TOOL`, `withPastTalks`): a query, an optional power and a limit (4, at most 8), answered with the passages, with whom, when and how close. The index: [runtime-services.md](runtime-services.md#related-past-events--srcgameairelatedeventsjs).

**Difficulty leads every prompt** (`difficulty.js`, since 2026-10-11). Difficulty decides how things go for the player: almost always well on Very Easy, usually well on Easy, realistically on Medium, often poorly on Hard, usually poorly on Very Hard, almost always poorly on Impossible. This reverses the earlier doctrine ("Difficulty 2.0"), under which a level changed only how much benefit of the doubt a plan got and how able the opposition was, and promised a world that never leaned for or against the human. Each level now has a `priority` line of two or three sentences, and `difficultyPriorityBlock` writes it as `[PRIORITY — Difficulty: <label>]`, the line, and one paragraph that is the same at every level: this comes before every other instruction on how things turn out (a later passage on how difficulty applies included); each outcome has a cause the text gives; what the player orders is always attempted and always gets an outcome; established facts, figures and the Game Master's instructions are never rewritten; where an event or the record already says how something turned out, that stands and no tilt is added; and nothing the player reads says the word difficulty.

`withDifficultyPriority` puts the block in front of a system prompt, and `callAI` (`main.jsx`) calls it for every request the game sends, as `submitAIBatch` does for a batched one, so no task can be built without it. **The provider's prompt cache**: the block is the same for every call of a campaign, so it belongs to the game-lifetime prefix; `withDifficultyPriority` moves `staticPrefixEnd` forward by the block's length, the prefix that was byte-identical from call to call still is, and Anthropic's `cache_control` split (`splitSystemPromptForCache`) and the implicit prefix caches of OpenAI and Gemini cover it. Changing the difficulty mid-game changes the first bytes once and the cache refills.

### 6a. The time skip's prompt (since 2026-09-26)

A time skip (`jumpForward`, `autoJumpForward`) is its template with two blocks rendered into it: the standing rules at `${JUMP_STATIC_RULES}` (helper → `jumpStaticRules`, `buildJumpStaticRules` in `gameplay.js`) and ONE block of live records at `${JUMP_LIVE_STATE}` (helper → `jumpLiveState`, `buildJumpLiveState`). Nothing is appended after the template, so the template decides where everything sits. Since 2026-11-07 it is laid out for the providers' prompt caches (sizes before and after: [prompt budget](prompt-budget.md)): everything no turn of a campaign changes comes first, the two templates are byte-identical up to `${CACHE_BREAK}` (a placeholder that renders as nothing; `promptLayout.js` `CACHE_BREAK_KEY` reports where it falls), and the live records come last. Until 2026-09-26 the template was followed by some twenty rule blocks appended at call time (Player Agency, Map Truth, Why the Land Moves, Region and City Capture, Unit Coordinates, Units on the Map, Other Powers' Militaries, Sovereign Acts, the Counterfactual Knowledge Boundary, the World Director's doctrine, the Diplomatic Consequence Bridge, the 17,000-character Actions You Can Take…): a 30-day skip on the shipped 2014 save sent 186,630 characters, about 104,000 of them instructions. The same skip now sends about 106,000, most of it the world.

The template, in order:
1. **The brief** — `[What a Polity Is]`, what the game is; `[Your Role]`; `[Real History Is the Default]` (a game set in our history follows real history wherever the game has not changed things, and departs from it only where the game has; an alternate history from its divergence; a fictional world from its lore); `[Difficulty]` (the level's simulation directive, `${DIFFICULTY_DESCRIPTION_JUMP_FORWARD}`, then what difficulty makes harder); `[Player Agency — critical]`; `[What an Order Can Do]` (every order gets an outcome and cites its id; consent, means, authority, the pace of a war); `[The World Answers Back]` (the world moves first, both sides fight, the ban is on inventing a rivalry).
2. **How the world is recorded** — `[The Map]` (sovereignty = regionTransfers, control = regionControlOps, claims = regionClaims, the basis and what the engine does with it, place names the engine resolves), `[Polities]`, `[Placing Things — say WHERE in words]`, `[Units and Structures]`, `[Diplomacy]`, `[Reports — documents, not summaries]`.
3. **How the answer is recorded** — `${JUMP_STATIC_RULES}`: the rules the live records used to carry on every turn, built from what a campaign does not change (the player, the game's features, the era): `[Levers]` (what the output function's field notes leave out; the field shapes are the function's), `[Every Event Carries Its Consequences]` (a folded skip), `[Units and Structures on the Map]` (with the era's travel pace), `[Military Feasibility]` (the doctrine that used to ride the units list every turn), `[Taking Ground]`, how the Projects board is kept (from the board's first entry on: the op formats, the four answers, the proportion rule), the groups rule (Groups on), `[How Wars Are Recorded]` and `[How Relations and Agreements Are Recorded]` (the ledgers' hard rules and line formats), `[Reading the Diplomatic Ledger]` (how the slice is read, `DIPLOMATIC_SLICE_RULES`), `[What Chats Bind]`, `[Front Orders]` (how a front order line is written, Fronts on), `[Who Spies on the Player]` and the espionage orders (Espionage on). `buildJumpStaticRules` reads the save for the era and the board, so the block changes only when the game's features change, the game's date crosses into another era of travel (`unitMotion.js` `eraOf`, or the scenario's era setting) or the board gets its first entry, and each costs the cache once.
4. **`[How to Write an Event]`** (guidance, id `quality`) — the title is the headline; the description is the article under it and tells the story (who acted, what they did, in what order, where, with what, what it cost, how it ended), never the headline restated; specifics; a minor event at least a full paragraph, a major one several; quotes; what counts as an event; an example from real history. No word cap and no voice rules.
5. **The scenario** — `[The World Before Round 1]`, `[What Is True Now]` (technical: the map and records outrank the game's events, which outrank real history and the briefing), `[Extra Simulation Rules for This Preset]`. Then `${CACHE_BREAK}`: everything to here is the same in both templates, the part Anthropic pins with a breakpoint of its own.
6. **The mode's own part** — the rest of the opening (what this kind of jump is), `[What to Simulate]` (guidance, id `scope`: the whole world, as many events as the period holds), the auto-jump's `[Where the Auto-Jump Stops]` and `[How Many Events]`, `[Output]`.
7. **The campaign's reference** (cached with the opening, since it changes only now and then) — `[City Coordinates]` (`${CITY_COORDINATES}`, the map's own catalog, lat, lng), `[Polity Lore]` (`${POLITY_LORE_REFERENCE}`: every polity's note as of `world.promptReference`, renewed after six notes have moved or 25 rounds; a note written since rides in the map description) and `[The Story So Far]` (`${CAMPAIGN_HISTORY}`: the canon, then the history document's eras and years, rewritten only when a fold is written; the event history below points at it). See [the history in tiers](#the-history-in-tiers-and-the-canon). All three are static keys (`STATIC_PROMPT_KEYS`), so the cacheable prefix runs on to the first value a turn changes: `${CURRENT_ROUND_NUMBER}`, in the turn's premise that opens part 8.
8. **This game** — turns premise, event history (the newest skip's events in full, older ones by their one-line digest, then a line each for the recent events the ranking left out), this round's orders (with their ids), the map description (without the briefing the template already gives), chats (each thread once: its memory, then its last words; a chat kept on file only counted, with its binding word and the excerpts that bear on the turn, §5.3), units, structures. What the turn is about is shown in full and the rest in a line (`promptFocus.js`, `buildPromptFocus`): the powers in view are the player, its neighbours (regions whose boxes touch, or declared adjacent), its relevant countries (idle diplomacy's `rankRelevantPolities`, `idlePoliticalDiplomacyContext.js`: the twenty latest to have had something happen to them or to have dealt with the player, scored as a neighbour is; on a map without political profiles they are ranked among the map's own powers), every power at war, every power the orders name, the chat partners, the powers the recent events moved or named, and those changed since the last skip (`world.promptSnapshot`, stored by `applySimulationResult`: each power's region count and hashes of its roster line, tags and lore as the skip that just ran read them) or in a live storyline; the player, every belligerent and every power the orders name are never capped out. No power is singled out for a turn of its own: the rotating spotlight on three distant powers was taken out after the quality A/B (its sentence read as a quota; [round 2](prompt-compression-ab.md#round-2-the-fixes)). The map description gives region names for the powers in view and then, while the names stay under the budget of 480, for the next powers by rank; a roster line for the others in view (`TIERED_ROSTER_INTRO`: name a place in one by a city of [City Coordinates] or as the country); and every other power by name and size in one paragraph, each with what the records say of it (`buildOneLineDetail`: who leads it, whom it is at war with, its alliances and agreements, its latest peace, and who holds its land or whose land it holds, each only where recorded), followed by a line saying a region the description never names is held as on the scenario's map but for the territorial changes listed (one line pointing at `list_regions` and `power_info` with the lookups on). Territorial changes and tags are grouped; an override for a region the map does not have is left out of the changes rather than printed as its id. Units are a table (by owner; type, strength under 100%, posture when not idle, what it is, lat, lng), and the units of powers out of view are named by type in a line per owner; structures likewise (name: kind, owner, status when not active; lat, lng; dates; what it is), the city catalog `name (country): lat, lng` with the order of the fields said once, and the hidden backend's figures in words (1.43 billion, not 1430000000), rounded to three digits; the military feasibility doctrine is said once, among the standing rules. Occupied and contested regions are grouped by sovereign, controller and claimants, the lines of the powers in view naming every region; land no power rules is capped at 40 neighbouring powers, and the air strikes block at 6,000 characters (the heaviest strikes kept, the rest counted). Every region the prompt names is named, never given by its id: the event history's impact lines, the group areas and the World Director's pressures and units go through `promptRegionNamer` (`promptContext.js`, over `nameRefs.js` `regionNamer`), which gives the map's name, `region: X` where the name alone could be another region of the map or a country, and nothing for a region the map lacks (`promptNamesNotIds.test.js` scans a rig-built skip for every region id of its map). Other tasks keep their untiered summaries.

   **Places.** An event's `places` follow `EVENT_PLACES_RULE` (`eventPlaces.js`, in the standing rules): a region is one [Game Map Description] lists by name, a power listed without its regions is placed by a city of [City Coordinates] or as the country, and the country after a city or a region is the power that holds it now. The [City Coordinates] header says its names are what a place, a unit's `at` and a structure use. The finder (`buildPlacementGazetteer`, `gameplay.js`) ranks a region said with a country by its holder first, then by the country it lies in on the base map (a stock id's ISO3, or the row's `base`), so "region: Métropole du Grand Paris, country: France" is found on a map where Italy holds Paris.
9. **`${JUMP_LIVE_STATE}`** — `[Social Media]` (Rostra's posts as public statements, and the posts the period is to write, §7.18; only while the Social media feature is on), `[This Game and Real History]` (`buildRealHistoryDirective`, `futureHistoryBoundary.js`: when the game began and, from Scenario Canon v2, whether and where this world split from ours), occupied and contested regions, `[Groups]` (the current areas, the rule itself being among the standing rules; #### What a provider can cache

The request, front to back, as a provider's prompt cache sees it (sizes per save: [prompt budget](prompt-budget.md)):

| Part | Ends at | Changes when | On Anthropic |
|---|---|---|---|
| The functions | the system prompt | the skip's own options change; the agents' reports are offered only on a skip with agents due, so the turn-to-turn function is the same | cached with the prefix (tools come first in Anthropic's order) |
| The difficulty's priority block, then parts 1 to 5 | `${CACHE_BREAK}` (`sharedPrefixEnd`) | never within a campaign, whichever of the two skips runs | breakpoint 1, kept an hour |
| Parts 6 and 7 | the first per-turn value, `${CURRENT_ROUND_NUMBER}` (`staticPrefixEnd`) | the lore reference is renewed (`world.promptReference`: six notes moved, or 25 rounds and any note moved) or a history fold is written; that one skip pays for it | breakpoint 2, kept an hour |
| Parts 8 and 9, and the language directive `callAI` appends | the end of the system prompt | every turn | breakpoint 3, only on a call that offers a function that answers back (`order_troops`, the lookups), so that its next round reads it; five minutes |
| The conversation so far | its last block | each lookup round | breakpoint 4 (`toolTurns.js` `withCachedHistory`), only on a round that follows lookups |
| The user message | — | every turn and segment | — |

Four breakpoints are all Anthropic takes. None is set on a block under `MIN_CACHEABLE_PREFIX_CHARS` (3,000 characters, about Anthropic's 1,024-token minimum). `ttl: "1h"` goes only with `jumpForward` and `autoJumpForward` (`HOUR_CACHED_TASKS`) and only to Anthropic's own API, never a compatible proxy: a write costs twice the input price instead of 1.25 times and a read a tenth, and a skip's next turn rarely comes within five minutes, so it pays from the third skip in an hour. OpenAI's own API gets `prompt_cache_key` (`gameplay.js` `promptCacheKeyFor`: `oh-<hash of the campaign id>-skip` for both skips, `oh-<hash>-<task>` for the rest; nothing of the save leaves in it). Gemini and OpenAI cache an identical opening on their own, which this layout gives them from skip to skip; the A/B saw Gemini's implicit cache take 45k to 63k tokens (`cachedContentTokenCount`).

What keeps the prefix byte-identical: everything in it is rendered from `STATIC_PROMPT_KEYS` (`promptLayout.js`), each block that rides there renders the same text for the same save (the city catalog, `buildPolityLoreReference` from the stored reference, the story so far as last folded), and nothing is appended after a skip's template. `promptLayout.test.js` holds the share of each template ahead of its first per-turn placeholder, and `staticPrefixEndOf` drops a boundary the final prompt no longer opens with, so a rewritten opening is sent uncached rather than cached wrong. A template edit that puts a per-turn placeholder earlier, or a static key whose value varies by turn, silently costs every skip its cache.

Event ranges (`eventCountRangeForDays`): under a day 1-2, a week 3-6, a month 10-15, a quarter 16-22, half a year 22-30, longer 28-36; a segment of a split jump asks for its share of the whole jump's range, and the queued orders raise the floor as before.

## 7. AI tasks

Each subsection: purpose · default prompt location · entry point · key inputs · output tool/schema · validation & fallback. All schemas are in `gameplaySchemas.js`; the tool name is what the model calls. Task text lives at `defaultPrompts.json` `tasks.<key>`.

### 7.1 `jumpForward` — manual time skip
- **Purpose:** Simulate every event between the origin date and a player-chosen target date; move the map, units, structures, diplomacy.
- **Prompt:** `tasks.jumpForward`. **Entry:** `simulateTimelineJump({days, mode:"jump", signal})` `gameplay.js`.
- **Inputs:** full state bundle; `targetDate`; event-count band from `eventCountRangeForDays(days)` (a month 10-15, §6a) with a floor of one event per queued action; duration label; `${CURRENT_UNITS/MAP_STRUCTURES/CITY_COORDINATES}`; the live records (§6a).
- **Tool/schema:** `submit_jump_result` / `JUMP_FORWARD_SCHEMA` (`gameplaySchemas.js`). Payload: `events[]` (each `date/title/description` + `impacts`), `stopDate`, `summary`, `clearActions`, top-level `diplomaticOutreach[]`. No scene: now and then the skip offers one of its events as an interactive event instead, at no cost (`runtime/interactiveOffer.js`).
- **Validation:** `validatePayload` (`gameplay.js`) — strict on attempt 1 / salvage on final: event-count range, `validateTimelineDates` then `clampTimelineDates` on salvage, then `validateGeneratedWorldChanges` resolving region names → ids (`resolveRegionTransfers`) with a corrective owner-region list (`buildTransferFeedback`) and the two **capture-reluctance guards** (strict attempt only; off for the GM preview through `captureGuard: false`): capture wording (`CONTROL_CHANGE_LANGUAGE`) with zero `regionControlOps`, and legal-settlement wording such as annex*/cede* (`LEGAL_TRANSFER_LANGUAGE`) with zero `regionTransfers`. See [ai-schemas.md §5.4](ai-schemas.md). **Fallback:** `fallbackJumpSimulation`, whose events and summary are written in the player's language: its sentences are the `FALLBACK_TURN_TEXTS` table (`src/runtime/fallbackTurnText.js`), which the language packs carry, looked up whole in the player's pack when the turn is written (`uiString`, English where the pack has none). Timeout: unbounded unless the "Limit AI generation" map setting is on (then 5 min); `signal` aborts cleanly.
- **Applied by:** `applySimulationResult` — appends events, bumps round/date, resolves planned actions, applies impacts, opens generated chats, writes a `simulationHistory` entry, snapshots for rollback.

- **What the jump is told** (both jump templates; pinned by `jumpPromptCraft.test.js`; the whole layout is §6a):
 - `[Real History Is the Default]` *(guidance, id `history`)* — the real events of the period happen, with their real people, places, dates and numbers, unless something in this game has changed their causes; the game departs from history only where the game has; an alternate history follows ours only to its divergence, a fictional world its own lore. It replaced the call-time Counterfactual Knowledge Boundary ("MEMORY IS NOT EVIDENCE"), under which a skip could not hold a month's real elections or crises.
 - `[What an Order Can Do]` *(guidance, id `orders`)* — every order is an attempt and gets an outcome, citing its id; acts that need nobody's consent happen now, acts that bind another polity need its agreement or a fait accompli (else a claim); means and authority decide what is possible; wars take time.
 - `[What Is True Now]` *(technical — deliberately **not** editable)* — the order of authority: the current map, records and last turn's application result; then the game's events, which explain the present and are never evidence of who holds what today; then real history and the world before round 1, the default for everything the game has not changed.
 - `[The World Answers Back]` *(guidance, id `reactions`)* — every other polity acts on its own interests; the world may move first, including against the player; both sides of a fight fight; a large move by the player gets answers from every power with a stake; other powers' forces show on the map; the player's own reply is never decided for them.
 - `[How to Write an Event]` *(guidance, id `quality`)* — last in the prompt: the title is the headline, the description the story under it, never the headline restated; no word cap, no voice rules.

### 7.2 `autoJumpForward` — auto skip to the next notable event
- **Purpose:** Same engine, but **stop early** at the first strategically notable / player-relevant / memorable event and set it `notable:true` (a notable event is preferred when the skip offers an interactive event).
- **Prompt:** `tasks.autoJumpForward`. **Entry:** `simulateAutoJump({days=365, signal})` → `simulateTimelineJump(mode:"auto")` `gameplay.js`.
- **Tool/schema:** `submit_jump_result` / `AUTO_JUMP_FORWARD_SCHEMA` (= `JUMP_FORWARD_SCHEMA`, `gameplaySchemas.js`).
- **Validation:** same validator; in `auto` mode `stopDate` may be any date after origin and ≤ target (`validateTimelineDates` in `timelineDates.js`); the event-count range is not strictly enforced.

### 7.3 `actions` — strategic action suggestions
- **Purpose:** Produce 6–9 "Topics of Concern," each with 2–5 concrete actions (kind `action`, or `chat` for outreach).
- **Prompt:** `tasks.actions`. **Entry:** `generateActionSuggestions({force})` `gameplay.js`.
- **Tool/schema:** `submit_actions` / `ACTIONS_SCHEMA` (`gameplaySchemas.js`): `topics[] { title, description, actions[] { title, text, kind, invitees, chatStarter } }`.
- **Validation/fallback:** accepts array/`topics`/`suggestions` shapes; empty → `fallbackActionSuggestions` (the four `FALLBACK_SUGGESTION_TOPICS`, written in the player's language from `FALLBACK_TURN_TEXTS`, `src/runtime/fallbackTurnText.js`). Result stored on `world.actionSuggestions`; canned topics (a failed task or an empty answer) are stored with `source: "fallback"`. Returns `{ topics, source, fallbackReason, rawResponse }`, so the Actions panel can say the list is generic.

### 7.4 `descriptionToAction` — freeform text → structured command
- **Purpose:** Turn the player's raw sentence into one action (or a chat invitation), ~50% longer, tone-matched, ≤650 chars.
- **Prompt:** `tasks.descriptionToAction`. **Entry:** `refinePlayerAction(rawInput, {persist})` `gameplay.js` (passes `actionInput`). Returns `{ action, source, fallbackReason, rawResponse }`; on `source: "fallback"` the Actions panel keeps the player's text instead of the template.

- **Fallback:** `fallbackDescriptionToAction` — heuristic chat detection via `looksLikeChatRequest` (`chatHints.js`: stems for talks, negotiations, meetings and messages in every language with a shipped pack; a stem starts a word where words are written apart, and may sit anywhere in German compounds and in scripts without spaces) and `inferInviteeNames`; its text is written in the player's language from `FALLBACK_TURN_TEXTS`.

### 7.5 Diplomatic speaker routing — native / in-batch
- **One-on-one:** there is exactly one AI counterpart, selected natively. No speaker-selection model call exists.
- **Groups and institution conversations:** `runChatActionBatch` is the canonical path, for an institution's Council even with a single AI member (it has an agenda, a charter and votes, which the one-on-one leader path cannot act on). The same AI request that decides what the table does also decides who speaks, reacts, votes, or stays silent and in what order.
- **Failure:** the group batch fails closed and reports the request error. There is no legacy sequential group-chat fallback and no standalone `nextSpeaker` prompt/tool/schema.

### 7.6 `eventConsolidator` — compress history
- **Purpose:** Fold a batch of events + closed chats into one continuity summary (~≤360 words) so old detail leaves the context window without losing map/diplomacy facts.
- **Prompt:** `tasks.eventConsolidator`. **Entries:** a time skip carries a fold that is due inside its own request: the whole prompt goes into the skip's as a fenced job and the answer comes back in the skip's `history` field (`prepareSkipHistoryFold`, `buildSkipHistoryJob`; see [the folded time skip](ai-overview.md#the-folded-time-skip-one-request-its-own-consequences)). `consolidateHistoryBatch` is the same prompt as a request of its own: run by `compactHistoryIfNeeded` only for a skip that could not carry the fold, and by `consolidateHistoryNow` (Cheats → History Document, refused while a turn is in flight).
- **Tool/schema:** `submit_event_consolidation` / `EVENT_CONSOLIDATOR_SCHEMA`: `{ summary, years, canon, eras, document }`, only `summary` required. A time skip's `history` field takes the same fields, loose (its function is near the size Gemini takes).
- **Fallback:** concatenate raw event lines + `buildChatSummaryText`. Triggers: `CONSOLIDATION_*` thresholds (`gameplay.js`).

#### The history in tiers and the canon
Since 2026-11-07 (`runtime/historyTiers.js`) the history document is kept in tiers instead of one text near 1,500 words that every fold rewrote whole (and condensed by the model's own judgement of what mattered): `historyDocument.years` (a paragraph per game year, the newest three), `historyDocument.eras` (the older years; a fold condenses them only when they pass 1,200 words, and a revision keeping less than a third of their words is refused) and `world.canonFacts` (treaties, deaths, regime and border changes, office holders and wars, each dated: never condensed, and kept in the save up to 400 facts, past which superseded facts go first and then the oldest (`normalizeCanonFacts`); an office's fact is superseded on the page by its next holder's, and stays in the save). `buildHistoryDocumentDirective` asks a fold for `years` (the whole paragraph of each year its material covers), `canon` (only what is new) and, when they are over their budget, `eras`; `judgeSkipHistoryAnswer` and `applyHistoryDocumentUpdate` take each entry on its own merits against the years the fold covers (`yearSpanOf`), and say what they left out. `buildConsolidatedHistoryText` gives the canon, the eras and the years each their own budget, the canon first. A save from before keeps its document as its first era from the first fold that writes years; one that only appended a summary keeps it as a note "Since then", which the next fold folds in.

**The skip's tiers name their fields.** A folded skip's `history` field (`foldJumpTool`, `gameplaySchemas.js`) gives `years`, `canon` and `eras` the consolidator's own entry shapes (`HISTORY_YEAR_ITEM` `{year, text}`, `HISTORY_CANON_ITEM` `{date, kind, text, key}` with the kinds of `CANON_KINDS`, `HISTORY_ERA_ITEM` `{from, to, text}`), without descriptions; the turn-to-turn function is 30,088 characters as Gemini gets it, under the 30,435 that went through. Before, the items were objects with no properties and Gemini answered every one as `{}` ([the A/B](prompt-compression-ab.md#the-specific-failures)); in [round 2](prompt-compression-ab.md#round-2-the-fixes) the fold on the round-67 save came back with two years and a canon fact, all taken. **No fold, no history.** The function offers `history` on every folded turn (a function that changed on the turns a fold rides would throw away the provider's cached prompt, functions and opening, on each of them), so a skip with no fold due is told, last, where the job would be: "No history job rides on this answer: leave the "history" field out" (`NO_SKIP_HISTORY_JOB`), and the field's description says the same. Round 1 filled it on 3 skips of 4 without a job; round 2 on none of 4.

### 7.10 `pregameHistory` — backstory generator
- **Purpose:** Write 4–10 dated events **strictly before** the start date, and the Round-One bootstrap of the ledgers (wars, relations, agreements, subordinations, storylines already true on the start date). **Run in the Workshop, not by the game:** the scenario designer clicks **Generate pre-history** in the Pre-history tab (`PrehistoryPanel.jsx` → `generateScenarioPrehistory`), with an optional prompt of their own that rides at the end of the user message; the result is edited there and saved with the scenario as `world.prehistory` (`runtime/scenarioPrehistory.js`). A new game inherits it and `maybeGeneratePregameHistory` applies it on the first open with **no request**. The task still runs at the first open only for a game whose scenario has no `prehistory` record at all (made before scenarios kept one) and a "World Before Round One" briefing; an empty record is the designer's choice of no backstory and asks nothing. Either way it runs once (the `simulationHistory` entry, `source` `"scenario"` or `"ai"`, doubles as the done-marker); events carry **no impacts** (world already reflects them); clock stays at start, round stays 1.
- **Against a scenario:** `generateScenarioPrehistory` runs the same task and validator against the scenario rather than the active game — its world and start date, its prompt pack (`runJsonTask({ promptPack })`, `buildTemplateVariables({ taskKey, promptPack })`, so only what the template reads is built), and its own map: `mapSource` (`{ regionCatalog, regionsGeojson, citiesGeojson, nationTags }`, the catalog from `assets.js buildRegionCatalogForMap` over the scenario's regions file) threaded into `buildPromptContext`, `buildWorldSummary`, the lookups (`buildTaskLookups`), the groups context and the polity vocabulary. The active game's own catalog is never primed or replaced.
- **Prompt:** `tasks.pregameHistory`. **Entry:** `requestPregameHistoryPayload` `gameplay.js`, from `generateScenarioPrehistory` (Workshop) and `maybeGeneratePregameHistory` (a legacy scenario's first open).
- **Tool/schema:** `submit_pregame_history` / `PREGAME_HISTORY_SCHEMA`: `{ events[1..12] { date,title,description,importance,kind }, summary }` — note the impact-free `pregameEventSchema`.
- **Validation:** `validatePregameEvents` (`timelineDates.js`, tested in `timelineDates.test.js`) — strict/salvage: all dates before start, chronological; non-Gregorian scenarios skip date checks. No fallback (silent null on failure).

### 7.11 `gameMaster` — direct map/state cheat
- **Purpose:** Apply an explicit player/GM request to the map/world; never argue or refuse.
- **Prompt:** `tasks.gameMaster`. **Entry:** `previewGameMasterCommand(requestText, { mode })` `gameplay.js` (passes `gameMasterRequest`); the console then applies that exact preview with `applyGameMasterPreview(preview)`. There is no direct execution path.
- **Tool/schema:** `submit_game_master` / `GAME_MASTER_SCHEMA`: `{ summary, impacts { regionTransfers, polityChanges, markerOps } }`.
- **Validation:** `validateGeneratedWorldChanges` (strict on attempt 1). **Fallback:** empty impacts + neutral summary. Wrapped as a "Game master intervention" event.
- **The request's own checks, in any language.** Besides its JSON array texts the transport (`GAME_MASTER_TRANSPORT_SCHEMA`) requires three fields the model fills from the administrator's request: `requestedSubordination` (it asks for a puppet, satellite, protectorate or client; false for a release), `requestedDate` (the one exact date it names, YYYY-MM-DD, BC negative, or empty) and `requestedOngoingProcess` (it describes an unresolved multi-turn process). The preview then requires a `puppetUpdates` install (`gameMasterRequestAsksForPuppet`, `gameMasterRequestCompleteness.js`), an exact-event date equal to the requested one, and a storyline for a world intervention, exactly as before. The English patterns (`requestExplicitlyInstallsPuppet`, `extractExplicitGameMasterRequestDates`, `GAME_MASTER_PERSISTENT_PROCESS_HINT`) decide only for an answer without the fields; the decoded transaction carries them only when the answer did, and `GAME_MASTER_SCHEMA` leaves them optional so an older saved preview still validates. No request is added.

### 7.12 `countryStatSheet` — structured national stats
- **Purpose:** Compile a full stat sheet for a selected polity for the Stats tab.
- **Prompt:** `tasks.countryStatSheet`. **Entry:** `generateCountryStatSheet({code, name})` `gameplay.js` (userMessage carries a `buildTargetDossier` + era slice). The dossier has one implementation, `buildTargetDossierKernel` (`countryStatsWorkerKernel.js`), which the worker and `gameplay.js` both call; it counts the target's regions over the whole map by effective owner (the override, else the catalog row's base owner, `regionOwnerName`), says how many it holds and how many it is the lawful sovereign of, names what it holds beyond its starting territory in the scenario and counts what of that territory others hold.
- **Tool/schema:** `submit_country_stat_sheet` / `COUNTRY_STAT_SHEET_SCHEMA`: `capital, continent, government, leader, stability(0–100), indices{sovereignty,foodAutonomy,energyAutonomy,economicIndependence,internalSecurity,internationalReputation}, economy{gdp,gdpGrowth,gdpPerCapita,currency,inflation,unemployment,publicDebt,budgetBalance}, gdpBreakdown{agriculture,industry,services}`.
- **Validation:** all strings non-blank; all indices 0–100 integers; `agriculture+industry+services === 100` (`gameplaySchemas.js`). No fallback.
- **A scenario's own sheet:** `loadStatSheetDefinition` (`src/runtime/statsSheet.js`) reads the scenario's `stats.json` once per library generation (scenario, its cache token and the library token) and never keeps a failed read. When a scenario that has one cannot be read, this task, a time skip and the Game Master fail before any request is sent, and a turn's tracked-stats refresh is skipped and logged; none of them falls back to the standard sheet, which would write the wrong statistics.

### 7.12a `timelineCurator` — the native timeline curator

- **Prompt:** `tasks.timelineCurator` (uses `${curatorPriorHistory}` and `${curatorCandidates}`, passed directly) plus the `[Strict Curator Calibration]` directive appended at call time. **Entry:** `curateGeneratedEvents` in `src/Game/AI/nativeTimelineCurator.js`, called from `applySimulationResult` after the content de-dup and before canonical ids, impacts and persistence.
- **Purpose:** the model classifies every fresh candidate (KEEP / REDUNDANT / UNSUPPORTED_REVERSAL with confidence, matched prior indexes, storyline, worthwhile/substantive/process flags). Native gates decide what may be removed: an event with hard consequences (territory, claims, units, features, chats, a polity rename or recolor, a war-ledger binding) is always kept; an exact same-date restatement of a prior event is always dropped; a REDUNDANT verdict removes an event only with high confidence, a retrieved prior match that is genuinely similar, no new dimension and no recurrence value; saturation and process-filler gates catch routine churn in a busy storyline. Ledger records bound only to a dropped event are dropped with it. Any failure of the analysis keeps everything.
- **Asked only when something could go.** Whether requests are being saved or not, the model is asked only when `candidatesWorthJudging` finds a candidate it could remove; a skip whose events all carry a transfer, a unit op or a war (or resemble nothing on record) makes no curator request, and neither does the breadth repair's curator pass.

### 7.12b `unitDirector` — the native unit director

- **Prompt:** `tasks.unitDirector` (uses `${unitDirectorGameDate}`, `${unitDirectorRound}`, `${unitDirectorUnits}`, `${unitDirectorCandidates}`, all passed directly by the caller) plus the `[Native Unit Director — runtime rules]` directive appended at call time. **Entry:** `directGeneratedUnitOps` in `src/Game/AI/nativeUnitDirector.js`, called from `finishTimelineJump` after the segments are merged.
- **Purpose:** the jump writes history; this pass keeps the persistent order of battle coherent with it. Only events whose text describes an operational change (advance, redeploy, clash, mobilize, siege…) are offered, with the current units: each with its type, owner, strength, status, posture, composition, cover and any standing order (`world.pendingUnitOrders`: kind, target, `untilRound`), at most 60 (`UNIT_DIRECTOR_UNIT_LIMIT`), the units the events name (their owner or the formation itself, exact names) or already touch first, and a line counting the rest. The model answers `eventOrders` (unit ops per event index). Native rules keep only plausible ops: reuse before spawn (spawn budget, explicit new-formation cue), a move needs only a valid destination (the director accepts it at any distance, because dropping a far objective strands the counter), strength only where the event narrates casualties/attrition/reinforcement, remove only for destruction/disbandment, no duplicates. Accepted ops are attached to the event and applied exactly like the simulator's own unitOps. **Distance is the engine's limit, not the director's:** a unit moves at most `kmPerDay(type, gameDate)` (`runtime/unitMotion.js`, by unit type and era) times the days that passed, and the rest of the way stays in `world.pendingUnitOrders` as a standing order that `advanceStandingOrders` (`runtime/gameState.js`) walks on later turns. There is no attack op on this build; a failed or unavailable director leaves the events unchanged. **Region types:** when the scenario's `world.regionTypes` has a type that is impassable, slower or faster to cross, or out of play (map-editor.md §8), the unit and structure directors' prompts get a `[Region types]` block (`${regionTypeRules}`, `regionTypeRulesFor` in `gameplay.js`, `regionTypeRules` in `runtime/regionTypes.js`): one line per type, naming up to 12 of its regions from the compact region catalog. It adds no request, and a map without such types adds no text.

- **A power with no counter.** Each candidate carries `combatantsWithoutUnits`: the event's combatants that own no unit at all (`nativeUnitDirector.js`). The instruction and the prompt's rule 5 tell the director to spawn one formation for such a power where the event puts its forces, even though the event does not say the formation is new, so a war between powers the map gave no counters (Russia and Ukraine in a Modern Day game, 2026-09-30) is not a war nobody can see. Its later events then move and weaken that same unit. The combatants are the event's own and both sides of the war it is bound to (`warId`). A model can ignore the rule (a live check, 2026-10-02: told Russia had no unit, the review moved another unit instead), so the engine makes sure of it: a power the answer leaves without a spawn gets one formation from `raiseMissingCombatants` (`gameplay.js`; `missingCombatantSpawns` / `pickCombatantPlace` in `nativeUnitDirector.js`), at the first place it holds in the events naming it, else in the part of its own land nearest the first place they name, else in its own land, one per power and at most two per skip (the wars' leading powers first), placed and kept by the same rules as the director's own spawns. Such a formation carries `raisedForWar` and is disbanded when that war ends (a ceasefire keeps it), and every unit of a power that held land when a turn began and holds none at its end leaves the map with its standing orders (`pruneWarUnits`, run in `applySimulationResult` after the turn's wars and borders). A power that never held land keeps its units.

### 7.12c The native world director, storylines and `worldMotionRepair`

- **Not a prompt-pack task.** `nativeWorldDirector.js` + `nativeWorldIntegrity.js` (ported from kernely's Continuum branch) run deterministic CPU analysis before every jump segment, in a module worker (`worldDirectorWorker.js`, main-thread fallback): which persistent storylines get focused attention this segment and which are deferred, a rotating exploration slate of at most 10 lanes (`buildNativeWorldExplorationSlate`, `nativeWorldIntegrity.js`): 5 player-sphere lanes (actor lanes, with regional-system fillers when there are fewer than 5 player-sphere actors) and 5 wider-world lanes (3 actor lanes, 1 evidence and 2 latent, plus the protected crisis-discovery lane and a cross-border global lane; wider-world fillers when there are fewer than 3 wider-world actors), the era's conflict-risk posture, economic and diplomatic attention, and the storyline record contract. The text becomes `${worldInitiativeContext}` (appended as the `[Native World Director — authoritative live causal context]` directive); the analysis drives validation.
- **Storylines.** `world.storylines` (world-state.md §2b-bis) is the hidden state of the world's ongoing processes. A jump payload carries them as compact `storylineUpdates` lines (`id~status~pressure~momentum~startedDate~kind~title~participantsCSV~eventNumbersCSV~state`). Per segment, after the ledgers: the director's binders attach records to their events (`storylineIds` on events), quiet echoes of deferred processes are stripped, serious visible history must bite into a canonical owner (`validateWorldEventConsequencePayload`; a major event whose only consequence is an open Board entry, found by the engine's own matcher `boardEntriesConcernedByEvent`, passes provisionally and must be backed by the board pass, §7.17, while an unresolved crisis still needs a storyline), the records are checked (`validateWorldStorylinePayload`; among its rules, a crisis-level storyline — pressure ≥ 55, or a war — may not lower its pressure while its bound events carry only escalation/failure cues, a keyword test that is not applied to quiet programmes because ordinary words like "deploys" trip it) and the exploration audit is validated. Every accepted segment then passes the integrity screen (`screenGeneratedWorldEvents`, in this order: player-agency provenance first — an event whose own `agency` record makes a fresh sovereign choice for the player's polity without a player order or commitment behind it, or is malformed, is dropped as `PLAYER_AGENCY_AUTHORITY`; then a non-belligerent's wartime economy; routine no-delta military or administrative process cards, which are kept off the timeline as Hidden events; and the low-trajectory feed guard) before the next segment or the curator sees it; a record bound only to a dropped event goes with it. The player-agency check rebuilds each event's decision owner natively (the jump never writes `event.agency`) and marks an event in which the player's own country is shown making a fresh sovereign choice (its title opens with the country, or it is a party to a joint commitment: the parties of an `agreementUpdates` start record bound to the event are taken as its actors, since the jump never writes `event.actors`) that neither a queued order nor a player-authored chat message authorizes; the screen is given the turn's orders and chats for that. For now the mark is logged only (`player-agency verdicts` in the console, `wouldWithhold: true`; the result's `playerVerdicts`) and the event is kept: the title reading still takes "Poland Comes Under Attack as Russia Declares War" for Poland's own choice, so enforcing it would erase the world acting on the player. An event that cites a queued order in `impacts.actionIds` is never marked, and one that merely names the player's country is logged with its own verdict. `applyWorldStorylineUpdates` writes the ledger once per turn, after wars and diplomacy.
- **`worldMotionRepair`** (tool `submit_world_motion_repair`, `WORLD_MOTION_REPAIR_SCHEMA`): **once per skip, never per segment** (`repairSkipStorylineMotion`, after the last segment is in hand). Every storyline any segment selected (`mergeSkipAttentionStorylines`) is judged once over the whole skip (`findSkipStorylineMotionIssues`): where it stood before the skip against the last update it received in any segment, with its event links rebuilt from the skip's events. One that never got an update, or is past its anti-stasis backstop and still objectively unchanged, gets one narrow repair call (`runTargetedWorldMotionRepair`: inline system prompt, no events or other ledgers, `callRepairAI`). Detection, prompt and validation all use the skip's merged stop date. A failed repair withdraws that storyline's skip updates (unless the storyline was born in the skip), so it stays overdue for the next turn; it never costs the turn. Past the backstop (`storylineAtAntiStasisBackstop`) the repair prompt states the validator's numeric rule — change status, or move pressure ≥`ANTI_STASIS_MIN_PRESSURE_DELTA` (4) or momentum ≥`ANTI_STASIS_MIN_MOMENTUM_DELTA` (6) — because a prose-only change is rejected there. The main pass and the validator's rejection state the same rule, plus linking a material event, for every storyline at the backstop, active wars below the high-pressure line included; all three read one sentence, `describeAntiStasisObjectiveRule`. **Limits** (`nativeWorldDirector.js`): a skip makes at most `MAX_MOTION_REPAIRS_PER_JUMP` (8) repair calls and spends at most `MAX_MOTION_REPAIR_MS_PER_JUMP` (10 min) on them — none starts once it is spent, and one still running when it runs out is stopped (`runBoundedRepairCall`, `repairCall.js`) and left overdue without a cooldown; a storyline whose repair failed is not retried for `MOTION_REPAIR_FAILURE_COOLDOWN_ROUNDS` (3) rounds unless it changes or the player rewinds past the failure (in-memory `motionRepairFailures`, keyed by campaign); a turn that fell back to canned events makes no repair calls. A skipped issue is handled exactly like a failed repair, and each skip logs one `[OH World Motion Repair]` summary line (attempted, repaired, failed, left overdue and why).
- **Breadth repair.** After curation, a jump of 21–40 days left with ≤3 worthwhile events, or a busy window whose rolling consequence signal is low, gets one bounded composition search (the low signal itself is also stated in the main skip's `[What Is in Motion]`, which costs nothing, since this repair is skipped while requests are saved) of the exploration lanes still quiet after curation (`runWorldBreadthRepair`, reusing the jump tool, ≤5 events, no ledger mutation, new storylines only); its candidates pass the same integrity screen and the same curator.
- **GM Console.** `storylineUpdates` (transport `storylineUpdatesJson`) create, advance or resolve storylines in a previewed transaction; `${canonicalStorylineContext}` shows the current ones. **Pregame.** `storyline:active | storyline:dormant` canonicalUpdates persist unresolved non-war Day-1 processes; every live Round-One war is mirrored into `storyline-<warId>` mechanically (`ensurePregameWarStorylineMirrors`).

### 7.12d `territoryDirector` — the native territory director

- **Prompt:** `tasks.territoryDirector` (uses `${territorialControlContext}`, `${territoryDirectorState}`, `${territoryDirectorCandidates}`). **Entry:** `directGeneratedTerritoryOps` (`nativeTerritoryDirector.js`) in `finishTimelineJump`, after the unit director. **Tool/schema:** `submit_territory_director` / `TERRITORY_DIRECTOR_SCHEMA` (`eventOrders[{eventIndex, regionControlOps[], reason}]`).
- **What it is shown of the map:** `summarizeTerritorialState` (`nativeTerritoryDirector.js`) — the two sparse stores (`regionSovereigntyOverrides`, `regionClaimants`) and, of `regionOwnershipOverrides`, only the rows for the regions those two name: the occupied and disputed regions, capped at 400 with the front the candidate events are about kept first and anything left out counted. It used to be all three stores whole, pretty-printed. On a hand-drawn world every region carries an ownership override, so on the built-in scenario that was 4,848 rows of a numeric id and an owner — no region name, nothing to reason from — and a request of **215,323 characters, now 23,550**. It is also handed `placesTheseEventsName`: every region and city the candidate events name, each with who controls it now, who lawfully owns it where that differs, and who claims it (`placesNamedIn`, `lookupTools.js`) — because the controller is what the director writes into `fromCode`. For one day this was left to a lookup ("ask `find_region`"), which saved characters and cost a request: the wrong way round on a free key, where every lookup round re-sends the whole prompt ([the request budget](ai-overview.md#the-request-budget)). The template now says to take `fromCode` from that list, and the state never tells the model to go and ask for anything (pinned by `nativeTerritoryDirector.state.test.js`).
- **Asked only about events it could change.** An event is a candidate only when it is territorial *and* carries the wording one of the director's ops needs in order to be kept: a capture that is not negated (for `control`), a fight or dispute (for `contest`), or a ceasefire, withdrawal or peace (for `clear_contest`). A treaty that cedes a province, or a speech about sovereignty, is already described by its own `regionTransfers`; asking about it could only come back with ops the rules drop, so it is not asked (`isTerritoryCandidate`, pinned by `nativeTerritoryDirector.rules.test.js`).
- **Asked as a job, not a request, while requests are being saved.** `buildTerritoryDirectorInput` returns exactly what the director's analyzer would be sent, or `null` when no event is territorial, so [the turn review](ai-overview.md#the-turn-review-every-check-after-a-skip-in-one-request) can carry it in its one request; the director then runs unchanged with that part of the answer in place of a call of its own. The unit director (`buildUnitDirectorInput`), the curator (`buildCuratorInput`) and the board follow the same pattern.
- **Purpose:** the jump writes history; this pass turns the surviving front state into de-facto `regionControlOps` (contest / control / clear_contest) without inventing legal transfers. Legacy wartime `regionTransfers` on capture-worded events are converted to control ops first; deterministic rules sanitize the proposals (a control flip needs explicit capture wording and different sides, a contest needs fighting wording, clearAll needs a final settlement, duplicates dropped); accepted ops are resolved through the geography resolver bounded by current control. `window.__OH_NATIVE_TERRITORY_DIRECTOR__.last` shows the last pass.

### 7.12e `geographyResolver` — the bounded semantic geography pass

- **Prompt:** `tasks.geographyResolver` (uses `${geographyResolverItems}`). **Entry:** inside `resolveRegionTransfers` (`gameplay.js`), for transfers and control ops whose place wording exact matching could not resolve. **Tool/schema:** `submit_geography_resolution` / `GEOGRAPHY_RESOLVER_SCHEMA`.
- **Purpose:** map a city, fortress, exonym or historical area onto the losing side's real regions (its `candidateRegions`) or answer UNRESOLVED; never decides who should own anything. The resolver first tries the rendered scenario geometry (city points inside region polygons, aliases, the losing side's own regions) and accepts a semantic answer only above a confidence threshold with every id inside the bounded candidate set; conflicting recipients for one region fail safe. Narrated city coverage: an event that says control changed in a named city must carry an operation for that city's rendered region.

### 7.13 `idleDiplomacy` — unprompted note drip
- **Purpose:** Between jumps, on each real-minute tick, a small chance a single polity sends the player a short note; usually the answer is silence (`chat: null`).
- **Prompt:** `tasks.idleDiplomacy` (uses lowercase `${playerPolity}`, `${dateReadable}`, `${worldSummary}`, `${recentEvents}`, `${chatSummary}`). **Entry:** `maybeSendIdleDiplomacy()` in `gameplay.js`, rolled once a visible minute by `GameUI/main.jsx`. It is **background AI**: it does nothing while the player has Background AI turned off (Settings → AI → AI requests; on by default) or has reached that day's cap, and its calls are counted as background ([the request budget](ai-overview.md#the-request-budget)). Its one cadence is the game's Idle diplomacy feature — one attempt every N minutes, 8 by default, zero when the feature is off — and the same request also asks whether any forces would visibly move. It used to run at least one roll in four regardless of the feature, so that the map "breathed"; that floor is gone. It rolls only while the player has touched the game (pointer, key, wheel or touch) in the last ten minutes (`runtime/playerActivity.js`), so a window left open while they are away spends nothing. A pulse that answered with nothing makes the next one on the same world half as likely, and each further empty answer halves it again, to at most a thirty-second (`createIdlePulseBackoff`, `idlePulse.js`); a turn, a moved unit, a new event or a new message in an open chat (`idlePulseFingerprint`), or any answer with something in it, restores the full chance. Suspended by the simulation busy-lock, and a pulse that outlives a switch to another save writes nothing: no movement, sighting or note.
- **Tool/schema:** `submit_idle_diplomacy` / `IDLE_DIPLOMACY_SCHEMA`: `{ chat: null | createdChat }`. No editor section; no canned fallback (silent). A note from a country the player already 1:1s with lands in that thread.

### 7.17 `projects` — the Projects & Operations board

- **Purpose:** move the board to match the events a jump has just produced. Bookkeeping, not authorship: it records what the story did to each running effort.
- **Prompt:** `tasks.projects`. **Entry:** `generateProjectOps`, run by `simulateTimelineJump` after the segments merge and before anything is written.
- **Inputs:** the board (`${projectsSummary}`) and **every Canonical event** of the jump, numbered, in the user message: the visible (timeline) events first, then the Hidden events, meaning those the integrity screen's routine/low-value rules and the curator's redundancy/filler/churn routes kept off the timeline, each marked "(kept off the timeline)". Routine progress is exactly what moves a standing Operation, so the board must not depend on what the timeline chose to show (world-state.md §2e-bis). Events rejected as untrue (non-belligerent wartime causality, an unsupported reversal) and exact duplicates are never included. Deliberately nothing else — no world summary, no city coordinates, no unit list, no chat history. ~20 KB against the jump's ~500 KB, plus the Hidden events.
- **Tool/schema:** `submit_project_ops` / `PROJECTS_SCHEMA`: `{ projectOps[] }`, each carrying `eventIndex`. `boardPassCarriers` (`runtime/projects.js`) groups the ops by the event that caused them and orders those groups by date across the visible and Hidden lists, so an entry a Hidden event opens exists before a later event moves it. Each group is applied in turn through the event path (`applyEventImpactsToWorld`), so completion effects release exactly as they would from a timeline card (`applyBoardCarriers`, `AI/boardPassApply.js`); a completion that renames or recolours a polity is carried into the game's own polity, the queued orders, the chats, the flags and the baked regions, as an event's rename is. Ops on a visible event are also recorded on it, as before. A Hidden event's are applied without being stamped into the entry's activity (`boardOnlyEventIds`). An op with no usable `eventIndex` still rides on the last visible event, but in a group of its own.
- **Provisional major events.** A strategically major event whose only consequence is a Board entry passes the world director's consequence check provisionally (§7.12c). The turn judges it on the Board itself, before and after that event's own ops (`materiallyChangedEntryIds`): an entry opened, a status or progress change, or a checkpoint reached or missed. A `lastUpdate` alone and a restated figure do not count, and neither does an op with no usable `eventIndex`. An unbacked event leaves the timeline before the write, and its ops are applied without stamping it. An event that gained a consequence of its own after the segment check (unit or control ops from the directors, spy orders, resolved player orders) stands on that instead. The `[OH board]` console line reports how many Hidden events were read and how many of them moved how many Board entries, the provisional events and how many were unbacked, and any HIGH PRIORITY entry the pass left unassessed.
- **No fallback.** An empty board is what a failed call should leave behind, and `runJsonTask` throwing is what lets the caller hold the turn and offer a retry rather than pretending the board moved. The segments' Hidden events ride in the held turn's `result`, so a Retry reads the same ones. The curator's and the breadth repair's answers are replayed from the first attempt (`heldTurnReplay.js`), so a Retry keeps the same timeline and the same Hidden events and sends only the board call again. The curator's answer is kept with the turn's checks as well (`turnChecks.js`), so a Retry gives the same candidates the same verdicts. The board's own answer is replayed too once it has one (a failure is not kept, so a Retry asks again), which is what lets a skip kept for another campaign be written later without a board request.

Its rules live in the template, with one exception injected at call time: `buildBoardPassDirective` (`projectsDirective.js`) restates the HIGH PRIORITY rule, which means an explicit assessment every jump where "no material change this period, because…" is valid, never forced movement. It says it supersedes the old wording, a leftover of the frozen-prompt era (§2). The game master's inline board block and the jump's board directive share the same sentence (`HIGH_PRIORITY_ASSESSMENT_RULE`).

### 7.18 `[Social Media]` — Rostra in the time skip
- **No task of its own.** Rostra, the social network ([game-ui.md §10-ter](game-ui.md)), asks for nothing: its posts ride in the time skip's one answer (`socialPosts`, [ai-schemas.md §4.7](ai-schemas.md)), and its feed goes back into the skip's live records as `[Social Media]` (`socialFeedPromptBlock`, `runtime/socialFeed.js`), beside what the chats said. It took the place of Listen in, which was a request of its own for each feed. Search, its tab for a country or a region, brings Listen in back as the `placeFeed` task (below).
- **What the skip is told.** The posts that matter, most important first and listed oldest first: the player's posts of the last two rounds (marked as the player's, and as new since the last time skip), the posts that quote them, the newest from high office, then the newest of everyone else; at most 24 posts and 4,800 characters, each post's words cut at 280. Each is a public statement by the person who wrote it that can move events as a speech would, and the player's posts are their leader's own public words, to be carried like an order's consequences.
- **What it is asked for.** About 6 to 12 posts a month: the people who make the news on the period's events, in their own voices; answers that quote the player's new posts (by id); other quotes where someone would; and, every other skip (`wantsEverydayPost`: when none came with the last one), exactly one post about nothing in world affairs (`offTopic`). Each post: a person's full name, a role, the exact map name of their polity or nothing, a date in the period, at most 280 characters, and the id of a post it quotes or `#n` for an earlier post of its own list.
- **Whose voice.** The block says, in words, that no post is written as the leader of a polity a person plays, or as anyone who speaks for its government: those are the player's. Their opposition, press and people may post. No filter checks it (the owner's rule: prompts, not guards).
- **Polls.** A player's open poll is always listed (with its choices), and the block then asks for `pollResults`: per poll its id, the share each choice won among the public of the leader's country (whole percentages, in order, adding to 100), the votes and one sentence of consensus, decided from what that public thinks in this world and never from what the leader would like; the result is public opinion the events and posts are to show. A poll with results is listed with them. The field is in the tool only while a poll is open (`withSocialPosts(tool, on, { polls })`, from the `rostraOpenPolls` variable `promptContext.js` sets).
- **Off** (the **Social media** feature): no block and no field, so the skip spends nothing on it.
- **`rostraFeed`, the empty feed's Refresh.** The one other request Rostra makes, and only when the player presses **Refresh** on an empty **For you** feed ([game-ui.md §10-ter](game-ui.md)): the people who make the news write the first posts (`rostraRefreshRules`, `${rostraFeedRules}`: 8 to 12 posts dated up to the game's date, quotes as `"#n"` for an earlier post of the list, exactly one post about nothing in world affairs, never the leader of a polity a person plays), in the game's language (`${rostraFeedLanguage}`), over the simulation rules, the world before round one, the wars and the history. Its answer is the skip's post shape (`ROSTRA_FEED_SCHEMA`, tool `submit_rostra_posts`) and is read as a skip's posts are; one usable post is enough, none fails the request. No difficulty block, no lookup functions.
- **`placeFeed`, Search's one request.** Listen in's prompt as it was (ordinary people's posts, a quarter of them about nothing, only what the public knows, newest first, trends), renamed (`${placeFeedPlace}`, `${placeFeedPlaceDetails}`, `${placeFeedLanguage}`) and with an `[On Rostra]` section: the country's newest posts on Rostra and its leader's polls with their results (`placeRostraLines`, `${placeFeedRostra}`), so the people there talk about what is being said where they live. Its one editable passage is Listen in's `[Who Is Posting]`, with the translations it had. No lookup functions: the place's facts are in the prompt (`placeFeedContext.js`).

### 7.14 Root prompt: `leader` — AI diplomacy
- **Purpose:** Roleplay a single non-player polity replying in an ongoing chat; keep the existing hard rule to **match the player's average message length**, lightly match formality, and simulate a polity leaving. Decision posture comes from canon/current political state rather than from whether the proposal came from the player.
- **Prompt:** top-level `leader` string. **Assembly:** `buildDiplomaticSystemPrompt(countries, playerCountry)` (`main.jsx`; the diplomacy difficulty directive in the template) then `sendDiplomaticMessage(playerMessage, speakingAs, countries)` adds the per-turn instruction + optional `REACTION:<emoji>`. Free-form text (no tool/schema). `${RESPONDING_POLITY_NAME}` selects the voiced polity.
- **CP3C diplomacy prose contract:** the shipped guidance no longer forces first-person-only speech, automatic threats/consequences on refusal, or celebratory/grateful language on acceptance. A leader may use first-person or natural state/institutional references, while the per-turn instruction still forbids a redundant country-name prefix; the group-chat structured-action path also strips only an exact redundant speaker label at its native boundary. The cleanup changes writing guidance only: it does not alter Political World projection, CP3A/CP3B authority/selection, difficulty, player agency, durable diplomatic memory, or canonical state semantics.

- **Durable memory:** every reply also carries a hidden `DIPLOMATIC_MEMORY:<summary>` line — the thread's COMPLETE durable memory, modal force and attribution preserved (`buildDiplomaticTurnInstruction`, `runtime/diplomaticEnvelope.js`). `parseDiplomaticEnvelope` strips it and the chat stores it on the message as `memorySummary`; the newest one is fed back as a system-side context entry ahead of the dated, attributed transcript tail (`loadDiplomaticHistory`), and `diplomaticContinuity` (§5.1) shows it to the jump.
### 7.15 Root prompt: `advisor` — chief advisor chat
- **Purpose:** In-character strategic advice, ≤3000 chars, may append a `chart`-fenced Chart.js block. **Assembly:** `buildAdvisorSystemPrompt` (`main.jsx`) + `sendMessage` with rolling `advisorHistory`; language directive only (no difficulty, no schema); `[Our Country's Figures]` among its directives (§3b).
- **What it sees of the armies:** `${ALL_FORCES_POSTURE}` → `forcePosture` (`buildForcePostureText`, `forcePosture.js`): every power's formations, whose territory each stands in, how far it is from whose border and what it is under orders to do. It replaced `PLAYER_POLITY_BATTALION_SUMMARIES`, whose unit list arrived under the player's heading and was read as the player's own army.

### 7.16 Not in the prompt pack: `generateCountryStats` — intel briefing
- **Purpose:** Free-text bulleted intelligence briefing on a polity. Builds its **own inline system prompt** (dossier + world snapshot + recent events) and calls `callAI` **directly** (no tool, no `runJsonTask`, so only the language directive is appended). Entry: `generateCountryStats({code, name})` `gameplay.js`; its template variables are only the ones it reads (`requiredKeys`), and the call is under "Limit AI generation" (`callAIWithTaskLimit`). Distinct from `countryStatSheet` (§7.12). Task key `countryBriefing`: its own usage row and Per-task models row ("Advisor Report"), starting on the `countryStatSheet` pick until it has one of its own, and no deliberate temperature. The map's country panel asks for it with its **Advisor Report** button, one request per campaign and country at a time (`Selection/reportRequests.js`): reopening a country while its report is being written joins that request, and a report that comes back while the panel shows another country is kept and shown when its own country is opened again, never on the other one. Each answer is kept for the session under the campaign, polity, round, date and language (`briefingCacheKey`, `runtime/countryInfoPanel.js`): reopening the panel in the same round shows it again without a request, and the button then reads **Regenerate Report**, so a second request is the player's choice. The kept briefings are dropped on a campaign switch and on Android memory pressure.

**The target dossier** (`buildTargetDossier`, `gameplay.js`) is the target-specific evidence this briefing, the spy reports, the intelligence assessment, the motion repair and the stat sheets are given. Its polity, territory and forces lines are the Stats worker's (`buildTargetDossierKernel`, `countryStatsWorkerKernel.js`), one implementation for both paths; the ledgers' lines follow (`buildTargetLedgerLines`, `targetDossier.js`): the target's active and ceasefire wars, its relation and agreements with the player, who directs it and whom it directs (only what the player can see: a covert arrangement once their intelligence has found it), the groups holding its regions, its reputation, its rated service, and its stat sheet with an instruction to quote it. The tasks that write the sheet themselves (the stat sheets; the intelligence assessment, which adds it separately) are not shown the old sheet in the dossier.

### 7.19 `warRoom` — the player's generals

- **Purpose:** The talk in the war room ([game-ui.md §10-quater](game-ui.md)). The model speaks for every general of the player's side on ONE battlefield; a general is the commander of a body of its troops (`runtime/fronts/command.js`).
- **One request a message.** `generateWarRoomReply` calls `runJsonTask("warRoom")` once, with **no lookup functions**: the battlefield, its cities and what has been said are worked out in `warRoomContext.js` and handed over in the prompt. It writes nothing. The panel then writes one op (`talk`) through `runtime/warRoomWrites.js`.
- **Template** (`defaultPrompts.json` → `tasks.warRoom`): `[The Generals]` (one line an army: its title, its general's name, formations, strength, where, what it is at, what it has been told and not yet done), `[How They Speak]` (the one editable guidance passage, `voices`), `[Orders]`, `[The Battlefield]` (the engine's own brief with the other side's standing orders left out, the battlefield's cities with who holds each, and what the player's agents and Board have of the other side's planned movements), `[What Has Been Said]`, `[The Answer]`, `[The World]`.
- **Who is who.** A general is always named by his ARMY ("1st Army"), in the prompt and in the answer; his name is the model's to give the first time (`generals`), and is kept on the battlefield from then on. Nothing the model reads or writes carries an id.
- **Pushing back.** Every line carries a `stance`: `accepts`, `objects` or `speaks`. A general who objects has taken no order: the prompt says so, and `readWarRoomAnswer` drops any order written for his army in the same answer. He objects once: when the commander repeats the order, he obeys.
- **Orders.** `{ command, order, objective }`, `order` one of `WAR_ROOM_ORDERS` (advance, blitz, spearhead, flank, encircle, hold, dig in, fall back). An objective must be a city of the battlefield as the prompt lists it; one that is not is left off (nothing is put in its stead), and a thrust left with no place is an advance. An order is written onto the battlefield for the troops under that general and is carried out when time next passes.
- **Language.** `${warRoomLanguage}` is the interface language once the player has chosen one, else the save's (`readingLanguageName`), since `callAI` appends its language directive only for a non-English interface.
- **Measured live** (gemini-3.5-flash-lite, the built-in map, Russia against Ukraine): one request a message, about 2,500 tokens in and 70 to 250 out, five to eight seconds. Two faults were found and are guarded against: a name given as an example in the schema came back as a general's name (the schema gives none now), and an order was recorded for a general who was still arguing (hence `stance`).

## 9. Recipes

### Add a new template variable
1. **Compute it** in `buildPromptContext`'s return object (`promptContext.js`) — e.g. `myThing: buildMyThing(bundle.world)`. Add a builder next to the others if non-trivial. (If it needs reputation/feasibility-style augmentation only for tasks, add it in `buildTemplateVariables` `gameplay.js` instead — but remember advisor/leader won't see those.)
2. **Expose a placeholder** in `defaultPrompts.json` `helpers`: `"MY_THING": "${myThing}"`.
3. **Reference it** in the task/root text as `${MY_THING}` (or the lowercase `${myThing}` directly).
4. **Editor:** nothing — helpers are technical and never shown. If the sentence that uses the variable is guidance an author should be able to reword, keep it inside a segment declared in `promptGuidance.js` (or declare one, with unique `start`/`end` anchors) and keep the placeholder inside the passage.
5. Nothing else — `renderTemplate` picks up any key present in the merged `{...variables,...helperValues}` map.

### Add a new task
1. **Schema + tool:** define `MY_TASK_SCHEMA` and `MY_TASK_TOOL = makeTool("submit_my_task", …)` in `gameplaySchemas.js`; register both in `GAMEPLAY_SCHEMAS` and `GAMEPLAY_TOOLS` under the new key; add any task-specific checks to `validateGameplayPayload`.
2. **Prompt text:** add `tasks.myTask` to `defaultPrompts.json` ending with the JSON output contract. It is auto-picked-up: `PROMPT_TASK_KEYS = Object.keys(tasks)` and `normalizePromptPack` iterate it (`gameplayPrompts.js`).
3. **Entry point:** in `gameplay.js`, build variables (`buildTemplateVariables(bundle, {…})`) and call `runJsonTask("myTask", { userMessage, variables, fallback?, validatePayload?, timeoutMs? })`. Wrap state-writing tasks in `beginSimulation/endSimulation`.
4. **Call-time directives:** only for text that depends on runtime state; a rule in the template reaches every campaign (§2).
5. **(Optional) editor:** add a `PROMPT_SECTION_DEFINITIONS` entry (`type:"task"`) **and** at least one guidance segment in `promptGuidance.js`; a section without segments stays hidden, and only the segments are editable.

## 10. Gotchas

- **`worldSummary` and `worldSummaryNoCity` are the same string** — the "no city" name is historical; city coordinates are a separate `citiesSummary`/`${CITY_COORDINATES}`.
- **`worldSummary` embeds the briefing and the simulation rules**, so a prompt that also renders `${WORLD_BEFORE_ROUND_ONE_TEXT}` or `${HISTORICAL_PRESET_SIMULATION_RULES}` would send them twice. `collapseRepeatedWorldContext` (`promptDedupe.js`) keeps the first copy of each and swaps later copies for a pointer; `runJsonTask` applies it to every task and `main.jsx` to the advisor and leader prompts. Values under 400 characters are left alone. Don't strip them from the summary instead: `actions` and `idleDiplomacy` see the rules only there.
- **Two output attempts per task**, then a deterministic fallback (or throw). `finalAttempt` comes from `runJsonTask`, never from counting validator calls — attempt-1 schema failures skip `validatePayload` entirely (`gameplay.js` comment).
- **Reputation and military-feasibility reach only the task path** (`buildTemplateVariables`). Advisor/leader use `buildPromptContext` directly and never see them.
- **The intel `generateCountryStats` briefing is invisible to the Prompts editor** — it is an inline prompt not in `defaultPrompts.json`. (`idleDiplomacy` has had a section, with one guidance passage, since 2026-09-16.)
- **Editing `defaultPrompts.json` reaches every campaign** (the guidance model, §2) — but an edit that moves or rewrites a guidance passage must keep, or update, that passage's anchors in `promptGuidance.js`; `promptGuidance.test.js` fails otherwise, and a passage whose anchors are gone silently drops out of the editor.
- **Shortening a default passage shortens its limit.** An author's edit made against the longer default can then be over the new limit; it is left out and its author told (§2, the length limit). Run `node scripts/prompts/record-shipped-guidance.mjs` after changing a passage or a translation so `guidanceLengths.js` follows.
