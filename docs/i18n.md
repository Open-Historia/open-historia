# Languages & Translation

Open Historia is written in English and its interface is shown in 36 languages: English, the 22 with a shipped pack, and Danish, Hungarian, Romanian, Czech, Finnish, Latvian, Lithuanian, Slovak, Estonian, Greek, Hebrew, Irish and Maltese, which a translation model on the device covers (`getUiLanguageOptions()` in `i18n.js`). No translation is an AI request unless the player turns on **Translate with my AI** (below). Every string the game shows falls into one of three kinds, and each kind is translated differently:

| Kind | Examples | Translated by | Cost to the player |
|---|---|---|---|
| **Interface** | buttons, tabs, labels, hints, errors, the tutorial, stock country names, the names of the cities the map labels, the built-in scenarios' region names and cards | the **shipped language packs** (`public/lang/<code>.json`) | nothing |
| **A scenario's own text, where it ships a pack** | everything of the above that a scenario says itself, in the languages its author generated in the Workshop's **Languages** tab | the **scenario's language pack** (`scenario.languages`, [below](#a-scenarios-own-language-packs)), first, before everything else | nothing: no request, no model |
| **Content** | a scenario's and a saved game's name and description, polity names, roles and notes, the scenario's own events, a custom Stats sheet, the region names of a map that is not built in, country names a pack lacks, Community posts | a **translation model on the device** where the language has one (below); once, then saved to the server's language pack. A language with a pack and no model shows content in English | a one-time download of 110 to 150 MB, asked before it is made |
| **AI writing** | events, chats, the advisor, summaries written during play | nobody: the model writes them in the player's language (`languageDirective`), and the containers are marked `data-no-translate` (the timeline's AI events, the advisor's replies, the leaders' replies) so the interface translator never sends them back to the AI | nothing extra |

A reply written in a chat language other than the interface's (Settings → chat language) also takes that language's direction: `chatTextDirection()` in `i18n.js` gives `rtl` or `ltr` for the advisor's and the leaders' replies, so Arabic reads right to left under an English interface and English left to right under an Arabic one.

The default prompts' **guidance passages** (the role, the tone, what makes a good event: the parts an author edits in the Prompts tab) ship translated too (`public/lang/prompts/<code>.json`), so the model that runs the world reads its instructions in the player's language wherever the scenario has not written its own. The prompts' technical template (placeholders, output contracts, map rules) stays English, because the game parses what it asks for.

Related pages: [Runtime services](runtime-services.md) · [Prompt-Making Guide](ai-prompts.md) · [Server](server.md) · [Web build](web-build.md)

## Which languages have a pack

`SHIPPED_PACK_LANGUAGES` in `src/runtime/i18n.js` lists them: `ar bn de es fa fr hi id it ja ko nl pl pt ru sv th tr uk ur vi zh`. `src/runtime/languagePacks.test.js` fails if that list and the files in `public/lang/` disagree.

- **With a pack**, the interface comes from the pack. A string the pack lacks stays English and is recorded in `window.__ohI18n.missing` (a `Set`, capped at 3,000) for the next pack; `window.__ohI18n.pending` is what is queued for the model.
- **Without a pack**, a language is offered only where the model covers it (`da hu ro cs fi lv lt sk et el he ga mt`): the model translates the interface too, saved to the server's pack and reused on every device. `lv lt sk et ga mt` are not among the fifty most spoken, and `LANGUAGES` lists them after the fifty for that reason. The other languages of the fifty are offered only for what the AI writes (Settings → AI chat language); a device whose stored interface language is one of them starts in English (`canTranslateTo`).
- **Changing the language** (`switchLanguage` in `translator.js`, from Settings and the first-time setup) happens where the player is, with no reload: what the translator wrote over the page is put back to English (`restoreEnglish`) and the new language laid over it; Settings and its chat-language picker follow the `oh:ui-language-changed` event.

## A scenario's own language packs

The owner, 2026-11-06: "add a feature to ship high quality api generated language packs with scenarios". The model on the device translates names and flavour text poorly, so a scenario may carry its own text translated once, by its author's AI, and every player of it reads that instead.

**The record** (`server/scenarioLanguages.js`, shared by both stores, the editor, the suggestion diff and the hub reader): `scenario.languages = { <code>: { <English>: <translation> } }`, keyed by the English exactly as the shipped packs are, so a string is found the same way wherever it is rendered (`book.setAll`). A code is a language's (`de`, `fil`, `zh-Hant`; never `en`); values are strings; `__proto__`, `constructor` and `prototype` are never keys; at most 24 languages, 20,000 strings in one, 4,000 characters in a source and 8,000 in a translation, and 4 MiB in all (what goes past is cut from the end). The hub's checks hold the same limits (Open-historia-scenarios `scripts/lib/scenario-languages.mjs`). Because the key is the source text, a string the author rewrites is a new key: its old entry matches nothing and is dropped on the next generation, and the new one is missing.

**Where it travels**: a scenario detail like `music` (`readScenarioMeta`/`writeScenarioMeta` on both stores; `null` takes it away), on a save, an export (`scenario.languages` in the bundle, absent when there is none), an import, a clone and a hub Update (which takes the new version's packs or takes the old away), and a suggestion (one change per language, [game-ui.md §4.8](game-ui.md#48-suggested-changes)). **Never in a listing**: the library's catalog, its lean meta index on the web and the runtime scenario carry `languageCodes` only (`withoutScenarioLanguages`); the editor's details carry the packs, and a game asks for one language: `GET /api/scenarios/:id/languages/:code` → `{ code, strings }` (both stores).

**Making them** (the scenario editor's **Languages** tab, `ScenarioLanguagesPanel.jsx`; `src/runtime/scenarioLanguagePacks.js`; the request is `src/Game/AI/scenarioTranslation.js`):

- `collectScenarioStrings` gathers what the scenario itself shows, once each: its card (name, eyebrow, subtitles, description, as the form has them), its polities (name, aliases, map labels, role, note), groups, the Politics tab's institutions, actors, power and agreements, its own events (not the AI's) and its pre-history, a custom Stats sheet, then the names of its own map's cities and regions (a scenario on the stock map has none of its own).
- Skipped: what the language's pack already has, and what the game's **shipped** pack for that language has (a stock country, city or region: `public/lang/<code>.json`, never the server's learned entries).
- `planScenarioTranslation`: strings missing from the same languages travel together, so a first run asks for each string in all of them at once, up to 4 languages a request, in batches whose answer fits 20,000 characters (and at most 300 strings). A few hundred strings in six languages is two to four requests; the tab says how many before Generate is pressed.
- The prompt (`buildTranslationSystemPrompt`) asks for the names published histories in the language use for the scenario's period (exonyms such as Böhmen, Saint-Empire romain germanique), the original name kept or transliterated where the language has none, never a name translated word by word, one translation for one string and one rendering for one term, `{{slots}}`, placeholders, tags, numbers and dates kept, names kept short and prose its length. Each string carries its kind. The answer is the output function `submit_translations` (`{ translations: [{ id, lang, text }] }`, short ids per request), read as a stranger's (`readTranslationAnswer`: only what was asked, nothing empty, every `{{slot}}` of the source kept); what is missing stays missing for the next run.
- The task is `scenarioTranslation` in Settings > AI > Task routing, through `callAI` like every request (the Fallback list, the request count), with no difficulty and no language directive, temperature 0.2.
- Progress is kept as each request lands; Stop or a failure keeps what came before. Each language shows `{{done}} of {{total}} strings` or **Up to date**; **Edit strings** lists every string beside its translation (search, **Missing only**), and a translation typed by hand is never asked about again. Without an AI set up the tab says so. The packs are part of the form: **Save** writes them.

**In a game**: `useScenarioLanguagePack` (`GameUI/main.jsx`) fetches the pack of the open game's scenario for the interface language, when its `languageCodes` has it, and hands it to `setScenarioLanguagePack` in `translator.js`, which lays it over the book after the server's pack (and again after each start in a language), and takes its strings off the model's queue. So the scenario's strings come from it first, map labels included (`translateLabel`, `lookupLabel`); what it lacks falls back as before; English is untouched. A pack replaced by another scenario's leaves its entries in the book until the language is changed.

**The hub** lists a scenario's languages with its post (`scenario_languages` in the index, kept by `normalizeHubIndex`), and the Community tab says **Languages:** and their own names on the scenario's page.

## The files

| File | Holds | Made by |
|---|---|---|
| `public/lang/catalog-en.json` | every English interface string, sorted: exact strings and patterns; plus every stock country name, the preset scenarios' card text, the built-in scenarios' polity names and aliases (`server/seed/*/world.json`), the names of the cities the map labels: every city of the built-in scenarios (`server/seed/*/cities.geojson`) and, from `public/assets/cities-seed.json`, the stock capitals and the stock cities above 250,000 people; and the built-in scenarios' region names (`server/seed/*/regions.geojson`), which the translator finds in the pack before it would ask the AI | `scripts/i18n/build-catalog.mjs` |
| `public/lang/<code>.json` | `{ "<English>": "<translation>" }` for the catalog | translation (below) |
| `public/lang/prompts/catalog-en.json` | every guidance passage of the default prompts | `scripts/i18n/build-catalog.mjs` |
| `public/lang/prompts/<code>.json` | `{ "<English passage>": "<translated passage>" }` | translation (below) |
| `server/data/lang/<code>.json` (desktop) / IndexedDB `lang:<code>` (web) | translations the model made at runtime: content, and the whole interface in a language without a pack (older ones were the AI's) | the translator, via `PUT /api/lang/:code` |

`GET /api/lang/:code` (`server/server.js`, and `handleLang` in `src/runtime/web/settingsStore.js` for the web build) returns the saved pack **under** the shipped one: the shipped entry wins, because a saved entry for a string the pack now covers is an older AI translation. `PUT` does not save a string the shipped pack already has.

### Patterns

A string built around a value is a **pattern**: the value is a slot in double braces, named after the expression it came from.

```
"Found {{count}} regions"              → "{{count}} Regionen gefunden"
"{{name}} declared war on {{target}}"  → "{{target}} wurde von {{name}} der Krieg erklärt"
```

A translation keeps every slot and may move it. Plain interface text never contains `{{`, so a key with a slot is a pattern. A choice of strings is expanded into each variant, never a suffix slot: `` `${n} game${n === 1 ? "" : "s"}` `` gives `"{{n}} game"` and `"{{n}} games"`.

## How the game applies a pack — `translator.js` + `phraseBook.js`

`startTranslator()` (called from `src/main.jsx`) returns at once for English. Otherwise it sets `<html lang>` (and `direction: rtl` for ar/fa/ur/he), starts loading the prompts' passages (`loadPromptTranslations`), reads this device's cache, fetches `/api/lang/:code`, waits for the startup screen to go, then walks the DOM and watches it with a `MutationObserver`.

**Lookup** (`createPhraseBook()` in `src/runtime/phraseBook.js`, pure and tested in `phraseBook.test.js`):

1. the exact string, then the string with its whitespace collapsed;
2. a **date**: the game writes its dates in English ("Jan 1, 2016", "1 March 218 BC", "2016-01-08", from `formatGameDateReadable` in `gameDates.js` and dayjs), and the same functions write the dates the AI reads, so they stay English at the source. `createDateLocalizer` (`src/runtime/localDates.js`) recognizes a string that is exactly one of those shapes and writes it the player's way with `Intl` ("1. Jan. 2016", "2016年1月1日", "1. März 218 v. Chr."), always in the Gregorian calendar and with Latin digits;
3. the patterns, most literal text first: the slots capture the values, each value is itself looked up, exactly or as a date (so `"Edit {{label}}"` over "Edit Borders" reads "Grenzen bearbeiten"), and the translation is filled in;
4. a **list** joined with " / ", " · ", " • " or " | " ("Modern Day Session / Japan / 2016-01-01"), which no pattern holds because it has no words of its own: each part is looked up by itself, and the list changes only when some part is known. Dashes are not separators, since prose uses them.

Two guards keep a short pattern from rewriting prose that merely starts with its words (an English reply in a chat set to another language, say): a **weak** pattern (fewer than 8 letters of its own, like `"Our {{label}}"`) accepts at most 4 words of value, and no value that mixes words and numbers unless the book knows it ("Found 12" before `"{{value}} regions"` is the start of another sentence; "Jan 1, 2016" is a date); and a value never spans two sentences unless the pattern has 16 or more letters of its own. Two slots with nothing between them are never compiled (they cannot be told apart).

**The DOM:**

- A text node is looked up by its English. The translator remembers, per node, the English it last saw and what it wrote (`nodeRecords`), so its own writes are never mistaken for source text and React's next write (new English) is translated again.
- **Runs.** React renders `<p>Found {count} regions</p>` as three text nodes. A parent whose children are all text nodes is read as one string; when the pack knows it, the whole translation goes in the first node and the others are emptied (they keep their English, so React's next update to any of them re-composes the sentence). When the pack does not know the whole, each piece is looked up on its own.
- **Attributes:** `title`, `placeholder`, `aria-label`, `aria-description`, `alt`, observed as they change; and `document.title`.
- **Skipped:** `script, style, noscript, input, textarea, [contenteditable], [data-no-translate]` (an input's own `placeholder` and `title` are still translated).

**Precedence:** the server's pack (shipped over saved) is laid over this device's cache (`localStorage["i18n_v2_<code>"]`), so a stale local translation never hides the pack's. The cache holds only what the AI translated on this device and the server does not have yet. The pre-pack caches (`i18n_cache_*`) are removed on boot; what they held that the server lacked is sent to it first.

**The first screens** (the website's home page and demo notice, the Android boot screen) are drawn with plain DOM calls before the game mounts and the translator starts. Their text is the `BOOT_TEXTS` table in `src/runtime/web/bootTexts.js`, which the extractor reads like any `_TEXTS` constant; `installWebBackend` (`src/runtime/web/index.js`) loads the player's shipped pack before the home page paints (the boot screen, painted first, is relabelled when it arrives, within 1.5 s) and each string is looked up whole with `bootText(key)`, English as the fallback. A screen drawn from a pack is marked `data-no-translate`, so the translator does not look its translated text up again. A language without a shipped pack stays English there until the translator reaches it.

**The loading screen** (`StartupScreen.jsx`) is marked `data-no-translate` and the DOM translator waits for it to go, so it looks its own text up with `translateNow(text)`: the phrase book as it stands (the device cache at once, the server pack a moment later), nothing queued and no request. Its strings are written whole in the component so the catalog reads them.

**Map labels** are not DOM: `translateLabel(name)` (used by `Nations.jsx`) looks the name up and queues it as content when unknown; `"i18n:updated"` tells the label builders to rebuild when translations arrive. The country labels of a scenario's own map are built in the political worker from those names, and two labels that read alike fall back to their owners' names; that comparison (`labelFoldKey` in `Game/Map/vnext/polityNaming.js`, whose `resolvePolityLabelNames` Nations.jsx runs) keeps letters of every script, since a fold to a-z made every Chinese or Arabic name the same empty key and put every label back in English. City names on the map come from the pack through `lookupLabel(name)`, which never queues: `Cities.jsx` gives each name the pack has its translation (a `match` in the label's `text-field`), and a name it lacks stays as it is. Stock names are read from the loaded tiles, a scenario's from its `cities.geojson`; a city the AI renamed (`world.cityRenames`) shows the new name as written. They rebuild on `"i18n:updated"`.

## Content

Content is whatever a scenario's author or a player made. It is queued only where the model is in use, and gathered up front, so it is translated once instead of one panel at a time:

- **At boot and on every switch of save** (`oh:active-game-changed`), `collectContentStrings()` queues: scenario and game cards (`/api/scenarios`, `/api/games`), country names the pack lacks, every polity's name, aliases, role, note and map labels (`world.polityOverrides`), the scenario's own events (those whose `source` is `"scenario"`; the AI's events are already in the player's language), a custom Stats sheet's section and stat labels, descriptions and units, and Community posts.
- **Region names** are the big set: the built-in Modern Day map has 4,848. The built-in scenarios' names ship in the packs (`build-catalog.mjs` reads `server/seed/*/regions.geojson`), so the book finds them. Any other map's region names are only remembered at boot, and one goes to the model when it is shown (a tag, an owned-region pill, an event's impacts) and the book has nothing for it.
- **As it is written:** `library.js` calls `enqueueContentStrings(payload)` when a scenario or game is created or saved; `gameState.js` calls `enqueueEventStrings(events)` on every event-log write (only the scenario's own events are queued); `communityHub.jsx` calls `enqueueStrings` for fetched posts. Polities written during play are not queued: the AI writes them in the player's language, and the player types theirs in it.

Anything already known is never queued. Results are saved to the server's pack (`PUT /api/lang/:code`), so each string is translated once, on every device.

### The translation model

Where a small open model translates English into the player's language well, it translates the queue on the device (`src/runtime/translationModels.js`, pure and tested in `translationModels.test.js`). Until 2026-11-05 the player's AI model translated whatever no model or pack covered; the owner: "remove the option to use your api. it should make you use the model if you want to translate the game at all". The models are [Opus-MT](https://github.com/Helsinki-NLP/Opus-MT) (University of Helsinki, CC BY 4.0), in the int8 ONNX copies Transformers.js publishes (`Xenova/opus-mt-en-*` on Hugging Face, pinned to a commit) or, where nobody had published one, converted for the game the same way (Optimum's ONNX export, ONNX Runtime's int8 quantization, a `tokenizer.json` from the model's own SentencePiece model); one per language, 110 to 150 MB each:

| Language | Model | Note |
|---|---|---|
| ar | `opus-mt-en-ar` | told `>>ara<<` |
| de es fr id it nl ru | `opus-mt-en-<code>` | |
| pt | `opus-mt-en-ROMANCE` | told `>>pt_BR<<`, as the pack is Brazilian |
| zh | `opus-mt-en-zh` | told `>>cmn_Hans<<` |
| da hu ro cs fi | `opus-mt-en-<code>` | no shipped pack: the whole interface goes to it |
| sv | `opus-mt-en-gmq` (converted) | told `>>swe<<` |
| lv lt | `opus-mt-en-bat` (converted) | told `>>lav<<` / `>>lit<<`; one download for both. No pack |
| sk et el he ga mt | `opus-mt-en-<code>` (converted) | no pack. Hebrew reads right to left (`RTL_LANGUAGES`) |

**Where the files come from.** Xenova's copies are read from Hugging Face. The converted models (`mirrorOnly`, made with `converted()` in `translationModels.js`) are published nowhere else: eight models for nine languages (`opus-mt-en-bat` for Latvian and Lithuanian, one download; `en-sk`, `en-et`, `en-el`, `en-he`, `en-ga`, `en-mt`; and `en-gmq` for Swedish), each six files of 134 to 149 MB in all. They are kept on the scenario repository's `translation-models` branch (`models/<name>/<file>`, with a README naming each source, revision and licence) and read through `raw.githubusercontent.com`, which answers any origin (GitHub's release downloads send no CORS header). `MIRROR` in `translationModels.js` pins that branch to a commit; `modelSources(entry)` gives the host and path template a model is read from, which the worker hands Transformers.js (`env.remoteHost`, `env.remotePathTemplate`), and `modelFileUrl` is the same URL, which is also the file's cache key.

The other shipped languages show their pack alone: `vi`, `hi` and `uk` have a model, but on a trial of polity names and scenario blurbs it renamed places ("Kingdom of Bavaria" → Persia in Vietnamese) or ran on (so did `opus-mt-en-sv`, "Duchy of Milan" → "chairman", before the North Germanic model replaced it); `ja`, `ko`, `pl`, `tr`, `bn`, `fa`, `th` and `ur` have none under a few hundred MB that runs in Transformers.js. NLLB-200 covers them all but is CC BY-NC; M2M100-418M is about 640 MB.

- **Asked before the language is used.** Choosing a language with a model (Settings, or the first-time setup) shows a card over whatever is on screen, in that language where its pack has the words: its size, **Download** or **Keep English** (**Cancel** from another language). A yes downloads it there, the card showing how far; the language is applied once the model is ready, and a failed download offers **Try again**. A device already in such a language without a yes is asked at start, and a no puts it in English. The answer is kept in `localStorage["oh:translation-model:<code>"]`. The card takes the interface theme's colours (`--oh-ui-*`), neutral grey without one.
- **Downloaded once, run in a worker.** `translationModel.js` (the page's side, imported only when needed) runs `translationWorker.js`, which loads the model with Transformers.js on ONNX Runtime's CPU WebAssembly, one thread. The runtime's `.wasm` (14 MB) is emitted into the build (`vite.config.ts`, `oh-ort-transformers/`); the weights are kept under `oh-translation-model-v1`, which the start-up sweep of old caches in `assets.js` leaves alone, and only one language's model is kept. Where they are kept is `src/runtime/modelStore.js`'s choice (`openModelCache`, `deleteModelCache`): the browser's Cache Storage where the page has it, otherwise IndexedDB (a database `oh-model-store:<name>`, one store of files keyed by URL), which answers the part of the Cache API that Transformers.js (`env.customCache`) and the workers use: `match`, `put`, `keys` and `delete`. The Android app is served from `http://app.openhistoria`, which is not a secure origin, and Cache Storage exists only in one, so before this every model download on the phone failed ("Browser cache is not available in this environment.", a player's log, Arabic, Android stable #26). A connection the store opened is closed before its database is deleted, since a deletion waits for every connection. The on-device model of [related past events](runtime-services.md#related-past-events--srcgameairelatedeventsjs) is kept the same way. Loading from the cache needs no connection: the tokenizer is read by the worker itself, because Transformers.js 4.3.1's `AutoTokenizer` asks the model host about the `main` revision on every load.
- **Batches of 8 strings or 1,200 characters**, rows of similar length together; a long string is cut into its lines and sentences and put back with the same breaks. About 0.1–0.25 s a short name and 1–2 s a two-sentence blurb on one thread in Chrome.
- **What of its answer is kept** (`acceptModelOutput`): an answer that runs on (a mark or a word repeated to the end), far longer than the English, echoes its language token, or loses or invents a number or loses a `{{slot}}` is refused, and that string stays English for the session. A model that will not load leaves what it would translate in English for the session.
- What it translates is saved to the server's pack.

### Translate with my AI

"add an toggle to do translation with your api (still must require downloading the translation model, this option exists if they are unhappy with the models quality)" (the owner, 2026-11-06). A switch in Settings → General → Language, under the interface language, **off by default**, stored like the other UI settings (`localStorage["i18n_translate_with_ai"]`, `MAP_SETTING_KEYS.translateWithAi` in `mapSettings.js`). The rules are in `src/runtime/aiTranslation.js`, pure and tested in `aiTranslation.test.js`:

- **Where it is offered** (`aiTranslationOffered`): the interface language has a translation model and the player said yes to its download. Not in English, and not in a language with a pack and no model (`ja`, say): there the model translates nothing, so there is nothing to hand the AI. The download is never skipped; the switch appears only once it is done.
- **What goes to the AI:** exactly what the model would translate. A shipped pack's strings stay the pack's: the translator reads the shipped pack itself (`<base>lang/<code>.json`, as the server's merges the model's entries in) and never asks for one of its keys; until it has, and if it cannot, the model translates as with the switch off. In a language with a pack that is content only; in one without, the interface too. What the model translated earlier is asked of the AI again as it is shown, once.
- **Batches:** one request at a time, up to 240 strings or 6,000 characters (`planAiBatch`), with the old prompt (a JSON array in, one of the same length out), through `callAI` with `taskKey: "translation"` (its own row in Settings → AI → models per task, and in Used today) as a background request, `languageMode: "none"`. The AI's modules are imported only inside that path.
- **Cached:** the AI's translations are kept on the device in `localStorage["i18n_ai_v1_<code>"]`, apart from the model's (which go to the server's pack), and laid over the book while the switch is on; a string is asked of the AI once (answered: cached; failed: left to the model for the session).
- **Falls back to the model:** a request that fails (no key or nothing in the Fallback list, a rate limit, a refusal, an answer that is not a JSON array of the right length) sends that batch to the model, and an entry that fails `acceptModelOutput` goes to it alone. A string the model translated before keeps that translation. After a failure the AI rests a minute (the model translates meanwhile); after three in a row it is left alone for the session. The pill says so once: "Your AI could not translate, so the translation model on this device did."
- **Off at once:** turning it off lays the book again without the AI's translations and walks the page: the model's translations are back, and what only the AI had goes to the model. Off, the router never asks the AI (`createTranslationRouter`'s `isAiOn`, read before every step).

Transformers.js 4 no longer puts a Marian language token (`>>ara<<`) at the front of the input itself, and keeps generating a row that has finished while others in its batch have not; the worker prepends the token's id and cuts each row at its first end-of-sentence token.

What is translated at all is decided in `src/runtime/translationRules.js`, pure and tested in `translationRules.test.js`: which strings have words (`isTranslatable`) or are numeric dates (`isNumericDate`), where an unknown rendered string goes (`routeUnknownText`), and which events and fields are content (`isAuthoredEvent`, `collectContentText`: the display keys, `aliases`, no geometry, at most 6 levels deep and arrays of at most 500).

## The prompts

`src/runtime/promptTranslations.js` holds the loaded passages. `localizedGuidanceDefaults()` in `src/Game/AI/gameplayPrompts.js` is the default guidance tree with every passage the pack translates swapped in (memoized by `promptTranslationsVersion()`), and:

- `normalizePromptPack()` composes each prompt from its English template with the **localized defaults under the author's own passages** (`localizedPassages`). An author's passage is theirs, in whatever language they wrote it.
- `normalizePromptGuidance()` drops an edit identical to the localized default, as it drops one identical to the English default (`withoutLocalizedDefaults`), so opening and saving the Prompts tab in German never pins German wording into a scenario other players read.
- The Prompts tab (`PromptSectionEditor` in `libraryBar.jsx`) shows the localized defaults and re-renders when they load.
- `ensurePromptsLoaded()` in `src/Game/AI/main.jsx` keys its cache on the passages' version, so prompts composed before the passages arrived are recomposed.
- Exports and transfers (`materializePackGuidance`) use the English defaults.

The passages are keyed by their English text: a passage whose wording changes simply falls back to English until the packs are regenerated, and a branch whose prompts differ finds only the passages it shares.

## Writing interface code that translates well

The catalog is read out of the source (`scripts/i18n/extractStrings.mjs`), so the way a string is written decides whether a language can translate it:

- **Keep a sentence in one template or one run of text.** `` `${count} regions found` `` or `<p>Found {count} regions</p>` is one pattern a language can reorder. A sentence split around an element (`Found <b>{count}</b> regions`) becomes pieces ("Found", "regions") translated separately.
- **Plurals and variants as whole words:** `` {n === 1 ? "event" : "events"} `` or `` event{n === 1 ? "" : "s"} `` both expand into both variants. Never build a word from pieces a language cannot reorder.
- **One English string, one meaning.** A pack is keyed by the English text, so two things that share a label share its translation, whether or not the language has one word for both. "Features" was the scenario and game editors' tab of gameplay features and also the title of the Workshop's list of cities, bases and ports: most packs put the map's word on the tab (Japanese "地物"), French and German the gameplay word on the list. The list is **Map features** now. Give the second thing English wording of its own; and a pack that renames a tab renames it in the sentences that send the player there.
- **A sentence the DOM never shows as interface** (one put in a composer for the player to edit, or sent as the player's own line, or one the engine writes into the save in the model's place: a fallback turn's events, summary and suggested orders, from the `FALLBACK_TURN_TEXTS` table in `src/runtime/fallbackTurnText.js`) goes through `uiString(text, params)` from `translator.js`: the pack's entry for that exact key, a `{{slot}}` pattern filled from `params`, or the English. Write it as one string literal (a named constant if it is long, never glued with `+`), so the catalog holds the key whole.
- **Names, codes, numbers and anything the player typed** go in an element marked `data-no-translate`, so they are neither looked up nor mistaken for interface.
- Text-bearing props are read from JSX (`label`, `title`, `hint`, `description`, `placeholder` and the rest of `DISPLAY_KEYS`), from registries in the directories the extractor reads (`src/runtime`, `src/Game/GameUI`, `src/Game/Selection`, `src/Game/Map`, `src/Editor`), and from status setters (`setStatus(...)`, `STATUS_CALLS`). A camelCase key ending in `Label` (`mappedLabel`, `centerSubLabel`) counts too, and its value may be a single lowercase word ("landscape"), which elsewhere would read as an id. A difficulty level's profile values (`playerLeniency` and its three siblings) are display keys, and its `effects` list is read sentence by sentence (`DISPLAY_LIST_KEYS`); its `directives` are the model's and are not.
- **A panel's prose moved into plain `.js` stays the panel's.** A module split out of a `.jsx` panel so node can test it (`src/Game/GameUI/turnReveal.js`, the Events panel's map-change lines) is read the way a `.jsx` file is, every prose-like string included; list it in `PROSE_FILES` in the extractor, or its strings drop out of the catalog.
- **A screen shows what it catches.** Every `.jsx` file's thrown and returned prose is read (`throw new Error("Give the group a name.")`), because its screen puts `error.message` in front of the player.
- **Name a constant for what it holds.** Every string in an `UPPER_SNAKE` constant ending in `_LABEL(S)`, `_HINT(S)`, `_INTRO`, `_NOTE(S)`, `_TEXT(S)`, `_MESSAGE(S)`, `_TITLE(S)`, `_DESCRIPTION(S)`, `_BLURB(S)`, `_CAPTION(S)`, `_TOOLTIP(S)` or `_PLACEHOLDER(S)` is read as display text (`STRUCTURED_MODE_LABELS = { auto: "Automatic (recommended)" }`). A constant so named but written for the model goes in `MODEL_CONSTANTS` in the extractor.
- `src/Game/AI/*.js` is prompts and parsers, and is not read, except the registries behind Settings → AI and the Prompts tab (`JS_REGISTRY_FILES`) and the modules whose messages the player reads (`MESSAGE_FILES`: the provider failures, the Fallback list, the context window, the request budget), whose returned and thrown prose is read. The institutions' modules are message modules too (`institutionLifecycle(Core)`, `institutionalGovernance`, `institutionalChannels`, `institutionAuthoring`, `politicalWorldCapability`, and the advisor's and Game Master's institution helpers): what they refuse with shows in the Institutions tab, and the events and channel lines they write are read in the log. So is the GM tools' Puppet States editor (`src/Game/GameUI/puppetStatesTool.js`), whose refusals show in the cheats panel. A new module of player-facing messages belongs in that list.
- **A module whose messages reach the screen is read in full.** A sweep on 2026-11-06 for player-facing English that no pack held found 1,096 strings the extractor could not see, plus 15 catalog entries no pack had: 1,111 in all (`c71e60d6`). Since then `PROSE_FILES` lists about ninety `.js` modules whose returned, thrown and constant text reaches a screen as it is (War Room, aircraft, fortified-line and fleet refusals; the Workshop's imports, maps, flags and border report; a time skip's progress and what stopped it; the Advisor's proposal cards; spy headlines, peace terms, puppet loyalty, Rostra, hub, download, update and local-server errors; on beta also joining and hosting a shared game). `MESSAGE_ONLY_FILES` are read for their whole returned and thrown sentences only. In any message module an arrow's returned expression is a message (`(what) => "This " + what + " was…"`), and text joined with `+` is read as the whole sentence, never as its pieces. Update notices are read too: a notice's `items` is a display list and its `lead` and `button` are display keys (`notes.js`, `notesPast.js`; about 380 lines had stayed English).
- **`// i18n-ignore`** above a statement, a declaration or a property skips everything under it. Mark what a message module writes for the model or for the code (a prompt, a storage key, a pattern it matches, a hub marker): a few dozen places carry it, and without it their text would land in the catalog and be sent for translation.
- **The browser's own boxes** (`window.alert`, `confirm`, `prompt`) are drawn by the browser, not the page, so the DOM translator never saw them, though their text was in the packs. `src/runtime/nativeDialogs.js` (`installNativeDialogTranslation`, installed once by `src/main.jsx` with `translateNow`) wraps the three: each message is looked up whole (exactly or by pattern, `Delete {{count}} selected features?`) and, failing that, line by line, for a message built of sentences the packs hold one by one. A prompt's default value is the player's data and is left alone. About eighty dialogs go through it; write their text as one string or one pattern, like any other.
- **The desktop app's main process** (the right-click menu, the box when the page stops or the app cannot start, a failed update) never passes through the page. `electron/uiWords.cjs` `uiWord(text, params)` looks the English up in the shipped pack of the language the player chose (the server's `ui-settings.json`, which the page writes; the packs from the built `dist/lang` or `public/lang`), fills `{{slots}}` from `params`, and is the English without a choice, a pack or an entry. The extractor reads only what is handed to `uiWord` in `electron/main.cjs`, `payloadUpdate.cjs` and `layeredUpdate.cjs` (`WORD_FILES`); `server/desktopUiWords.test.js` pins it.
- **The Android plugins' refusals** (`mobile/android/.../*Plugin.java`): the sentence in `call.reject("…")` and in the `IOException`s they reject with reaches the page as an error's message, so the extractor reads it (`javaMessages`); a value joined on (`"…: " + error.getMessage()`) is a slot.
- **Write an event or a log line as one sentence per case**, not a sentence assembled from a verb looked up in a table (`${subject} ${actionLabel} ${name}`): a language can translate `"{{subject}} Joins {{name}}"`, never `"{{subject}} {{actionLabel}} {{name}}"`. `lifecycleEventTitle` and `outcomeEventDescription` are the pattern. `puppets.js` wrote what a puppet arrangement means from English word pieces until 2026-11-06; it now has a whole sentence for each side.

## Regenerating the packs

1. **Build the catalogs.** One catalog serves every branch: pass the other branches' trees and it is their union, so the same packs ship everywhere.

   ```
   git archive origin/beta src scripts/presets | tar -x -C ../tree-beta
   git archive origin/main src scripts/presets | tar -x -C ../tree-main
   node scripts/i18n/build-catalog.mjs --also ../tree-beta --also ../tree-main
   ```

2. **Translate what is new.** Since November 2026 the maintainer translates new interface strings with Gemini (`gemini-3.5-flash-lite`), through two small scripts kept outside the repository, in two passes. The changes that added strings since then (notices, new settings, the 1,111-string sweep) went through it, and their commits say so ("translated with gemini-3.5-flash-lite"). What they do, so it can be done again with any tool:

   - **What goes in.** The strings the catalog has and the packs lack, as a JSON array (`i18nCatalog.test.js` and `languagePacks.test.js` name them), the strings the catalog dropped, and a short background note: what the game is, and the words it already uses for its own things.
   - **First pass.** For each of the 22 pack languages, batches of 80 strings, one `generateContent` request each, asking for a JSON array of the same length (`responseMimeType: "application/json"`, a `responseSchema` of an array of strings) at temperature 0.2. The prompt asks for natural, consistent game-interface text; every placeholder (`{{name}}`, `{name}`, `%s`), tag, number and arrow kept exactly; the brand names (Open Historia, Gemini, OpenAI, Anthropic, Scott Buckley, Discord, GitHub) left untranslated; a label's capitalisation kept; and it gives the language's own pack renderings of the game's terms (War Room, Workshop, Advisor, time skip, scenario, Settings, Community, restore point, polity, front, battlefield) as a glossary. An answer of the wrong length, with an empty entry or with a different set of placeholders is asked again, up to three times; 429 and 5xx answers are waited out. A finished language is kept, so a run can be resumed.
   - **Every answer is checked** before it goes in: empty values, placeholders, English left in place (in a Latin-script language, more than 60% of a sentence's longer words unchanged), the wrong script for the language (Urdu or Hindi with other scripts mixed in, Japanese written as Chinese) and the pack's own name for a tab ("Features" called by another name). What fails is left out of the packs and shows in English until the second pass. In the sweep 342 of 1,111 × 22 values failed, mostly Urdu, Dutch and Japanese.
   - **Merge.** New strings join `catalog-en.json` (sorted, one-space indent, its own line endings) and every pack (`public/lang/<code>.json` stays one minified line, existing keys in their order, new ones appended, its final line ending as it was); the dropped ones leave both. A string both new and dropped is an error.
   - **Second pass, for what failed.** Per language, batches of 15 at temperature 0.1, with a stricter prompt: the string fully translated and written only in the language's own script (Latin letters only for brand names and placeholders), the terms of the game, Features, Actions, Rostra, Wars, Politics, Statistics, Spy and Diplomacy included, written exactly as the pack has them, and the two weak languages named precisely ("Japanese … never Chinese"; "Urdu (Arabic script, Nastaliq conventions; never Hindi or Bengali script)"). The same checks; a string that still fails is asked alone, up to four rounds in all; only answers that pass are kept (`5cfbf36f`: 362 entries).
   - **The key** is the maintainer's, read from a file outside every repository (or the environment), and never printed or committed. A pack holds nothing secret.

   `scripts/generate-lang-packs.mjs` is the in-repository way to do the same with any OpenAI-compatible endpoint (Gemini offers one too; the key is read from the environment and never written anywhere):

   ```
   OH_LLM_BASE_URL=… OH_LLM_KEY=… OH_LLM_MODEL=… node scripts/generate-lang-packs.mjs --all
   ```

   It is incremental (only strings a pack lacks are sent), drops entries the catalog no longer has, rejects a translation that loses a placeholder, and does the prompt passages too, one per request. `--lang de,fr` for some languages, `--dry-run` to count, `--force` to redo everything. It has no script or glossary checks: read what it wrote in the languages that went wrong before (Urdu, Hindi, Dutch, Japanese).

3. **Check.** `node --test src/runtime/languagePacks.test.js src/runtime/i18nCatalog.test.js`: every pack on disk is listed in `SHIPPED_PACK_LANGUAGES` and back, every placeholder survived, each pack covers at least 90% of its catalog, and every string the extractor finds is in the catalog.

To add a language: add its code to `SHIPPED_PACK_LANGUAGES` and to `LANGUAGES` in `generate-lang-packs.mjs`, then run step 2 for it.
