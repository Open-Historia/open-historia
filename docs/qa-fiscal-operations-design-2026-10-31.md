## 2026-11-01 - fiscal polity rename and Preview/Apply parity repair

**Additional source-proven integrity gap repaired; original #009 remains PARTIAL.** The canonical rename seam in `server/polityRename.js` already re-keyed military expenditure commitments but omitted the two new fiscal ledgers. A red-before-green regression proved renaming a polity left its authorized grant/payment and tax-holiday forecast assigned to the old, now inactive identity. The shared rename now re-keys `fiscalTransactions[].polity` and `fiscalTaxPolicies[].polity` while preserving all nominal amounts, denominations, legal and accounting dates, source event IDs, settled receipts and elapsed forecasts. It also covers repeated renames and does not touch foreign polities or the source world.

A second red-before-green regression established a real Preview/Apply mismatch: the native event reducer accepted a grant attributed to a country renamed in that same event, but `validateFiscalEventOperations` rejected it as unknown because its pure preflight still used the pre-rename world. Fiscal Preview now projects **only valid rename operations involving already-active canonical polities**, using the same shared rename writer, before fiscal authorization/payment checks; the resident polity resolver is rebuilt from the projected canonical world for each event. Both same-event and earlier-event renames preserve Preview/Apply identity, and the source world remains untouched. No generic polity creation/restoration, new Project creation, or financial mutation is simulated during fiscal Preview. These are separate source contracts still requiring their own acceptance. To preserve existing validation semantics, pure **non-fiscal** event batches bypass this fiscal preflight entirely; a regression proved the initial missing guard caused an unrelated rename clash to surface through the fiscal validator, and the correction passed.

**Monetary-denominator boundary confirmed from implementation:** `countryStats.js` displays national GDP as a **2026-EUR-equivalent** aggregate, while `economy.currency` is the *domestic currency*. An arbitrary nominal USD/EUR payment cannot be converted to debt-ratio points using the domestic-currency label as an exchange rate. A lawful new-debt settlement needs an explicitly sourced date, denomination and GDP-equivalent valuation; this patch adds **no** speculative conversion, debt posting or tax-to-actual-cash inference. The existing event Stats ratio and scenario-priced military commitment writer remain their own native authorities.

## 2026-11-01 - second partial native fiscal slice: bounded tax-holiday forecast

**Status: implemented in source, not independently live-accepted.** The earlier grant/payment/cancellation slice below remains current. An additional independent owner `world.fiscalTaxPolicies` now tracks *forecast revenue foregone* by an **enacted, explicitly total-priced** temporary tax holiday. It does NOT post actual Treasury cash movements or edit GDP, national debt, national deficit, or annual `budgetBalance`.

- `impacts.fiscalOps.enact-tax-holiday` requires stable ID, active polity, explicit ISO currency, stated nominal total, source event and reason, plus a dated start accounting boundary and final covered date spanning **1..240 days**. It refuses an unspecified total, rate, term, or a new field pretending to set debt/tax receipts. Because the period uses a boundary `startDate`, the first accrued day is the next civil day through `endDate`.
- `impacts.fiscalOps.repeal-tax-holiday` closes only the unaccrued remainder. Previous foregone-revenue forecasts remain immutable. A repeal during a Timeline turn excludes its own date if not accrued yet; a Game Master repeal on the last **already-accrued current date** is accepted and preserves that day's reading while stopping future accrual.
- `advanceFiscalTaxPolicyClock` is a separate deterministic, dated clock. It uses exact integer-cent cumulative allocation and BigInt intermediate products, so split versus whole skips and replays conserve **the same forecast to the cent**. Normalization refuses forged amount/cursor mismatches and invalid status or repeal history.
- The canonical event reducer carries this clock on advancing Timeline turns and settles tax events in date order. Game Master Apply records an enacted/repealed law **without advancing campaign time**. Fiscal event preflight uses the same native operation reducer, and GM Preview discloses planned tax authorizations and foregone-revenue forecasts separately from actual disbursements.
- The provider-facing ordinary Timeline grammar stays within its existing strict schema-size limit: tax operations are supported by the strict accepted-event validation and GM schema, but **not autonomously originated by the lean Timeline model tool**. The complete tax policy source/forecast remains multiplayer host-only like grant payment provenance.
- Added focused red-before-green current-day repeal regression, actual world reducer split-versus-whole/repeal tests, GM JSON transport/preview regressions, multiplayer privacy canary, and exact i18n catalog entries. Run production and full-suite logs for the last implementation state before describing any QA package as green.

**Still OPEN (#009 partial):** actual tax-receipt observation; funding and debt-financed nominal grant disbursement; source-authorized currency valuation/GDP denominator; coherent annual deficit adjustment and fiscal-clock double-count prevention; fiscal obligation stages beyond grants; provider-originated ordinary Timeline policy operations; paid Gemini and packaged Electron save/Undo acceptance. A nominal foregone-revenue *forecast* is not evidence of actual cash or debt.

## 2026-11-01 - partial native fiscal lifecycle now implemented

**Implementation status: partial, source-verified; no paid-provider/packaged Electron acceptance.** The original 2026-10-31 evidence and design discussion below are preserved as the baseline *before* this implementation. The smallest supported first-class fiscal owner now exists in `src/runtime/fiscalTransactions.js` and is persisted as `world.fiscalTransactions`. It is an append-only-in-effect, replay-checked **nominal commitment/payment ledger**, not a GDP, deficit, tax-accrual or debt-stock writer.

- **Enacted grant/relief/procurement/transfer**: a dated `impacts.fiscalOps.authorize` records exact nominal amount, explicit ISO currency, polity, stable ID, canonical source event, evidence reason and optional existing same-owner project. Authorized amount is **unpaid**; no Treasury payment follows from a Project's progress or creation.
- **Explicit already-budgeted payment**: `impacts.fiscalOps.pay` records a separately evidenced nominal tranche, date, stable event, source reason and exact remaining amount. A new debt financing claim is rejected as unsupported. Paid amounts may not exceed authorization and cannot be replayed into a double payment.
- **Cancellation**: `impacts.fiscalOps.cancel` closes remaining unpaid authorization, retaining prior payment receipts and refusing future payments. Unknown IDs, duplicate operations, backdates, invalid currency/amount, overpayment, and malformed persisted state fail closed.
- **Source integration**: `normalizeWorldState` validates and retains the ledger; `normalizeEventImpacts` retains fiscal operations; `applyEventImpactsToWorld` settles them within its detached canonical event reducer after project operations; `eventImpactKeys.js` marks these as genuine state-linked impacts. `gameplaySchemas.js` validates the 3 native operation shapes with `additionalProperties:false`.
- **GM parity**: `validateGeneratedWorldChanges` uses a pure sequential dry-run before Preview/Apply; `previewGameMasterCommand` exposes a read-only nominal amount/stage table in `cheats.jsx`. The GM prompt names this typed operation rather than reclassifying Projects as paid. A replay of an old authorization *after* subsequent payment/cancellation preserves the full later history. Direct baseline patches remain restricted by existing authority rules.
- **Important bounded provider contract**: `fiscalOps` is in the authoritative accepted Timeline event schema and GM tool schema. It is **not** added to the lean ordinary Timeline provider tool, whose tested size budget is unchanged. Ordinary Timeline AI is therefore not yet being asked to originate fiscal authorizations; future staged generation must respect the provider grammar limit rather than weakening it.
- **Multiplayer privacy**: the complete nominal fiscal ledger and payment provenance are classified **host-only**, matching military expenditure authorization receipts. They are never sent in other players' projected world state, including their own seat's host projection.
- **Validation**: 8,395 tests total / 8,392 passed / zero failed / one skipped / two TODO in `OpenHistoria-QA-FiscalLifecycle-20261101-FullTests-R2.log`. The first full suite found 13 real provider-budget/privacy coverage regressions; those were fixed at the architectural seams, retaining all original size and privacy guards. Final relevant focused checks 62/62, independent fiscal/GM/i18n checks 88/88; no schema limits loosened.

**Still missing before #009 can be closed**: tax-holiday enactment, bounded revenue-foregone accrual and expiry/repeal; nominal-to-GDP conversion requiring a defined currency and dated GDP valuation; explicit new borrowing/payment stock booking and avoiding double counting against existing `statsFiscalClock`; complete mixed project/disbursement references, live paid Gemini/GM Apply, save/reload/Undo and multiplayer event-audience acceptance. No output should claim that an authorization alone changes national debt, GDP, or the annual fiscal rate.

## What the evidence establishes

The sanitized GM study ran 56 completed Previews from 24 authored prompts. Forty-two validated. Of those valid previews, sixteen contained Project operations and none contained a `countryStatPatchesJson` baseline edit. In Test 36, a narrated $2bn payroll-tax holiday was represented as a project beginning at 10% progress. In Test 40, six valid $600m hurricane-relief outputs generated projects without a typed fiscal entry. In Test 44, five valid $400m cybersecurity-grant outputs did the same.

**Do not claim an Apply-time failure**: the QA cases were Previews, and no canonical save mutation was executed. Also, zero baseline country patches in these world-intervention cases are **correct**: `validateGameMasterStatsAuthority` deliberately reserves `countryStatPatches` for Direct administrator-authored baseline corrections. The absence of countryStatPatches is not itself a regression.

| `statsEventEffects.planStatsEventEffect` | Dated, **explicit new debt-financed** relief/procurement/mobilization/reconstruction outlay, expressed as `debtFinancedOutlayPercentGdp` with enumerated cause and bounded justification | Changes debt stock only. | `statsFiscalClock.advanceNativeFiscalClock` | Accrues an established **annual fiscal rate** into public debt over elapsed days | Source-derived, bounded to 240 days and +/-50 annual GDP-share points; replay-aware; does not infer new rates from policy prose. |

There is currently **no supported event field** for a $2bn tax-revenue reduction, an unfunded/appropriated-but-unpaid $600m grant, or a temporally bounded fiscal flow. Inventing a `taxRevenueDelta`, `budgetBalanceDelta` or `spentDollars` field would be rejected or, if smuggled through customStats, fork canonical ownership.

**2026-10-31 narrowly completed native chronology repair (not the proposed ledger):** The existing one-off `debtFinancedOutlayPercentGdp` writer previously accepted an event preceding the explicit national fiscal/GDP assessment from which its debt stock was read. That is an unauthorised temporal rebase. `planStatsEventEffect` now rejects a debt-financed outlay dated before an established assessment; the source-date selector is shared with `advanceNativeFiscalClock` to prevent drift, including existing legacy demographic/founding-date fallbacks. Matching and later dates remain valid, and undated legacy sheets retain their old behavior. Regression failed before repair, passed afterward with fiscal clock, event application and renderer tests. **This does not recognize an appropriation as a disbursement, solve the missing transaction lifecycle, or change the recommended design.**

## Interpretation of the QA examples

- **$2bn payroll-tax holiday:** An enacted tax policy is not an immediate GDP-stock shock. It may reduce receipts over a specified period, but the evidence does not establish whether $2bn is an annual estimate, fiscal-year total, already foregone cash, or future commitment. Creating a project may track implementation; it does not settle Treasury effects.
- **$600m hurricane relief / $400m cybersecurity grants:** Authorization, appropriation, obligation, disbursement and financing are **separate stages**. A new project can honestly represent administration or a sustained programme. Merely announcing a grant does not prove disbursement or borrowing. A debt increase is only valid when the source establishes debt financing, with a valid GDP denominator.
- **Test 42 cancellation:** The disposable fixture's cancellable project existence was not established; no confirmed cancellation defect follows from that example.

## Decision needed before new canonical implementation

**Recommended direction (proposal, not implemented):** add a *typed, dated fiscal-policy/transaction owner*, fed by validated GM/Timeline events and handled by deterministic settlement. Keep programme execution on the Projects board; make fiscal effects a separate first-class canonical ledger with a stable event identity, polity, explicit stage (authorized/obligated/disbursed or enacted/expired), financing classification and bounded monetary basis. Reuse the existing `countryStats` native financial authority and fiscalClock rather than creating a competing prose-defined budget.

A design review must decide:

1. **Accounting basis and units.** Is the supplied amount nominal currency, GDP percentage, annualized rate, or lump-sum stock? Which canonical currency/date and conversion authority are used? Missing denomination/scale must remain **unset**, never coerced to zero.
2. **Lifecycle.** Enacted tax exemptions have a start, bounded duration and expiry/repeal; grants have authorization, future obligations, partial disbursement and cancellation. Changes on a turn's last day may not accrue backwards into preceding days.
3. **Funding and stock/flow behavior.** Distinguish taxation/revenue foregone, expenditure, transfers, surplus/deficit rates, and new debt-financed borrowing. Do not charge both one-off debt and annual deficit accrual for one payment. Do not convert a project milestone into paid money.
4. **Referential integrity.** Stable polity ID, canonical event ID, cause, optionally project ID, dated receipt and nonduplicating replays. A project can be cancelled without inventing a Treasury refund.
5. **Bounds and completeness.** Explicitly priced effects only, bounded size and duration, source-backed GDP/debt anchors, audited cumulative windows, scenario custom-sheet compatibility and time-skips split/whole equivalence. Existing 240-day fiscal authority horizon should not be silently extended.
6. **Preview/Apply parity.** Preview must show proposed fiscal operation, amount/stage, source and expected effect (or why no effect is currently booked). Apply must revalidate all inputs and commit event, ledger, fiscal owner and receipt atomically, or fail without partial writes.

## Focused acceptance suite needed for implementation

- **Tax holiday:** enact $2bn with explicit term, canonical amount/basis and effective dates; accrue only on covered days, stop at expiry and do not silently rewrite GDP.
- **Relief:** authorize $600m without financing; track commitment but do **not** book debt. When independently proven debt funding and disbursement are accepted, post one bounded debt-stock change and receipt, never double-accrue it.
- **Grants:** $400m approved versus partially paid; only settled disbursements enter the fiscal flow.
- **Cancellation:** cancel an existing programme midstream; conserve previous receipts and close only remaining obligations. Unknown project IDs fail closed.
- **Time and state invariants:** one-year versus split-jump conservation, save/reload and replay idempotency, same-pair source references, historical GDP/fiscal ownership, custom Stats definition, finite bounds, direct-vs-world GM authority, action provenance, and no automatic AI reassessment.
- **Negative tests:** no inferred fiscal amount from narrative, no dropped monetary liabilities on an unsupported field, no forced zeros for absent financial data, no ambiguous dollar/GDP conversion.
