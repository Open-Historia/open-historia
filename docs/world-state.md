# World State & Turn Model

Open Historia keeps a running game in five plain-JSON documents served from a per-scenario/per-game runtime endpoint. The largest and most important is **`world.json`** — the political map plus everything the AI has changed since the scenario began (region ownership, polities, colors, tags, reputation, units, structures, interactive events, history). The **turn loop** is a "time jump": the AI returns a batch of `events`, each carrying machine-readable `impacts`, and `applyEventImpactsToWorld` folds those impacts into world state before it is persisted; the map re-renders because the write announces itself and `useWorldState` is listening.

Core files: `src/runtime/gameState.js` (state shape, normalizers, impact application), `src/Game/Map/useWorldState.js` (the map store), `src/runtime/runtimeStore.js` (the HUD store), `src/Game/Map/unitsController.js` (the units store), `src/runtime/countryTags.js` (tag rules), `src/runtime/assets.js` (read/write/cache plumbing), `src/Game/AI/gameplay.js` (`applySimulationResult`, the turn writer).

Related pages: [Country tags](world-state.md) · [Map rendering & Nations layer](game-map.md) · [Units & combat](world-state.md) · [AI turn / time jump](ai-overview.md) · [Scenario library](runtime-services.md).

## Glossary

The words below mean one thing each. Use them in code, prompts, tickets and PRs, and avoid the listed alternatives.

**Project**:
A deliberate effort one polity runs towards a goal, such as a research programme, a construction or a sustained campaign. It can complete, fail or be abandoned.
_Avoid_: Programme, initiative, plan (as the term for the record itself)

**Operation**:
A Project with a military or covert purpose.
_Avoid_: Mission, op

**Board**:
The player-visible list of Projects and Operations, including foreign ones the player's services know about.
_Avoid_: Projects & Operations panel, tracker

**Board entry**:
One Project or Operation on the Board.
_Avoid_: Effort, item, card

**Storyline**:
An ongoing situation no single polity controls, with unresolved stakes, such as a war, a crisis, a rivalry or unrest. Hidden from the player. A Project can cause or feed a Storyline, but the same thing is never both.
_Avoid_: Process, thread, arc

### The map

**Structure**:
Anything physical the campaign builds and the map draws in one place: a base, shipyard, data centre, ground station, reactor, embassy. Kept in `world.markers[]` and written by an event's `markerOps`, so **marker** is the field name for the record while Structure is the thing itself. A satellite is not one; the ground station that serves it is. Something that moves is a unit.
_Avoid_: Feature, facility, building (as the term for the record)

**Approximate placement**:
Where a Structure or unit goes when the place its event names is not on the map: near the capital of the country the place is said to be in, or in its owner's own territory when no country is named. The player may accept or move an approximate Structure of their own or their puppets'; everyone else's stays where it landed.
_Avoid_: Fallback spot, guessed location, default position

**Director**:
A check that reads Canonical events and turns what they narrate into changes on the map: the unit director moves, raises and wears down units, the territory director marks who holds the ground, the structure director builds Structures. It runs after a jump and after a Scene, never invents what the event does not say, and the engine's rules decide which of its changes stand.
_Avoid_: Reviewer, pass, reconciler (as the name of the check)

### Library

**Scenario**:
An authored starting position — the map, the polities and the opening state — that a Game is started from. Never written to during play, so one Scenario can seed many Games.
_Avoid_: Preset, map, mod

**Basemap**:
The flat map drawn beneath a Scenario's regions: a built-in Earth map, an uploaded picture, or a painted (vector) drawing. Every Scenario has one, and a custom one travels inside the Scenario. Players see it whenever a Scenario's detailed map is not shown.
_Avoid_: Basic map, painted map (as separate terms), background (as the term for the record)

**Tiled Basemap** (players see: **detailed map**):
One of a Scenario's maps (`CONTEXT.md`, [ADR 0007](adr/0007-detailed-maps-are-scenario-maps.md)): picture tiles **shown over** a drawn basemap of the Scenario, which players see in its place without the download, read a few tiles at a time as the player zooms. It is downloaded once, to disk, whatever its size, kept in the library, and shared by every Scenario that names it. A Scenario may name several, one of them maybe its starting map (`world.background.tiled`), the others in `world.ownBasemaps`; it names them, never carries them.
_Avoid_: Relief, terrain (as the term for the record)

**Official Basemap**:
A Tiled Basemap on the list of detailed maps on the community hub (`Open-Historia/Open-historia-scenarios`), the only place one is downloaded from. It has a fixed **map id** and numbered **versions**, each one exact file with its checksum. A Scenario names the map and the lowest version it needs; a player keeps one copy, of any version, and a newer version is offered, never forced.
_Avoid_: Catalog entry, release (as the term for the map)

**Game**:
One playthrough of a Scenario: everything the player has done and everything the world has become since it started. The thing a player names, continues, archives and exports.
_Avoid_: Save, save game, campaign, session (as the term for the record)

### Events

**Canonical event**:
Something the simulation accepted as having happened during a jump, whether or not the player sees it on the timeline.
_Avoid_: Accepted card

**Player event**:
A Canonical event that involves the player's polity in any way: something it does, something done to it or said about it, or something that happens inside its territory. Every other event is a World event.
_Avoid_: Player-related event, player-sphere event

**World event**:
A Canonical event that does not involve the player's polity at all, such as a crisis between two other powers in a theatre the player is not in.
_Avoid_: Wider-world event, background event

**Player focus**:
How much of each jump belongs to Player events: World first, Balanced, Focused or Spotlight. The Scenario sets the level a new Game starts on and the player changes it for their own Game, like any other feature setting. It is a minimum share that applies only as far as the player has something going on; in a quiet stretch the World fills the jump.
_Avoid_: Player share, player weighting, attention balance

**Interactive event**:
A moment a jump offers the player to play out in person instead of reading about it. The player can play it or let it pass.
_Avoid_: Interactive (as a noun), playable event

**Scene**:
An Interactive event the player chose to play: a run of choices that ends in one Scene outcome.
_Avoid_: Interactive, episode

**Scene outcome**:
The Canonical event a Scene ends in. It changes the world as any event from a jump would, including the map, through the Directors.
_Avoid_: Interactive event result, scene summary

**Hidden event**:
A Canonical event kept off the timeline because it was routine, low-value or already covered. It still happened. Distinct from a rejected event, which the simulation judged untrue and which never happened.
_Avoid_: Dropped event (for anything that still happened)

### Diagnostics

**Diagnostics log**:
The one log a player sends with a bug report: what they did and what went wrong, in order. It is kept on every platform, and on desktop it also carries the Desktop log's entries.
_Avoid_: Debug log, app log, server log

**Desktop log**:
Where the desktop app itself and its local server note their own start-up, update and server errors, because they cannot reach the Diagnostics log directly. It is not a second log: its entries appear in the Diagnostics log.
_Avoid_: app.log (as the name of a log), server log

**Detailed logging**:
The switch that adds whole AI exchanges, conversations and world changes to the Diagnostics log. Off by default.
_Avoid_: Verbose mode, debug mode

**Logging file**:
The single text file a player saves from the Diagnostics log to attach to a report: at most 1 MB of log, with the problem being reported on top, and never more than 2 MB in all.
_Avoid_: Debug report, bug report (for the file itself)

**Prompt fingerprint**:
The size and a short hash of each section of a prompt sent to the model, noted for every attempt under Detailed logging, so a prompt rebuilt from the save can be checked against the one actually sent.
_Avoid_: Prompt dump

### AI access

**Fallback list**:
The player's ordered list of models to answer AI calls, which may mix providers. Every call starts at the top — every call, whatever short mark an entry picked up a moment ago — and uses the first entry that answers. It moves down only when an entry cannot answer, passes over a Spent entry until its reset, and never spreads calls across entries to get more usage.
_Avoid_: Rotator, rotation, key rotation, model chain

**Connection**:
A saved way to reach one provider: which provider it is, a name the player gives it, its key, and its endpoint when the provider needs one. Many Fallback entries can share one Connection.
_Avoid_: Profile, preset, account

**Fallback entry**:
One Connection and one model, at one place in the Fallback list. A task that has its own pick names a Fallback entry: it tries that entry first, then the list from the top.
_Avoid_: Slot, route, step

**Spent**:
A Fallback list entry that has used up its allowance. Its row says so until its allowance resets, it answers again, or the player resets it. Calls go round it while the mark holds — the provider has already said it cannot answer — but never drop it: it is tried last when nothing else has answered.
_Avoid_: Exhausted, maxed out, dead

**Rate limited**:
Refused for the moment because of too many requests in a short window. Waiting fixes it, so a Rate limited entry is not Spent.
_Avoid_: Quota exceeded (for a short-window limit)

**Unusable**:
A Fallback entry that failed in a way waiting cannot fix, such as a rejected key or a model the provider does not know. It is skipped until the player edits it, and it shows the player what went wrong.
_Avoid_: Broken, Spent (for this case)

**Agent Connection**:
A Connection answered by an Agent on the player's own subscription rather than by a provider's API. It answers only what the player starts, of the kinds it ticks (time skips, the advisor, diplomacy, the Game Master, interactive events), and can be paused. It waits until it is answered, the player cancels, or the player sends the request to the next entry. Desktop only. See `docs/adr/0008-subscription-agents-answer-through-the-game.md`.
_Avoid_: Subscription mode, bridge (for the Connection itself)

**Agent**:
The program that answers an Agent Connection: Claude Code, Codex, OpenCode or Antigravity CLI, started and signed in by the player, never by the game. It returns answers; it never writes the save.
_Avoid_: Bot, AI player

**Agent queue**:
The requests an Agent Connection is waiting on, held by the local server until an Agent answers them.
_Avoid_: Inbox, jobs

**Agent folder**:
The folder the install ships for the player to open their own Agent in: its instructions, the `/answer` skill (and `/skip`, the same command), the MCP server's settings, the player's choice of models for Open Historia, and the prompt files of the Agent queue.
_Avoid_: Workspace, agent files

### Subordination

**Puppet**:
A polity whose foreign or domestic will is directed by another. It remains a separate country throughout: it holds its own territory, keeps its own sovereignty, and paints in its own colour. A Puppet is never a region-level fact.
_Avoid_: Vassal, satellite state, client state, subject (as the term for the record)

**Overlord**:
The polity directing a Puppet. One Puppet has at most one Overlord; one Overlord may hold many.
_Avoid_: Suzerain, master, patron, parent

**Loyalty**:
How far a Puppet accepts its Overlord's direction, 0-100. Always hidden, even where the subordination itself is open knowledge, and shown to the player only as a band.
_Avoid_: Obedience, compliance, satisfaction, stability

**Demand**:
An Overlord telling its own Puppet to do something, in the one-on-one conversation between them. The Puppet accepts it, refuses it, or offers an alternative, which the Overlord either takes or answers by demanding again. Only a refusal costs the Puppet Loyalty.
_Avoid_: Order, request, ultimatum (as the term for the record)

## 1. Storage model: the runtime JSON assets

All mutable game state lives behind a small set of URLs built in `src/runtime/assets.js` (`JSON_URLS`) and rebuilt on every scenario/game switch by `setRuntimeAssetEndpoints` (`src/runtime/assets.js`). Each URL carries a `?v=<token>` cache-buster; changing the token (a library mutation) sweeps the in-memory value caches so the next read re-fetches (`src/runtime/assets.js`).

| Asset key | URL (path) | Read / write helpers (`gameState.js`) | Holds |
|---|---|---|---|
| `world` | `/api/runtime/json/world` | `readWorldState` / `writeWorldState` | The political map + AI-mutated state (this page). |
| `game` | `/api/runtime/json/game` | `readGameData` / `writeGameData` | Player country, clock, round, difficulty (§6). |
| `events` | `/api/runtime/json/events` | `readEventsState` / `writeEventsState` | Timeline of AI/scenario events, each with `impacts`. |
| `actions` | `/api/runtime/json/actions` | `readActionsState` / `writeActionsState` | Player/queued orders awaiting the next jump. |
| `chat` | `/api/runtime/json/chat` | `readChatsState` / `writeChatsState` | Diplomacy conversation threads. |
| `colors` | `/api/runtime/json/colors` | plain `writeJson(JSON_URLS.colors, …)` / `getNationColors` (`assets.js`) | `code → [r,g,b]` palette (sibling of `world`, not inside it). |
| `flags` | `/api/runtime/json/flags` | `getNationFlags` (`assets.js`) | Author flags `code → PNG data URL`. |
| `tags` | `/api/runtime/json/tags` | `getNationTags` (`assets.js`) | Author STARTING country tags (§10). |
| `regionsGeojson` / `citiesGeojson` | `/api/runtime/json/regionsGeojson` … | via `loadRegionCatalog` (`assets.js`) | Custom drawn geometry (never value-cached, see `isNoStoreJsonUrl`). |

`readGameStateBundle` (`src/runtime/gameState.js`) reads `actions`, `chats`, `events`, `game`, `world` in one `Promise.all` and is the standard "load everything" entry point. `viewAsSeen` turns such a bundle into the campaign **as the player has been shown it** while a skip is being revealed — for whatever speaks to the player; it is never written back (see [what the player has not been shown yet](ai-overview.md#what-the-player-has-not-been-shown-yet)).

A chat message a turn wrote — a note an event sent, a letter a document became — carries `eventId`, the event whose reveal shows it, and so does its entry in the thread's log. Which of the newest skip's events are still unseen is kept on the device (localStorage `oh_unseen_turn_events`, `runtime/unseenEvents.js`), not in the save: it is the player's progress through the record, not part of the record.

### Games vs scenarios

The same asset keys are served from two different server roots (`src/runtime/library.js`):

- **Scenarios** — `/api/scenarios/*`. The immutable authored seed (WWII preset, a hub download, an editor export). `world.json` here is the STARTING position produced by the editor (`src/Editor/exportPreset.js`).
- **Games** — `/api/games/*`. A live playthrough. Selecting a scenario spawns a game whose `world.json` starts as a copy of the scenario's and is then mutated in place by every jump.

Only a **game's** `world.json` is written during play; the scenario copy stays pristine so the same scenario can seed many games. `setRuntimeAssetEndpoints` points `JSON_URLS.*` at whichever is active (the runtime token encodes it). `saveGame` in `src/Game/GameUI/libraryBar.jsx` writes `world` **whole** (never a shallow `worldPatch`, which would drop `polityOverrides`/`ownerCodes`/`regionOwnershipOverrides` and wipe the map).

## 2. `world.json` shape — field table

`WORLD_DEFAULTS` (`src/runtime/gameState.js`) is the authoritative default object; `normalizeWorldState` spreads `{...WORLD_DEFAULTS,...world }` and then re-derives the structured fields. Anything **not** in `WORLD_DEFAULTS` (e.g. `customRegions`, `basemap`, `ownerCodes`) passes through untouched from the stored document — these are scenario-authored or game-appended fields the normalizer never rewrites.

### 2a. Core political-map fields

| Field | Type | Default | Meaning / data flow |
|---|---|---|---|
| `regionOwnershipOverrides` | `{ regionId: ownerCode }` | `{}` | THE re-ownership map: which polity owns each region above the base tiles. Written by AI `regionTransfers` (§8) and by cheats. Read by the Nations layer to paint fills, and by `isPolityLandless`. Normalized to string→string, blanks dropped. |
| `polityOverrides` | `{ name: {code,name,aliases[],formerNames?[],color,note,status?,mapRefs?{gadm0[]},mapLabel?,mapDistinctLabel?,verbatim?} }` | `{}` | Declared/renamed polities: new countries, renames, colors, alt-names. **A polity is keyed by its name and `name` equals the key; a rename re-keys the country everywhere** (`server/polityRename.js` `renamePolityInWorld`, reached from an event's `polityChanges` — a `rename`, or an `update` carrying a new `name` — and from the Workshop) with the old name kept in `formerNames`, which `buildOwnerAliasMap` folds onto the country and `resolveCountryTags` uses to find the scenario's starting tags. In every map keyed by names (colours, flags, stats, tags, reputation, intelligence, the standing goal) the country's own value moves to the new name and anything already under it is dropped: no other polity may hold that name, so it is a leftover, such as an unused stock-palette colour, and it must not repaint or restate the renamed country. A save whose record still shows a display name over a different key is re-keyed on its next apply (`displayNameMigrations`), except onto a real country's name that was never its own. Written by AI `polityChanges` and the editor. `enqueueContentStrings` translates names on write. Normalized by `normalizePolityOverride`. Feeds `loadCountryNames` (`assets.js`) and every name/flag resolver. |
| `regionClaimants` | `{ regionId: string[] }` (≤4) | `{}` | Marks a region DISPUTED — striped in the administrator's + claimants' colors. World-data equivalent of a `claimants` list on the geojson feature, and WINS over feature props. Normalized (sliced to 4). Sparse: a row only while a region is disputed. |
| `groups` | `{ [name]: { name, description, color, formerNames?[] } }` (≤64) | `{}` | **Groups** (`src/runtime/groups.js`): actors that are not countries — a terrorist organisation, a cartel, a militia, a zombie outbreak — keyed by exact name like polities. `description` is what the AI is told the group is (≤1,200 chars); `color` is the `#rrggbb` tint of its area (a palette colour hashed from the name when none is given). A group may take one of its own former names back (`canRenameGroup`); a rename onto another group's name, current or former, is refused. **The player may lead one** (the picker's **Play as a group**): the game's polity is then a landless polity and a group of the same exact name (`playerGroupKey`; never a former name). The two stay one actor — renaming the polity re-keys the group and its area (`renameGroupKey`, `server/polityRename.js`), a `groupOps` `newName` on it goes through `renamePolityInWorld` so the game's polity follows (`renamedPolities`), and the model's `dissolve` of it is refused (a `release` still takes its area). |
| `groupAreas` | `{ [regionId]: groupName }` | `{}` | Which group CONTROLS each region: sparse, one group per region, a row naming no group is dropped. The region stays its owner's — the map outlines each group's whole area in its colour and tints it lightly (`GroupAreaLayers.jsx`, cut from the frontier topology by `vnext/groupAreas.js`), and the region card says **Group control**. |
| `regionTypes` | `[{ id, name, overrideColor, opacity, unownedOpacity, strokeColor, strokeWidth, strokeOpacity, zoomSettings, pathfindingSpeed, passable, interactable, ... }]` | *(pass-through; absent before)* | The scenario's region types, as the Workshop's Region Types panel keeps them (map-editor.md §8). Each region names its type by `typeId` in the regions file. The map draws a type's colour, opacity, border and zoom band where they differ from the default Land, and the unit and structure directors are told its rules for moving and placing (`src/runtime/regionTypes.js`). A template world key: a new game copies it from the scenario. |
| `settledRegionClaims` | `string[]` (region ids) | `[]` | Regions whose dispute the world has ended — a claim dropped, a contest cleared, a clean hand-over (`settleRegionClaims` in `gameState.js`). A region disputed again leaves the list; normalized unique, never one with a live row. |
| `regionSovereigntyOverrides` | `{ regionId: ownerCode }` | `{}` | The LEGAL sovereign of a region where it differs from the polity in `regionOwnershipOverrides` that administers it — an occupation, a displaced government's homeland. | `customRegions` | `boolean` | *(pass-through)* | When true, render political fills/borders/labels from the scenario's `regions.geojson` instead of the stock modern overlay. | `customCities` | `boolean` | *(pass-through)* | Render authored cities instead of the modern city set (`exportPreset.js`). Surfaced by `useWorldState`. |
| `basemap` | `string \| null` | *(pass-through)* | ESRI basemap preset id (`ESRI_BASEMAPS`, `assets.js`); falls back to `ocean` in-game. |

### 2b-bis. Canonical ledgers — wars, relations, agreements, storylines

Three engine-owned arrays carry the political facts the simulation used to keep only as prose. The AI never writes them directly: a jump payload carries compact text lines (`warUpdates`, `relationUpdates`, `agreementUpdates` — see ai-schemas.md §4.7) that `src/Game/AI/nativeWarLedger.js` and `src/Game/AI/nativeDiplomaticDirector.js` validate against the current world, bind to the event that caused them, and fold in once per turn (`applySimulationResult`).

| Field | Shape | Notes |
|---|---|---|
| `wars` | `[{ id, title, status, sideA[], sideB[], startedDate, endedDate, lastUpdatedDate, cause, note, sourceEventIds[], createdRound, updatedRound }]` | `status` ∈ active / ceasefire / ended. **The only source of belligerency** (the game itself enters in it those bound to defend a country that is attacked, and ends a war on terms: § war weariness, alliances and peace)**:** an event that narrates battlefield combat must carry `warId` and `combatants` naming polities from both sides of an *active* war, or the segment is rejected (on the final attempt the combat event is kept as narrative and loses its `warId` and `combatants` instead). Renewed fighting between a *ceasefire* war's own sides resumes it, whether or not the event carries that war's `warId`: when the answer has no record for the war, the engine adds the `resume` record itself (`reconcileCombatWarState`). Transitions are explicit: start, join-a, join-b, leave, ceasefire, resume, end. `title` is the name the start record's note gave the war (`Title: <name>;`), or "A–B War" without one; `cause` is the rest of that note. The Stats panel's Current conflicts card (stats.jsx) shows the title, the start date (read through `formatGameDateReadable`, BC spelled out), the other polities on the country's own side and the cause (hiding the engine's own bootstrap note), and a link that opens the Events panel on the war's first event it still keeps (`warTimelineEventId`, `turnReveal.js`; *See how it began on the timeline*, or *See it on the timeline* once the opening turn has aged out of the kept twelve, or the opening events out of the war's newest 24 ids (`warTimelineEventOpensWar`: the first id kept counts as the opening only on the turn whose round is the war's `createdRound`); no link when none of its events is kept). The prompts read the ledger as `canonicalWarContext` (`buildCanonicalWarContext`, `nativeWarLedger.js`): every active and ceasefire war, then the wars that ended in the last two rounds (`updatedRound`), at most five, one `ENDED <date>` line each, so the model knows the fighting stopped. |

### 2b-ter. Political actors, pressures and power

Four more fields make up the Political World: who governs each polity and how its domestic politics move (`politicalActors`, with its clock `politicalSimulation`), how much each polity counts (`powerStatus`), and the international organisations it belongs to (`institutions`). `politicalActors`, `powerStatus` and `institutions`, with `agreements` (§2b-bis) and `canonContext`, are the five fields of a scenario's **Politics** (`POLITICS_FIELDS`, `src/runtime/scenarioChanges.js`; the clock is campaign state and not among them): what the Workshop's Politics tab generates, and what a suggested change to a community scenario is reviewed against, one country or one institution at a time ([game UI](game-ui.md)). `normalizeWorldState` normalizes all four on every apply. All are keyed by exact polity name, like the rest of the world.

| Field | Shape | Notes |
|---|---|---|
| `politicalActors` | `{ schemaVersion: 6, byPolity: { [polity]: actor } }` | `normalizePoliticalActors` (`src/runtime/politicalActors.js`). **The pipeline: pressure → response → disposition.** Every actor carries three layers of hidden state, each derived from the one before:

- **`politicalPressures`** { `updatedAt`, `issues`: { [issue]: { `salience` 0–100, `lean` −100..100, `strain` 0–100, `persistence`, `momentum`, `recentSources[]` ≤ 4 } } } (`src/runtime/politicalPressure.js`). At most 24 issues; `POLITICAL_PRESSURE_AXES` names the usual ones (immigration, sovereignty, security, economic_stress, cost_of_living, unemployment, war_weariness and others) without limiting them. `persistence` is the share an issue keeps each month (0.72 by default), so a pressure the world stops feeding fades. The world feeds it through `derivePoliticalStructuralSignals` (`src/runtime/politicalStructuralPressure.js`), which reads only canonical ledgers: the Stats history (economic stress, cost of living, unemployment, institutional trust), relations at −40 or worse (security), active wars (security, and war weariness once a war is 90 days old), and group areas inside a polity's land (`groupAreas`: regionalism and security; none while the Groups feature is switched off, the `groups` option).
- **Response.** Each party and bloc has a hidden `politicalResponse` profile — `organization`, `credibility`, `inertia`, `resilience`, and per-issue `position`, `sensitivity` and `strainResponse` — that says how it gains or loses under each pressure (`src/runtime/politicalResponse.js`). One response tick is one month: party support or influence and bloc influence move by at most 2.5 points a tick and sustained strain hurts governing parties most.
- **`behavioralDisposition`**: eight 0–100 dimensions — assertiveness, riskTolerance, escalationPressure, compromisePressure, regimeVulnerability, deterrenceSensitivity, opportunityPerception, threatPerception — composed from the structured inputs above, never from ideology or goal prose (`src/runtime/politicalDisposition.js`). The political decision context (below) shows it to the model in words.

**Who writes what.**

| Writer | Writes | Path |
|---|---|---|
| Political World generation (Workshop → Politics) | actors (only the fields in `GENERATED_ACTOR_FIELDS`), institutions, agreements, the starting `powerStatus` | Per polity, a proposal is validated by `validatePoliticalGenerationProposal` (`src/runtime/politicalWorldGeneration.js`) and merged **fill-missing**: a generated value never overwrites one already there. Each field it fills is stamped in the actor's `generationProvenance.byPath` (source `generated`, the scenario date, the depth, a confidence). Institutions come in through `applyInstitutionUpdates`, power baselines through `seedPowerBaselineScore` and a round-zero `refreshPowerStatus(…, { immediate: true })`. Applying then derives every disposition once (`initializePoliticalDispositionsForWorld`). |
| The AI during play — a time skip's events and the Game Master | actors, through `impacts.politicalActorOps` on the event that causes the change: replace-leader, set-government, set-political-system, form/leave-coalition, create/update-party, set-party-support/influence/leader, create/update-power-bloc, set-power-bloc-influence, set-strategy, set-traits, set-perceptions, remove-perception (`src/runtime/politicalActorOps.js`); institutions, through `impacts.institutionLifecycleOps` and institution group chats | `validateGeneratedWorldChanges` (`gameplay.js`) checks each op's shape with `allowNativeDerived: false`; `applyEventImpactsToWorld` applies it (`applyPoliticalActorOperation`). **A government already at the table may rise** (`institutionAccessionStanding` in `src/runtime/institutionLifecycleCore.js`). An observer, a candidate, a participant or an associate is an entry in `members` like a full member, with a lower `status`; the standings rank observer < candidate < participant < associate < member (`institutionStandingRank`). An invitation to, or an application by, a polity that is represented BELOW the status asked for opens the same accession the charter prescribes for an outsider (a lifecycle case; a ballot of the eligible voters under `approval`, at once under `direct`; refused where accession is `not-permitted` or the charter does not admit that status), and when it is settled `applyInstitutionMembershipResolution` changes that entry's `status` and keeps its `sinceDate`: there is never a second entry, and the history records `joined` with the new status. Both used to refuse anyone found in `members` ("already represented"), so an observer could never be invited to full membership or ask for it (issue 849). Still refused, for the player, for a model's `institutionLifecycleOps` and for the Game Master alike, since all three go through `applyInstitutionLifecycleCommandCore`: the status already held or a lower one, which covers anything offered to a full member (`<polity> is already represented in <institution>.`); a suspended member, whose way back is a reinstatement motion (`<polity> is suspended from <institution>.`); and an answer to an invitation that asks for what its government already holds (an observer invited to membership that would rather stay one declines). An expelled polity is no longer in `members` and is invited or applies as any outsider does, as before.

In the Institutions workspace (`InstitutionsWorkspace.jsx`, Members tab) the invitation picker lists every government not represented and every one represented below the status on offer (`institutionInvitablePolities`), the second kind first and each marked with the status it holds (Observer, Candidate, Participant, Associate); the status offered is Member or any of observer, participant and associate the charter admits. A player whose own government is represented below full membership has **Request membership** there (`institutionMayRequestMembership`), which is the ordinary application.

**What the AI may not write.** `politicalPressures` and `behavioralDisposition` are derived state. A generation proposal that carries either is rejected (`FORBIDDEN_GENERATED_FIELDS`), and `set-political-pressures` / `set-behavioral-disposition` from a skip's events or the Game Master are refused as native-derived; the Game Master's prompt says never to emit them.

**Per turn.** After a skip's events have been applied (each event's `politicalActorOps` in `applyEventImpactsToWorld`, then each event's institution lifecycle ops), `applySimulationResult` (`gameplay.js`), with no AI request of its own:

1. refreshes tracked Stats if they are due (the one step here that may cost a request, and only when Stats tracking is on and due);
2. resolves dated institution lifecycle effects, such as a withdrawal whose notice period has run out (`advanceInstitutionLifecycleCore`);
3. advances the political background (`advancePoliticalBackgroundSimulation`, `src/runtime/politicalBackground.js`);
4. records the Stats history.

The background step plans from the clock (`buildPoliticalClockPlan`): the elapsed time runs from `lastProcessedDate`, or the turn's start when the clock is unset, to the new game date; every whole month is one response tick, the fraction carries over in `responseRemainderMonths`, and at most 24 ticks run per advance (the rest are dropped). It derives the structural signals, then runs pressure, the response ticks and disposition in a module worker (`politicalBackgroundWorker.js` through `politicalBackgroundClient.js`, the pure kernel in `politicalBackgroundKernel.js`) on a detached copy, and commits only the final values: pressures, then responses, then dispositions, then the clock. **What the clock guarantees:** each stage commits whole or not at all, and a failed commit, a missing worker or a worker error leaves both the political state and the clock as they were, so the next turn catches up over the whole gap. There is deliberately no main-thread fallback. The clock reads only `YYYY-MM-DD` dates with a year from 1 to 9999: a BC or free-text game date does not advance it.

`powerStatus` is normalized on every apply, but in this tree `refreshPowerStatus` runs only when the Political World is generated. No turn step refreshes it, so the hysteresis it implements — a tier change needs two successive rounds pointing at the new tier, and demotion thresholds sit below promotion ones (a major power drops below 55, a regional power below 35) — does not run during a campaign. The continuous scores the model sees are recomputed on read (`powerDecisionProfileForPolity`).

**Generation modes and depths.** The Politics tab offers three modes (`POLITICAL_WORLD_GENERATION_MODES`, `src/runtime/politicalWorldGenerationReview.js`), which set a depth per polity (`buildScenarioPoliticalRelevance`): the player's polity and every active belligerent are always `full`; **simulation-ready** makes every other sovereign polity `rich`; **balanced** makes `rich` those that already have an actor or take part in an active puppet relationship; everything else is `standard`, and a non-sovereign polity `minimal`. The depth decides what a proposal must supply (`assessPoliticalGenerationNeeds`): every depth needs the political system, the governing structure, the parties or blocs that represent it and their starting shares (a generated electoral roster must name at least 75% of the vote); richer depths add leadership traits, response profiles, strategic context, perceptions and domestic context.

**The Politics review path.** Generation writes nothing straight into the scenario. The panel (`PoliticalWorldGenerationPanel.jsx`) lists each polity's proposal for review; applying re-validates every selected one (`applyReviewedPoliticalGeneration`) and refuses the lot if any fails. The staged generator (`src/Game/AI/politicalWorldV2/`) keeps its work in a checkpoint and applies only when the checkpoint has reached canonical quality and the scenario's canon has not changed since generation began (`buildPoliticalWorldInputFingerprint`); otherwise it asks for a fresh run rather than overwrite the author's edits. A checkpoint also has a lifetime ceiling of AI calls (100, `totalModelCallCeiling`). A run that stops there offers three ways on: **Allow more AI calls** raises the ceiling by 25 (recorded in `ceilingGrants`); **Discard checkpoint** throws the run away; **Apply what is complete** (`applyCompletePoliticalWorldV2Work`) writes only the finished work. A polity counts as finished once its actor, governing alignment and power record are accepted, plus its exact-date check where the scenario needs one. The institutions, their members and the standing agreements count only once the whole layer is done. Every other polity keeps what the author has. The checkpoint is then re-keyed to the scenario as saved (`recordPoliticalWorldV2PartialApply`, logged in `partialApplications`), so Resume and the final Apply carry on with the rest. Each applied polity keeps the depth it was built at (`depthByPolity` in that log), because in balanced mode the actor now in the scenario would otherwise make it `rich` and Resume would rebuild it. A suggested change to a community scenario diffs the same five `POLITICS_FIELDS` entry by entry.

**Who reads it.** The model sees an actor through the political decision context (`buildPoliticalDecisionContext` / `buildBoundedPoliticalDecisionContextSet`, `src/Game/AI/politicalDecisionContext.js`): the actor's own government, parties, pressures, disposition and power profile, and what it knows of its counterpart through political knowledge. The time skip carries it in its user message (see [AI prompts](ai-prompts.md)), and the Game Master, the advisor and diplomacy have their own. The Country panel's political view reads it through `src/runtime/politicalPresentation.js` (`PoliticalOverview.jsx`); what one power knows of another's politics goes through `src/runtime/politicalKnowledge.js`.

`Unit` enums (–): `type ∈ {infantry,armor,air,naval,artillery,garrison}` (default `infantry`); `status ∈ {idle,moving,engaged,defeated,pending}` (default `idle`; `pending` = a player deploy awaiting AI resolution, rendered translucent); `source ∈ {player,ai,scenario}` (default `scenario`; `scenario` = placed in the map editor's Units panel, map-editor.md §9b); `posture ∈ {holding,massing,patrol,transit,exercise,blockade,withdrawing,assaulting}` (default `""` — intent, as distinct from lifecycle `status`; deliberately not `garrison`, which would collide with the unit *type*). **`assaulting` is the one posture that also moves the lifecycle**: a unit *arriving* under it is stamped `status: "engaged"` rather than `idle` (`applyUnitOpBatch`). It exists so a province assault can be expressed at all: the unit card deliberately has no direct-control buttons ("intent, not control"), so a typed order like "Attack Provence" is something the *model* enacts, through this posture. The AI still owns the outcome (casualties, and a `regionTransfer` only if the province actually falls); `engaged` is additionally exempt from `enforceUnitVolume` pruning, which is right for a formation in contact. `strength` is a **percentage of established strength**, clamped to `[0,100]` by `clampUnitStrength`, which coerces the old 1–1000 scale by dividing anything over 100 by ten. `composition` is free text for the order of battle ("1 aircraft carrier, 2 frigates"); `covert` is engine-assigned and means "no confirmed line of support" (a covert insertion **or** a presence only just detected), shown to the player as *Unconfirmed*; `eventId` links the event that created or last moved the unit. `marker.kind` is free-form (lowercased for stable styling), default `landmark`. `PendingUnitOrder.kind ∈ {move,patrol}` (default `move`; a legacy `attack` is coerced to `move`, keeping its destination and `targetLabel`).

### 2e-bis. Projects & operations (ride inside world state)

| Field | Type | Default | Element shape (normalizer) |
|---|---|---|---|
| `projects` | `Project[]` | `[]` | `normalizeProjectEntry`: `{id,name,kind,ownerCode,summary,status,progress,tags,secrecy,startedAt,targetDate,milestones,nextMilestone,lastUpdate,eventIds,linkedUnitIds,linkedMarkerIds,linkedSpyIds,verification,focus,note,createdAt,updatedAt,updatedRound}`. |

The **Projects & Operations board**: long-running efforts that span rounds — research and industrial programmes, construction projects, military and covert operations, sustained political campaigns. Deliberately distinct from the actions queue, which holds one round's orders and is resolved by the next jump.

A milestone may carry `repeat` (`weekly|monthly|quarterly|annual|biennial`) for a **standing commitment that comes round again** — an annual drill, a quarterly review. Marking one `done` does not retire it: `applyProjectOps` advances the date by one interval and sets it `pending` again, bumping `completedCount` and stamping `lastCompletedAt`. It rolls from the milestone's OWN date, not from the day it was ticked off, so an annual drill on 1 June stays on 1 June instead of drifting; a commitment missed for several cycles advances as many times as it takes to get ahead of the clock. Month-ends clamp (the 31st becomes the 28th in February) and recover afterwards. A skipped occurrence is deliberately **not** auto-rolled — it stays pending and flags `milestoneMissed`, because a drill nobody ran is exactly what the board should show.

`ongoing: true` marks a **standing effort with no planned end** — a permanent patrol, a continuous intelligence programme. It forces `targetDate` to `""` and can never be overdue, which is the point: without it the model invents an end date for something meant to continue, and the board then cries wolf the day that date passes. Distinct from merely having no `targetDate` yet, which is what an undated new entry looks like.

`kind ∈ {project, operation}` (default `project`); `status ∈ {proposed,active,stalled,paused,complete,failed,cancelled}` (default `active`; the still-running subset is exported as `PROJECT_OPEN_STATUSES`); `secrecy ∈ {public,restricted,covert}`. `tags` reuses `normalizeTagList` (`countryTags.js`) so the 8×32 caps and case-insensitive dedupe are shared with country tags. `ownerCode` is a country **NAME**, verbatim — same namespace as units and markers — and **blank means the player**, so the model is never made to restate the player's own country on every entry (a field it has to repeat is a field it eventually gets wrong). `nextMilestone` is **re-derived** from `milestones` on every normalize (earliest dated `pending` wins) rather than trusted: the model is given both and drifts them apart the moment it marks one done without restating the other.

Capped at **120 projects**, 8 milestones each and 12 `eventIds` each — sized against a real campaign (a forty-round game came back with 44 live projects) rather than guessed. One project measures ~1-1.4 KB, of which milestones are ~39%, so a full board costs ~160 KB against a `world.json` whose `startingTimelineText` and `consolidatedHistory` are already ~105 KB each. Going over the cap evicts **finished work first** (oldest by `updatedAt`), and only then the least recently touched live work — `.slice(0, N)` would have dropped whatever happened to be last, which is live work as often as not. The panel shows the count and warns within 10 of the limit, so this is never the first the player hears of it.

If a board ever genuinely needs more than this, the answer is not a bigger number: it is moving `projects` out to its own runtime asset. That is real work, because rollback snapshots and the staged event reveal both get `world.projects` for free today purely by riding inside world state.

**The player cannot author a project's content.** Only two things write what a project *is*: events, via `impacts.projectOps` (§5) — which since the board moved out of the jump are produced by the dedicated `projects` task and attached back onto the events that caused them — and the advisor, via its ```` ```projects ```` block. The player owns exactly two fields, from the panel itself: `priority` (`high|normal|low` — how much attention they want it to get, which the jump and advisor directives then act on) and abandoning it, which goes through the ordinary `cancel` op so the entry stays under Closed with the progress it actually reached. Both route through `applyProjectOpsToWorld`, the same door the advisor uses, so they stamp `updatedAt`/`updatedRound` and close out dangling milestones like any other write. `eventIds` is stamped by `applyProjectOps` from the causing event, which is what builds the per-project activity feed without the model having to maintain it.

**The board reads every Canonical event, not just the timeline.** The timeline cleanup (the integrity screen's routine and low-value rules, the curator's redundancy, filler and churn routes) decides what is *worth showing*, and keeps routine patrol, reconnaissance and administrative follow-up off the timeline. Those are Hidden events (see the Glossary): they still happened, and routine progress is exactly what moves a standing Operation or records a stall. So the board pass reads them too, and a Board entry can move without a timeline card. Its `lastUpdate` carries the explanation, and its activity feed stays a list of timeline events: a Hidden event is never stamped into `eventIds`. Only events judged untrue (rejected) and exact duplicates are withheld from the board. The same separation keeps a Project off the Storylines ledger: one polity's deliberate effort is a Board entry, a Storyline is a situation nobody controls, and the jump is told that one may cause the other but a thing is never both (ai-prompts.md §7.12c, §7.17).

**HIGH PRIORITY buys an assessment, not motion.** Every jump, each of the player's open HIGH PRIORITY entries gets an explicit assessment, and "no material change this period, because…" is a valid one. The earlier rule that such an entry "must not sit on the list two jumps running" forbade that honest answer and so invited invented progress. An entry the board pass leaves unassessed is named in the turn log, never retried.

Everything date-derived — overdue, due-soon, a slipped milestone, a programme untouched for several rounds — is **not stored**. It is computed from the game clock by `src/runtime/projects.js` (import-free, unit-tested in a bare checkout), so it cannot go stale between AI turns. That split is the point of the feature: the model owns what only it can know, the calendar owns the rest.

Not in `TEMPLATE_WORLD_OVERRIDE_KEYS`, deliberately — `buildFreshWorldSeedFromScenario` carries *authored settings* across, and projects are play state. (`units` *is* in the list since the map editor gained a Units panel: a scenario's authored starting formations carry into every game made from it — map-editor.md §9b. So, since 2026-09-25, are `markers`, `puppets`, `groups` and `groupAreas`, which the Workshop now authors too: a scenario's structures, puppet states and groups reach every game made from it, even one that was played in place. And `seas`, a scenario map's own named seas for placing fleets — `[{ "name", "aliases", "point": [lng, lat] }]`, see ai-overview.md, placing things by name.)

#### Espionage on the board

`linkedSpyIds` ties a covert operation to the agent it is actually running. The split is deliberate: the **engine** owns whether such an entry exists and whether it has ended (`spyOperationOps` in `projects.js`, called from the turn and from the Spy tab, so the two cannot disagree), and the **model** owns the story — progress, milestones, `lastUpdate` — because once the entry exists it is an ordinary board entry. The field is engine-written only: it is absent from `projectSchema`, so a strict provider cannot emit it, and absent from `PROJECT_PATCHABLE_FIELDS`, so no update can rewrite the link.

Three cases are deliberately left alone. A `turned` agent changes nothing — the player is never told, and an entry that closed itself would say so louder than any message. A `suspected` one is left alone too, because the model is free to set it back to active on the next jump and the two would flip-flop; the Spy tab already flags it. And another polity's agent inside the player is not the player's programme.

Espionage also reaches the board **through the events it produces**: `resolveEspionage` runs inside `applySimulationResult`, and the `projects` task now runs there too, after it — so an exposure can stall the operation it belonged to on the same turn rather than a turn later. The `projects` task additionally receives the `[Espionage]` brief (framed for the board rather than the simulator), which is the one source that can put a **rival's** programme on the board as a foreign entry.

#### Doubting what a spy told you

A turned agent feeds planted material and the board opens a foreign entry from it. That is the deception working. What makes it a mechanic rather than noise is that it ends, and that settling it is a **move the player makes**.

`verification` runs `"" → doubted → confirmed | refuted`, and ownership is split:

- `spyProvenanceOps` ties a foreign entry to the agent that must have produced it (the brief is the only channel that puts a rival's programme on the board), stamping `linkedSpyIds`. Retroactive on purpose, so entries opened before this existed still get linked.
- `spyIntelDoubtOps` stamps **`doubted`** when that agent is `suspected`, or `exposed` after having been turned (it has a `turnedAt`) — the analysts' own warning, the same flag the Spy tab shows, not proof. Cast once per entry, so a later verdict is never overwritten. A turned agent nobody suspects yet casts no doubt, and the wording never says an agent was turned: the player is not told, so the board is not either.
- `doubtedAwaitingFreshSource` lists doubted entries the player now has a **clean** agent for — not the one that caused the doubt, and not a suspected replacement. That list is handed to the `projects` task, because whether a fresh source bears on an entry is a fact about world state, not something readable from board text.
- **`confirmed` and `refuted` are the model's**, through an ordinary op. `projectSchema` offers only those two, so no model can cast doubt on the board itself — only settle one already cast.

The engine never decides whether a programme was real; that is fiction, and only the model has it. It decides only *whether the question can honestly be asked yet*.

> `linkedSpyIds` and `verification` are both in `PROJECT_PATCHABLE_FIELDS` because the engine sets them through ordinary update ops. The protection is `projectSchema`, which omits `linkedSpyIds` entirely and restricts `verification` to the two verdicts: **the schema decides what a model can say, the whitelist only decides what an op can carry.**

`world.intelligence` is reachable from the board rather than only from a bare `polityChange`: a sustained build-up belongs in a programme whose `onComplete.polityChanges` carries the new rating, so it lands when the work finishes and can be funded, watched, or wrecked first. A sudden shock — a purge, a defector, a ring rolled up — still changes it directly. `onComplete` releases on completion only, never on a cancel or a fail, so abandoning the programme delivers nothing.

### 2e-ter. Espionage (rides inside world state, except the intercepts)

| Field | Type | Default | Element shape (normalizer) |
|---|---|---|---|
| `intelligence` | `{[polity]: number}` | `{}` | Per-polity service capability 0-100, clamped and rounded. Absent means `DEFAULT_INTELLIGENCE` (40) — "ordinary", not "none". |
| `spies` | `Spy[]` | `[]` | `normalizeSpy`: `{id,owner,target,deployedAt,status,turnedAt,exposedAt,coverStory,suspected}`. The Spy tab deploys and recalls by hand; a jump event's `impacts.spyOps` does the same for the player's queued orders (`spycraft.js applySpyOps`, same rules, skipped orders logged). |
| `spySeal` | `string` | `""` | 64 hex chars, validated `/^[0-9a-f]{64}$/i`; blanked if malformed. |

`intelligence` is keyed by country **NAME**, verbatim — the same namespace as `internationalReputation`, `polityOverrides` and `countryTags` — and moves exactly like reputation: the AI sets it through `polityChanges.intelligence` (0-100), applied in `applyPolityAndTerritoryImpacts` against the **alias-resolved** owner key, so a polity the model names by an alias cannot end up with two split ratings. It decides how much of others' diplomacy a polity can read and how much of its own it can keep secret. Rendered by the Stats tab's 🕵 card, never part of the AI-written stat sheet. A service nobody has rated gets a **first reading** the moment it matters — the Stats pane opens on that polity, an agent is sent there, one of its intercepts is read, one of its agents is caught, an order deploys an agent there — through the `intelligenceAssessment` task (`gameplay.js assessIntelligenceService`, 0-100 with a rationale), written here only while the key is still absent; the turn owns the number after that. The same triggers give the polity its stat sheet if it has none (`ensureCountryStatSheet`), and the Stats pane now generates the sheet on any sub-tab rather than only on Economy. Both readings, and the Stats pane's own sheet, wait for a running turn before asking the model and again before writing — a sheet's write then holds the simulation lock (`beginStatsWrite`) — and write nothing into a save the player switched to while the model was answering. A background first reading of a polity with neither asks for both in the sheet's one request (`ensureCountryAssessed`): the stat-sheet tool carries the assessment's fields last (`withIntelligenceRating`, `intelligenceService`, a transport field taken off before the sheet is validated), and the rating is written after the sheet, under the same re-check (`storeFirstIntelligenceRating`). An answer without a usable rating falls back to the standalone assessment. The Stats pane's own reading, and a polity that already has a sheet, keep the standalone request.

`Spy.status ∈ {active, discovered, turned, exposed, recalled}`. `active` is in place and reporting; `discovered` was caught by the target and is waiting on the **player's** decision (it reports nothing meanwhile); `turned` is a double agent whose owner is not told — the target writes what it "reports"; `exposed` and `recalled` are terminal. `owner: ""` is a pre-ownership record and means the player's. Caps: `MAX_ACTIVE_SPIES` 3 per owner, `MAX_FOREIGN_SPIES` 3 inside the player at once.

**The intercepts are NOT in world state.** They live in their own runtime-only JSON asset (`storage/intercepts.json`, `readInterceptsState` / `writeInterceptsState`), because they are refreshed *after* the jump's world write and a second world writer would race it. Those post-commit writes (each agent's report, the stolen documents, the advisor's notices of them) carry the campaign the turn was generated for and stop once another save is open, so a player who switches saves while the agents report never gets this campaign's reports filed into the other one. Shape: `{[targetPolity]: {gatheredAt, round, planted, exchanges}}`, where an exchange is `{id, counterpart, date, subject, messages, eventId?}` (`eventId` only on a stolen document's copy: the event whose reveal shows it, see [what the player has not been shown yet](ai-overview.md#what-the-player-has-not-been-shown-yet)) and a message is `{speaker, text}` **or** `{speaker, cipher}` — never both. A turn's restore point keeps this file as it stood before the turn filed anything into it (`snapshot.state.intercepts`), so an undo or an Intervene takes the turn's reports and stolen copies back with it; restoring a snapshot captured before that keeps today's file, less every stolen copy whose report the restored world no longer holds as stolen (`reportDelivery.js withoutOrphanedDocuments`, which runs on every restore). At rest it is always `cipher`: `spySeal.js` seals each message with AES-GCM under `world.spySeal` (WebCrypto, or the byte-identical pure-JS `aesGcm.js` where there is no `crypto.subtle`, as in the Android app), opened in exactly two places (the simulator prompt, and the intercept view for as long as it is on screen). `planted: true` marks a report produced while the agent was turned; the file remembers, the player is never told.

This is the one asset in `RUNTIME_ONLY_JSON_ASSET_FILES` whose default is an **object**, which is why the server's write-path shape guard derives `expectsArray` from `JSON_ASSET_DEFAULTS` rather than from registry membership (`server/libraryStore.js`, and `server/runtimeJsonShape.test.js` pins it).

Espionage resolves once per turn in `applySimulationResult`, **after** the standing-order/unit-volume pipeline, so an agent's round is decided against where forces actually ended up. It is deterministic, seeded on `${round}:${key}` with four roll keys — `:detect`, `:turn`, `:suspect`, `:deploy`. **Those key strings are save-compatibility surface**: changing one makes every existing save replay its next round differently. Its events are appended to `freshEvents` *before* `nextEvents` is built, so they persist to the event log.

### 2e-quater. Battlefields: the war room's part, and a scenario's fronts

`world.battlefields[]` (`runtime/fronts/record.js`) is written by the front engine. Three things beside the engine write to a record, all through `runtime/fronts/warRoomOps.js`, and all of it is kept in the record itself:

| Where | What |
|---|---|
| `orders[]` with `chosen: true` | An order for troops picked out, not for a stretch of line: `{ s, sector: "all", order, objective?, way?, by, since, chosen, mark?, attacks? }`. `way` is a route drawn for them, as up to 12 `[lng, lat]` points; they may lie beyond the frame, which grows toward where its troops are sent. `attacks` is written by the engine when it puts a route to its troops: the names of the countries outside the war that the route goes into (see below). `mark` says what wrote it when it was not a hand in the war room: `plan:<project id>` (a Board operation) or `watch` (a side that dug in against a movement it learnt of). An order for a stretch of line never replaces one of these; it ends when its troops have carried it out, are released, have stopped getting anywhere under it (an attack or a route none of whose troops has got 4 km further in 6 days: `battle.js stuckOrders`), or, for an attack, after 120 days. |
| `brief.carry.under[side][troop]` | Which standing order each troop serves (its place in `orders`), or -1. |
| `brief.carry.next[side][troop]` | For a troop on a route drawn for it: which of the route's points it is making for, or -1. The next run sends it on from there (a route may cross itself, so the place nearest the troop is no guide). Left out when nobody is on a route. |
| `brief.carry.ages[order]` | How many days of fighting each standing order has stood. 0 is an order nobody has begun to carry out: a plan. |
| `brief.told` | `true` when the story of the run that left the record was written knowing how it went (see below). Absent, the next skip tells that run with its own period. |
| `brief.carry.command[side][troop]`, `.generals[side][command]` | Which general each troop is under, and what the generals are called. A record never shared out is shared out on read by the engine's own rule (`command.js`). |
| `brief.carry.talk[side]` | The last 40 lines said in that side's war room: `{ who: "" (the commander) \| command, text, at }`. |
| `brief.carry.plans[side]` | Kept plans (`plans.js`): a diversion `{ id, kind: "diversion", way, troops, at }`, and what the player changed of a Board operation's arrow `{ id: "project:<id>", kind: "project", project, way?, off?, sent? }`. Every other planned movement is worked out from the orders and the Board when it is wanted. A diversion is dropped by the engine at the end of a run that fought at least a day (`battle.js plansKept`). |

In a shared game a side's chosen orders, generals, talk and plans are its own: `runtime/fronts/view.js` leaves them out of what the other side is sent, and points `under` into the list of orders each viewer gets.

**A country outside the war comes into it when troops are sent into it** (`runtime/fronts/invade.js`). On a battlefield the land of everybody but its two sides is a wall: no troop walks there and nothing is painted there. A route drawn in the war room that runs at least 30 km (`ROUTE_INTO_KM`) inside such a country is an attack on it, and the engine writes the country's name on the order (`attacks`). Clipping a corner attacks nobody, and nothing a line does by itself ever crosses such a border. On the day the first troop of that order comes within 18 km of the country's land (`INVADE_REACH_KM`), the country joins the war on the side its attackers are not on: it is a member of that side on every battlefield of the war, its land there is ground to be fought over, it raises troops on its own stretch, and the frame grows as the fighting nears its edge (`day.js growIfNeeded`, up to six times). The battlefield's log gets `{ k: "invaded", s, at: "country: X" }` and the run returns `joins: [{ day, date, battlefield, warId, name, side, by }]`. From then on the route attacks nobody new, and the name comes off its order. The turn hands those to the war ledger as `join-a` / `join-b` records dated by `baselineDate` (`frontApply.js frontWarJoins`, merged after the answer's own records in `gameplay.js`), so the ledger says what the battlefields already do whether or not the story wrote it. A record of the story's that names the same country as joining does not move the day: the engine waits for its own troops (so the run that applies a turn is the run that was fought before the story was asked for).

**A war may begin with an attack** (`engine.js attackOpensWar`). A side may send its troops at a country it is not at war with, whoever that is (one a person plays is attacked like any other), and that IS the war beginning. Three things do it: an order to attack on `border: A / B` from one of the two (a border fortified in peace becomes the front as it stands); an order to attack that names no battlefield there is but aims at a place another country holds (`attackAtObjective`: the battlefield that opens takes the order's name; a `land` opens one round the place, where the two do not touch); and a transporter sent in peace to another country's land (it sails with nobody at war with it, so nobody hunts it, and the war begins the day its troops are put down). A war begins between the two, whatever other war either is fighting: the country attacked is at war with whoever attacked it and with nobody else, and who else comes into that war is the story's to say (only a ROUTE drawn through a country outside a war brings it into THAT war, `joins`, above). The run returns the new war in `starts: [{ day, date, warId, attacker, defender }]`, which the turn hands to the war ledger as a `start` record under the id the battlefield already carries (`frontApply.js frontWarStarts`, merged before the joins). A war the story opens itself in the same answer for the same two is taken as THAT war, begun on the day the troops went in, so there is never two. A ceasefire is not broken this way, and nobody attacks its own ally. The battlefield's log says who struck (`{ k: "attacked", s, at: "country: X" }`), and the next period's account tells it. The rule is in the `[Fronts]` block: any country may strike first when the story has it do so.

**A side nobody plays decides for itself** (`runtime/fronts/staff.js`, `engine.js reviewStaff`). Such a side took its orders from the story alone, and held wherever the story gave it none: a front between two countries nobody plays lay still, and an enemy of the player's waited to be attacked. It has a staff now, the engine's own. On a battle's first day of a run and every 10 days after (`STAFF_REVIEW_DAYS`), before the day is fought, the staff weighs what the side's troops are worth against the other side's (strength, kind, supply, the side's quality and what the difficulty gives it) and decides by that and by WHO BEGAN THE WAR (a war's first side):

**What a scenario made a front stands** (`SCENARIO_MARK`, `runtime/fronts/constants.js`). The stance a scenario's author gives each side of a front (hold, dig in, attack: `scenarioFronts.js`) used to be a first-day order and nothing more: a side told only to hold was written no order at all, the story re-ordered every side each period, and the staff sent a side with no order forward at once, so every front played as an offensive whatever its author chose. Every side is now written its order, marked `scenario`, and that order stands until an event changes it: the staff never replaces it (`staff.js staffMayOrder`); an order of the story's to attack is carried out only when it rests on an event of its answer (`frontTurn.js planFrontMoments` marks one that rests on none `unbound`, `orders.js applyOrder` refuses it with the note `posture-stands`); the brief shows it as `(the scenario's)` and the rules say what that means. A person's own order, and any order to hold or dig in, replaces it as before.

**Battlefields are for wars** (`WAR_EFFORTS`, `engine.js seriousAttack`). An order of the story's to attack a country its giver is at peace with begins a war only at effort `major` or `total`, or when the story opens that war in its own ledger in the same answer. With no effort, or `token` or `limited`, it is a border clash: no war, no battlefield, and the note `minor-attack` tells the story to tell it with the formations that fought it (unitOps), as before fronts. A person's own order always begins the war: one given through the skip's function (`given`), and any line for a country a person plays. The rules say all of it (`frontPrompt.js ORDER_LINES`).

**A war begun on a fortified border is fought.** A border fortified in peace becomes the front when a war between its two sides begins (`engine.js adoptStanding`), with both sides dug in or holding as the peace left them: a war in which nobody moved. The orders stop being the scenario's on that day, and the side that began the war attacks along the whole line from its first day (`reviewStaff`, an order marked `staff`), unless a person plays it or the story has ordered it already; the defender stays as it stood.

**Troops of one front sent against the enemy of another go over to its battlefield** (`engine.js handOver`). A country at war with two others fights each on a battlefield of its own, and land one enemy holds is that battlefield's ground and a wall on every other. Troops sent by hand from the first front into such land (to take back their own country's ground, most often) used to bring that enemy into THEIR war as a newcomer: the same ground then lay on two battlefields with two accounts of who held it, the troops fought, and the map went on showing the land as the enemy's. On the day the first of them comes to that land (`INVADE_REACH_KM`) the troops on the route now leave their battlefield and stand, where they are, on the one that enemy is fought on, with the same route (`order.crosses`, read by `markAttacks`; the war room does not warn of an attack on a country outside the war for such a route, `frontApply.js routesIntoOthers`). A named formation goes back to the world there and is taken in by that battlefield when it next begins.

**Half as many troops, and a draft that brings more** (`REINFORCE_ORDER`, `engine.js reinforceOnFront`). A side raises half the counters it did: `TROOPS_PER_STRENGTH` 6 (was 12), a line with room for one every `TROOPS_LINE_KM_EACH` 3 km (was 1.5), `TROOPS_MIN` 3 (was 6). A run's input may carry `troops`, a factor of that (`troops.js troopsFactor`): the game passes none, and the engine's own tests of other things run at 2, the numbers their figures were worked out at (`syntheticMap.js frontInput`). Battlefields already open keep the troops they have. More come by the order `reinforce` (the ledger also reads draft, mobilise, conscription, send reinforcements: `nativeFrontLedger.js`), whose objective field is how many formations, 1 to 60, a quarter of the side's usual number when it says none. They are raised on the side's own ground along the stretch of line the order names, with their reserves, and come under whatever that stretch is told (dug in where it is dug in); the line then evens itself out as it does with any troops. A person's action that drafts or sends reinforcements is such a line for their country, given through the skip's function (`frontOrderFunction.js`) or written for them by the story; a country nobody plays is reinforced only by a line resting on an event (note `reinforce-needs-event`). A side is never brought past 3 times the number its own strength raises nor past twice what its line has room for (note `reinforce-full`). The log's kind is `drafted`, told to the story by date.

**A city beyond a battlefield's edge is a place its troops can be sent at** (`OBJECTIVE_BEYOND_KM`, `engine.js holdObjective`, `day.js growToHold`). A battlefield's places were the cities inside its frame, and the frame is the box round its line: a capital 700 km behind the enemy's front was no place of the battlefield's. The war room's generals were given only that list and told that anything else was not on the battlefield ("Mexico City isn't on our operational maps, Commander"), an order they did take for such a city was dropped when their answer was read, and an order that reached the engine found no objective. Now the generals are also told the cities past the edge and within 1,500 km of it, the ones beyond the other side's ground first, each with how far and which way (`warRoomContext.js placesBeyond`, `describePlaces`; the task's prompt in `defaultPrompts.json`); an order naming one is kept (`readWarRoomAnswer`); and the engine grows the frame toward the city, a step at a time, before it reads the order, whether the order is a moment of the turn or was written onto the record by a general (`begin`). Such growth is not counted among the times a frame may grow after its line. A city further off, or one the map does not have, is still no objective (note `objective-not-found`).

**Recruitment draws on a country's people** (`runtime/fronts/manpower.js`). A formation is so many men by era (`MEN_PER_FORMATION_BY_ERA`: 2,000 / 5,000 / 12,000 / 10,000) and a country can have `MANPOWER_SHARE` (12%) of its population under arms. Every formation raised on a battlefield, every one a draft or reinforcements bring, the troops a transporter raises, and every man its reserves send to make good a loss is drawn from that pool; a side cannot raise more than its members have the men for (`formationsLeft`; a draft that finds none is refused with the note `reinforce-no-men`). The men who come home (a battlefield closing, a country leaving a war or withdrawing from a front) are given back. The run reports the ledger (`result.manpower`: drawn and returned, in men) and the turn takes the difference off the country's `population.total` (`frontApply.js withFrontManpower`): a war costs a country the men it lost. A country whose population nobody knows (no sheet of statistics and no figure from its scenario) is held to nothing and charged nothing; the armies a scenario begins with are part of the population its author gave and are not charged; formations of the world's own that a battlefield took in are not counted either way.

**A country's economy is in its weight in a land war** (`runtime/militaryFunding.js`). `militaryFunding(sheet)` is what it has for its forces in a year, in the sheet's own currency: `MILITARY_GDP_SHARE` (3%) of GDP, more with a budget in surplus, less with one in deficit and with debt past 60% of GDP (`treasuryFactor`, held to 0.6..1.25). `fundingFactor` is what that does to `countryWeight` (`frontTurn.js`): with three or more countries' economies known, its funding a head against the middle of them, to the power 0.25, held to 0.6..1.5; with fewer to compare with, the state of its treasury alone; 1 for a country with no sheet. Nothing asks a model for any of it.

**A scenario's own populations** (`runtime/populationFigure.js`). The Workshop has a field, Population when the scenario begins, for each country (`Editor/PolitiesPanel.jsx`, kept as `world.polityOverrides[name].population`) and each group (`Editor/GroupsPanel.jsx`, `world.groups[name].population`). It reads 12,500,000, 12.5 million or 850k. The game takes that figure for the country's or the group's people until a sheet of statistics says what they are now (`frontTurn.js frontWorldReaders peopleOf`): its troops are raised from them, it weighs in a land war by them (a group no longer by the land it holds alone), and whoever writes the country's statistics is told to begin from it (`countryStatsWorkerKernel.js`).

**Historical tracking is on unless the player turns it off** (`countryStats.js COUNTRY_STATS_TRACKING_DEFAULT_MONTHS`, 6; `COUNTRY_STATS_TRACKING_VERSION` 2). A game with no setting stored, or one stored before the default with no interval, tracks the player's own country every six months; Off chosen in the stats pane stays off. The player's country is asked for its first sheet once, after the first skip, as any first reading is (`gameplay.js requestTrackedBaseline`): that is one request a game, and the refresh is one request each six months of game time, from the skip's `stats` budget as before.

**Cities follow their country** (`runtime/cityPopulation.js countryPopulationMoves`, `citiesFollowing`; `frontApply.js citiesFollowCountries`). When a country's population has moved by 0.5% or more since its cities last followed (`world.cityPopulationBasis`), every city of the map it holds is moved by the same share, from whatever that city is at that moment, and the figure is kept in `world.cityPopulations`, which every reader of a city's population looks at first. A city whose figure the turn's own events set (struck, razed, resettled) is left at what they say that turn and follows from there the next time. Which country holds a city is read from the map on the fronts' sheet of the whole of it, and the map's shapes are read for that only on a turn when some country is due. No request is made.

**Two layers of statistics** (`runtime/statsBackend.js`). The BACKEND is four figures every country's sheet can carry: its people, its economy, the balance of its budget and its public debt (`population.total`, `economy.gdp`, `economy.budgetBalance`, `economy.publicDebt`). It is what the war reads: manpower, funding, weight. The FRONTEND is what the player is shown. In an ordinary scenario that is the standard sheet and the backend is part of it. A scenario with a sheet of its own (`customStats`) shows only that, and used to keep nothing else, so the war had nothing to go by. Its sheet is now asked for with a `backend` object in the same request (`gameplaySchemas.js getGameplayToolForCustomStatSheet`; `statsBackendInstruction`): the model works the four figures out first and then writes the scenario's own values to say the same thing. The backend is kept on the sheet beside the custom values (`gameplay.js generateScenarioCustomStatSheet`), shown to and moved by the periodic refresh of such sheets (`refreshTrackedCustomStatsIfDue`), and never shown to the player (`stats.jsx` renders the custom sheet alone).

**The countries the player comes into conflict with are asked of in one request** (`statsBackend.js conflictSheetTargets`, `gameplay.js requestConflictSheets` and `ensureConflictBackends`, `Game/AI/conflictBackends.js`). A country that is on a battlefield with a country a person plays, or that a route of its troops goes into, and that has no backend, is asked of. All of them go in ONE request, which wants only the four figures of the backend and not a whole sheet a country: up to `CONFLICT_BACKENDS_MOST` (8) at once, the rest on later turns, with the backends already known shown for the unit and the scale. It is a first reading like the others (background AI, after the turn, one at a time a campaign). In a scenario with a sheet of its own the same request writes that sheet too, for every country that has none (the backend first, then the scenario's values saying the same thing), so such a country has both layers at once and nothing is left to ask for; a country whose own sheet is there is shown it and given the backend that agrees. In an ordinary scenario the four figures are what is kept, and the rest of the standard sheet is written when somebody opens that country's statistics. Nothing is written over a backend that is there. Those it fights come first, then those its routes go into, then its own side. It is asked after every turn, when a scenario's fronts are built at a game's first opening, and when a route is drawn into a country in the war room. A scenario's own sheet that is complete but was written before it kept a backend is given one by the same request, and is not written again. Groups are not countries and are never asked. (The player's own country, tracked from the first skip, is still asked for a whole sheet with its backend: `requestTrackedBaseline`.)

**Both layers are written by the same request** (`statsBackend.js`). Wherever a request writes a country's statistics it writes the backend with them: a scenario's own sheet at its first reading and at its periodic refresh; the request for the countries in a conflict; and a time skip, whose stats patch in such a scenario has `backend` beside `customStats` (`gameplaySchemas.js STATS_BACKEND_PATCH_SCHEMA`, any of the four figures) and which is shown the backends it may move (`statsBackendTurnRule`, added to the skip's live records after the scenario's sheet). A patch's `backend` is taken for the standard fields it stands for wherever a patch is merged (`countryStats.js mergeCountryStatPatch`), so the Game Master's patches carry it the same way.

| | the side that began the war | the side defending |
|---|---|---|
| a general advance along the whole line | from 1.25 to 1 | from 1.5 to 1 |
| an attack on the stretch of line where it is strongest against what faces it | from 0.9 to 1, in 7 reviews of 10 | from 1.15 to 1, in 5 of 10 |
| holds | below that | below that |
| digs in | under 0.55 to 1 | under 0.55 to 1 |

What it decides is an ordinary standing order by the side's first country, marked `mark: "staff"` (kept in the record), so the brief, the war room and the next period's story show it like any other; going over to the attack is logged (`{ k: "offensive", s, at }`, `at` a stretch of line or `the whole line`) and told. **The story still commands**: an order the story gave stands, and the staff leaves the side alone, for 45 days (`STAFF_STORY_ORDER_DAYS`); only an order that old, the staff's own, or none at all is the staff's to replace, and a line the story writes replaces the staff's at once. A side with a person on it has no staff (`sideIsPlayed`). The same run decides the same (the chance is drawn from the run's seed, the battlefield, the side and the date), so the period fought before the story and the run that applies it agree. A run given `staff: false` leaves every side to its orders (the engine's tests of other things are; `frontTurn.js` passes it through).

**Each country of a side commands its own troops** (`orders.js takesOrder`, `giverOf`). An order is for the troops of the member that gave it (`by`), and one member's order never replaces another's (`setStandingOrder`). The order of a side's first member is also for the troops of any other member that nobody plays and that has no order of its own for where they stand, so a coalition the story orders in one line still moves together; a person's troops are moved by nobody else's order (the engine is told who is played: `input.players`). No general commands two countries' troops (`command.js shareOut`), the brief says how many formations each member has there (`strength[side].members`) and whose an order is, and in the war room a country picks, orders, routes, releases, withdraws and ships only the troops it brought (`warRoomOps.js ownIndexes`, `command.js ownTroopsOf`, `generalsOf(record, side, { member })`). **Strategy is agreed by diplomacy:** an ally nobody plays has its orders written by the story, which is told who the player's allies are (`frontPrompt.js alliesRule`) and that what an ally agreed with the player in their talks (`[Diplomatic Memory]`) is what its orders carry out; what was only asked of it, it weighs as its own government would.

**Withdrawing** (`engine.js withdrawWhoLeft`, order word `withdraw`). Troops told to withdraw go back from the line as troops falling back do, with no end to how far, and leave the battlefield once they are 60 km back (`WITHDRAW_KM`), can go no further, or after 12 days (`WITHDRAW_DAYS_MOST`; troops with the sea behind them are taken off where they stand). A formation of the world is a unit of the world again where it left from (`unitChanges`, and `carry.sentHome` keeps it from being taken straight back in); a counter the battle raised is stood down. **The ground stays as it is**: nothing is handed back, and the other side does not follow troops that are leaving (only troops that fall back), so what was taken stays taken until somebody is ordered to walk in. A side whose last troops have gone is away (`carry.away`): it stands under an order to withdraw, takes nobody in, and its brief says its ground is unguarded. Given any other order it comes back (`comeBack`: its troops are raised again on the ground it holds, log `returned`). On a border fortified in peace, to withdraw is to stand down.

**A person's typed actions are their orders, given through a function the skip's model calls** (`AI/frontOrderFunction.js`). The period a skip fights before it asks for the story (`forecastTurnFronts`) is the period as it goes IF NO PLAYER ORDERS ANYTHING NEW: the orders that stand, and what the war room set. A player may have typed just such an order as an action ("I withdraw my troops"; "the north-west digs trenches, the south pushes for the city"). Nothing in the game reads the action's words for that: the model reads the action, and the `[Fronts]` block tells it (`frontPrompt.js playerRule`) to call `order_troops` FIRST, with a line for each stretch of line the action speaks of (`battlefield~side~order~sector~date~objective`; only a played country's own troops, never a strike or a transporter: `readGivenOrders`). The period is then fought AGAIN with those orders, each from the day it was given (`forecastTurnFronts` with `given`; a given order carries `now: true` and its `date`, and `frontTurn.js planFrontMoments` puts it on its day even on a battlefield whose period was told), and the function answers with the battlefields as that leaves them (`frontsListBlock`), which is the war the events then tell. The orders are kept with the turn (`result.frontsGiven`) and the run that applies it is that second run again (`applyTurnFronts`, `givenOrders`). The function is offered only where there is a period fought beforehand and an action queued, and not to a skip made in segments; it is answered once. **Cost: one request more, only in a skip where the model calls it** (the skip's own budget of function rounds); a skip in which no action orders troops is one request, as ever. With no period fought beforehand (peace, or a war that begins in the answer) the order is a line of the answer resting on the event that carries the action, kept by `screenFrontOrders` because that event carries it (`impacts.actionIds`), and is carried out from that event's day.

**The difficulty weighs the land war** (`runtime/fronts/handicap.js`, `constants.js DIFFICULTY_EDGES`). On Medium a battlefield is fought as it is, the same for both sides. Above Medium the side that fights a country a person plays is given an edge, and below it that side is the one held back. An edge is four figures: `power` (what its troops are worth in attack and in defence, beside the side's quality in `combat.js`), `pace` (how fast its own troops advance), `reserves` (how much reserve comes with every troop it raises, brings in or lands) and `mend` (how fast its troops are brought back up to strength). Above 1, `power` is also how slowly that side's ground is taken: a step into it never goes faster than `1 / power` of the pace, whether a defender is near or not (`combat.js stepForward`, `open`). Most of a large army's advance meets nobody, so a level that weighed only the fights was hardly felt by a player with the bigger army.

| Level | power | pace | reserves | mend | An even enemy attacks the player for a month: the share of the sheet the player still holds, having begun with half |
|---|---|---|---|---|---|
| Very Easy | 0.85 | 0.9 | 0.7 | 0.75 | 48% |
| Easy | 0.93 | 0.95 | 0.85 | 0.9 | 48% |
| Medium | 1 | 1 | 1 | 1 | 24% |
| Hard | 1.15 | 1.1 | 1.3 | 1.25 | 12% |
| Very Hard | 1.35 | 1.2 | 1.75 | 1.6 | 1% |
| Impossible | 1.75 | 1.4 | 3 | 2.5 | none: driven off the sheet, with a third of its army gone |

(Measured 2026-10-11 on an even sheet, two equal armies, neither dug in. With the player attacking instead it ends the month holding 88% on Medium, 71% on Hard, and gains nothing from Very Hard up. On the real map, through whole skips with a stand-in model, Russia with 289 formations against about 200: played and attacking for a month it takes 76 regions on Medium, 68 on Hard, 64 on Very Hard and 57 on Impossible; attacked instead by that army, the player loses in ten days 9 regions on Medium, 10 on Hard, 19 on Very Hard and 36 on Impossible. A player with three times the enemy's army still wins on Impossible, only more slowly.) Only a battlefield with a person on ONE side is weighed (`weighedSide`): a war between countries nobody plays is fought fair on every level, nobody is handicapped against another player, and the countries beside a person are given nothing either way. The edge is never kept with the record (`battle.edge`, read by every run from `input.difficulty` and `input.players`, and again when a country comes into the battle or leaves it), so a level changed in mid-game counts from the next skip, and the run made before the story and the one that applies it are given the same level (`frontApply.js turnRunInput`). It is said, never hidden: the `[Fronts]` block tells the story the figures on every level but Medium (`frontPrompt.js difficultyRule`), each level's list of effects says them where the level is chosen (`runtime/difficulty.js`), and the war room says them of the other side on the battlefield shown. This is the one place a difficulty changes an engine's arithmetic; everywhere else it is a directive to the model (`difficulty.js`).

**Transporters** (`world.transports`, `runtime/fronts/transports.js`). Troops reach a battlefield over land their side holds; a transporter takes them where it holds none, which is how a country fights one it has no border with and opens a second front behind a line. A record is `{ id, medium: "sea"|"land"|"air", kind, owner, warId, battlefield, from, to: { lng, lat, name }, speed, capacity, load: [[strength, troopKind]...], status, ordered, departed, due, ended, way, km, gone, at, landing, hunters, hits, sunk, by, note, attacks?, embark?, raise? }`. `kind` is free (a troop convoy, an armoured train, anything the story calls it); `medium` says where it can go, `speed` its kilometres a day and `capacity` the formations one carrier takes (`CARRIERS` gives the usual of each medium by the year: nothing flew troops before 1936). `status` is `ordered` (it sets out on the first day time next passes), `moving`, or an end: `landed`, `lost`, `refused` (with `note` saying why), `returned`. One that has ended is kept through the run that follows, so it can be told and shown, and then dropped.

- **Its way is found, not drawn** (`wayfinder.js`, over `worldGrid.js`): the whole map as a sheet of cells a quarter of a degree a side, each saying how much of it is land and which region lies there, drawn once from the map's shapes and kept with the arenas. A ship goes by water round the land (a cell that is partly sea is open, so a strait is; Suez from 1869 and Panama from 1914, and only where the map IS that part of the Earth: `CANALS` carries places round each that are sea and land there, and every one of them has to be so on the sheet), keeps off a shore its enemies hold where another way is little longer, and comes to the coast nearest where it was sent; a train goes through land its own side holds and stops at the last of it; an aircraft goes the short way, round its enemies' land where that costs little. The same map and holders give the same way every time. Regions of a type that is water are left as sea on it (`runtime/regionTypes.js isWaterType`), so a map whose sea is drawn as regions is sailed all the same. The sheet is drawn from the scenario's own regions, so an invented world (on a globe of its own, or on a flat sheet) is sailed round its own land like any other, and is dug no canal. These files, like the rest of the engine, use only arithmetic every machine does alike: their sines and arctangents are series (`worldGrid.js sine`, `arcTan2`).
- **What it carries** is troops taken off a battlefield (`embark: { battlefield, side, troops }`, written by the war room: they leave it when it sets out) or a number raised when it sets out (`raise`, for one the story ordered, from its owner's city nearest the place).
- **Interception** (`interceptionOf`): each day under way it may be caught by its enemies' naval and air formations near it (`world.units`; ships reach 380 km after a ship, aircraft 900 km after a ship or an aircraft and 650 km after a train), from a shore they hold, and above all by whoever was told to go after it (`hunters`). Its own side's ships and aircraft beside it cover it. A hit takes at least a carrier's load and at most 85% of what is aboard; with nothing left it is `lost`. The roll is the transporter's own (`transportChance`: seed, id, day), so the run that applies a turn is the run that was fought before its story.
- **Arrival** (`engine.js landTransport`): on a battlefield of its war, on its own side's ground the troops simply arrive (`reinforced`), on the other side's they take a disc of it with an anchor (`landed`); where no battlefield is, one opens there with the carried troops as the attacker's force and only the defender raised (`openLandingAt`), and they are told to advance. Land of a country outside the war is an attack on it: it joins the other side that day, exactly as for a route (`joins`, and `attacks` on the record from the day it sets out). A force put ashore advances although it holds little ground: within 75 km of its anchor the rule that a rank waits for ground beside it does not apply (`ANCHOR_FREE_KM`, `move.js`).
- **The run returns** `transports` (the list to write) and `voyages`: what became of each, `{ d, day, k: "sailed"|"intercepted"|"lost"|"landed"|"reinforced"|"invaded"|"returned"|"refused", id, owner, kind, medium, to, n, ... }`. A battlefield's own log gets `landed` / `reinforced`.
- **Who orders one.** The story, in its lines of orders: `ship`, `rail` and `airlift` are order words (`nativeFrontLedger.js`), with three more fields after effort for what carries the troops, how many formations and how fast; `frontTurn.js` sets those lines apart from the orders a battlefield is given and adds each to the world as `ordered`, so it sets out when the NEXT period begins and that period, fought before its story, tells the voyage (`frontPrompt.js describeTransports`). A player, in the war room (ops `transport`, `untransport`, `hunt`). A transporter under way is reason enough to fight a period before its story (`frontApply.js fighting`).

**Strikes** (`world.strikes`, `runtime/strikes.js`). When an event tells of a missile launched or a place bombed, the map shows it. A strike is what the story wrote of one, and nothing else: `{ id, eventId, date, round, owner, weapon, count, down, from: { name, lng, lat }, to: { name, lng, lat } }`. `weapon` is `silo missile`, `submarine missile` or `nuclear bomber` (the three that are nuclear), `missile strike` or `bombing run`; `count` is how many missiles or aircraft, `down` how many of them were intercepted on the way (the story writes a number, or `all`, `most`, `half`, `some`, `none`: `nativeFrontLedger.js shotDown`; the block tells it that an event which tells of an interception owes the field). What is intercepted is seen to be: an interceptor climbs to meet it and it blows up in the air (game-ui.md, strikes). **It changes nothing by itself**: what a strike did is whatever its event's own operations say, and the strike is only what is drawn.

- **Who writes one.** The story, as a line of its own among its orders (`nativeFrontLedger.js`): `strike~side~weapon~from~eventNumbers~target~shot down~count`. The rule is part of the `[Fronts]` block, which every skip of a game with fronts carries whether or not a war is being fought, so a first strike in peace is drawn too. A strike is no order: the rule that a person's troops take orders only from that person does not touch it (`screenFrontOrders`), and one whose weapon or target cannot be read is left out with the reason on the turn's receipt.
- **Its places** are found when the turn is applied (`frontTurn.js`, `findStrikePlace`): among the places its event itself placed, then the map's cities, the world's structures and its formations, and then by the game's own reader of places (`gameplay.js createStrikePlaceReader`, handed to the turn as `strikePlaces`): a country at its capital, a region at its middle, and a city this map spells another way through the world's towns, exactly as a placing is read (`placement.js resolvePlacement`: Kyiv, on a map that writes Kyyiv; said with its kind a name is a city of the MAP or nothing, so it is read as a bare phrase). Launched from nowhere that is named, it sets off from what its owner has on the map for it (`pickStrikeOrigin`): a silo for a missile, a formation at sea for a submarine's, an airfield or an air wing for aircraft, the nearer the target the better. With nothing of the kind it leaves a city of its own (`strikePlaces.origin`): its capital for a missile from a silo, and for the rest the nearest city it holds that is at least 250 km from what it strikes, so that there is a flight to see. A submarine no fleet stands for still fires from the sea (`seaLaunchPlace`): open water well off every shore, in the widest sea within 400 to 2,600 km of the target, read off the same sheet of land and sea the transporters sail on. A place nothing can find is kept by its name, and the map looks for it among the places it knows when the strike is played (`Map/strikePlaces.js`).
- **How long it is kept.** For the turn it happened in and the one after (`withTurnStrikes`, `STRIKE_ROUNDS_KEPT`), at most 16 a turn and 48 in all; a turn applied again replaces its own. Every player's map is given them (`PUBLIC_WORLD_KEYS`).

**The war at sea** (`runtime/naval/engine.js`, `world.seaBattles`, `world.naviesRaised`). The land war is fought by an engine; so is the sea. **A fleet is still one of the world's formations** (`world.units`, type `naval`): it is moved as it always was (the story's unit operations, a player's orders), and where it is and the posture it keeps are its orders. What the engine decides is what happens when hostile fleets are in reach of each other, a day at a time over the period, in the same run that fights the land war (`frontTurn.js runTurnFronts`, on the same sheet of land and sea the transporters sail on) and so before the story is asked for.

- **Who fights.** The fleets of countries on opposite sides of an active war, not on a battlefield's books (`committedTo`), within `NAVAL_REACH_KM` of each other by era (150, 300, 600, 900 km). A day's chance goes by the keener posture of the two (`POSTURE_KEEN`: `assaulting` most, then `blockade`, `patrol`, `holding`, `withdrawing` least), less where one is withdrawing (`EVADES`) and less again where a fleet that is withdrawing or holding lies within `HOME_WATERS_KM` of its own coast (`SHELTERED`). Every fleet of the two sides in reach joins. A fleet that has fought fights no more for `REFIT_DAYS`.
- **What a battle does.** Each side's weight is its fleets' strength, what their countries are (`navyFactor` of the same `countryWeight` the land war uses) and how they are handled (`POSTURE_FIGHTS`), with a little luck from the run's seed. The side outweighed loses more. A fleet at or under `SUNK_UNDER` is gone; a fleet under `BREAKS_UNDER`, and every fleet of a side whose share was under `LOST_UNDER`, breaks off: its posture becomes `withdrawing` and it fights no more that period.
- **Moving.** Only two postures move a fleet by themselves, and only over open water in a straight line (no course is found round a cape): `assaulting` closes with the nearest hostile fleet within `SORTIE_REACHES` reaches, and `withdrawing` makes for the water under its own coast.
- **A navy to fight with.** A country at war with a coast, no naval formation at all and an enemy it could meet at sea is commissioned a home fleet off its coast nearest its capital (`COMMISSION_LEAST` and up by what it is), within the caps on formations (`MAX_UNITS_PER_POLITY`, `MAX_UNITS_GLOBAL`). It fits out for `FITTING_OUT_DAYS` before it can fight. `world.naviesRaised` (`[{ country, date }]`) keeps when each country was given one or lost the last of one, and nobody is given another within `NAVY_REBUILD_DAYS` (three years): a navy sunk is not handed back the turn after.
- **What the run returns.** `sea: { battles, fleets, commissioned, raised }`, and its changes to the fleets among `unitChanges` (strength, place, a posture, `remove`), which `frontApply.js withFrontUnits` writes onto `world.units` after the story's own operations: what a battle did to a fleet is the engine's figure, whatever the story wrote. A formation the land war took up in the same period is left to the land war.
- **What the story is told** (`AI/navalPrompt.js`, the `[Seas]` block, after `[Fronts]` in the skip's live records, at most `SEAS_BLOCK_MAX` characters and only while there is a war with a fleet in it): the rules, the battles ALREADY fought this period with what became of each fleet, any fleet commissioned, and the fleets as the period leaves them. It adds no request. A person's fleets are moved only as an action of the turn orders, so an order to a fleet is fought over in the next period.
- **`world.seaBattles`** (`runtime/naval/record.js`): `{ id, date, round, place, lng, lat, warId, sides, fleets: [[{ name, owner, before, after, sunk?, broke? }], [...]], winner }`, kept for the turn it was fought in and the one after (`SEA_BATTLE_ROUNDS_KEPT`) for the map to mark (`Map/SeaBattleLayers.jsx`: a ring and a cross in the colour of how it went for the player, with who fought and when). They decide nothing: what a battle did is on the fleets. Every player's map is given them (`PUBLIC_WORLD_KEYS`).
- **Off** with the Fronts feature, with `naval: false` to `runTurnFronts`, and whenever the map's sheet cannot be drawn (fleets in reach still fight; nobody is commissioned and nobody moves). A sea that cannot be fought never stops the turn.
- **Blockades** (`runtime/naval/blockade.js`, `world.blockades`). A fleet in the posture `blockade`, not beaten off, within its reach of the coast of a country its own is at war with presses on that country. The pressure, 0 to 1, is worked out for every day of the period inside the same run: the country's coast is read at up to `BLOCKADE_STATIONS_MOST` places; a place is closed by the fleets in reach of it, wholly at `BLOCKADE_CLOSES` of weight (a fleet's strength by `navyFactor`), less what the fleets of its enemies in reach of a blockader tie down (one that is withdrawing ties down nothing); and the whole is scaled by how much the country lives by sea (`seaShareOf`: its coast against its land borders with countries it is NOT at war with, a border counting `LAND_TRADE_WEIGHT` of a like stretch of coast, and never under `SEA_TRADE_LEAST`). An island lives by nothing else; a neighbour that joins the war against it closes that border too. The period's pressure is the mean of its days, so a blockader driven off half-way laid half a blockade. Without the map's sheet nobody's coast is known and no blockade is worked out.
  - **The record**: `{ country, by: [names], pressure, covered, days, since }` (`withTurnBlockades`): the last period's pressure, the share of its coast reached, the days in a row it has stood and the day it was laid. A period that no longer presses lifts it. Every player's map is given them (`PUBLIC_WORLD_KEYS`).
  - **The economy** (`frontApply.js withBlockadeEconomy`, applied with the turn's manpower): `BLOCKADE_GDP_A_YEAR` (a fifth) of the country's GDP in a year at full pressure, by the period's length and never more than `BLOCKADE_GDP_PERIOD_MOST` in one period, taken off `economy.gdp` (and `gdpPerCapita` with it) on the backend of its sheet, and `BLOCKADE_BUDGET_A_YEAR` (6) points off its `economy.budgetBalance` (`budgetUnderBlockade`), each where the sheet has it. What it has to spend on its forces follows (`militaryFunding.js`), and so does how fast its war resources refill, which the blockade cuts besides. A country with neither on its sheet is left as it is.
  - **The land war** (`runtime/fronts/handicap.js shortEdge`, `constants.js SHORTAGE_EDGE`). A country is SHORT by its blockade's pressure times how long it has stood, in full after `BLOCKADE_BITES_DAYS` (`shortageOfBlockade`). `frontTurn.js` hands the engine `shortageOf` from the blockades standing AS THE PERIOD BEGINS (a blockade laid this period bites on land from the next), and `battle.js setHandicap` weighs each side for it as it weighs one for the difficulty, each member by what it brings (`sideShortage`): at a shortage of 1 its troops are brought back up to strength at half the pace, half the reserve comes with every troop raised, and they fight and move at 85%. Nothing of it is kept with a battlefield's record.
  - **The story** is told each blockade in the `[Seas]` block (who is cut off by whom, how much, which day of it) and that the game takes the cost off the economy itself: it tells the shortages and moves the country's other figures, and leaves its GDP alone.
- **Not in it yet:** command of a sea and a war room for fleets. A blockading fleet is not moved to a coast by the game: whoever orders it there puts it there. A transporter's crossing is intercepted by the fleets as before (`transports.js`), so a fleet worn down at sea catches fewer.

**War weariness, alliances coming due, and peace on terms** (`Game/AI/warAndPeace.js`; the rules in `runtime/warWeariness.js`, `runtime/peaceTerms.js`, `runtime/alliances.js`). The game keeps weariness, alliances and reparations itself; WHETHER a country wants peace, and on what terms, is the AI's (since 2026-10-30: "it should not be fully deterministic anymore"), and the game checks and carries out what it is told. `turnWarAndPeace` runs at the end of every turn, after the ledgers the story wrote are merged and before `pruneWarUnits`, and is handed the world as the turn began, so the same turn applied twice is the same world. In order:

- **Reparations** (`world.reparations`: `{ id, warId, payer, receiver, share, since, days, paidDays }`) are paid for the period (`reparationsDue`): on the backend of each sheet the payer's `economy.publicDebt` rises by the share of its GDP it paid, in points, and the receiver's falls by what that sum is of its own GDP. A payer with no economy on its sheet pays in the story only; its days still count. They end when `paidDays` reaches `days`.
- **Alliances come due** (`world.callsToArms`). A DEFENSIVE BOND is an active agreement of type `alliance` or `mutual_defense` (every party to every other), a `guarantee` (its guarantor to its beneficiary, one way), or full membership of an active institution of kind `security_alliance` or `defense_pact` (`alliances.js defendersOf`). When a war BEGINS in a turn (it is active in the ledger and was not as the turn began), the country it was begun against, the first of its second side, calls on those bound to defend it; one already in the war, or bound to an attacker too, is not called. **A country nobody plays** comes in, as a `join-b` record on the ledger (the strongest first, at most `ALLIES_CALLED_MOST` a war, within the ledger's twelve a side), unless its relation with the defender is under `HONOUR_RELATION_LEAST` or its own weariness is at `HONOUR_WEARINESS_MOST`: then it has BROKEN THE TREATY. **A country a person plays** is asked: the call is `open` until they honour it (they join the war) or refuse it, and one left unanswered for `CALL_STANDS_ROUNDS` turns is a refusal. Nobody joins a war on a person's behalf. A bond the story itself ended or suspended in the turn the war began is a treaty broken too. **A treaty broken** costs the breaker `TREATY_BROKEN_REPUTATION` (15) of `world.internationalReputation` (and of the figure on its sheet where its sheet carries one), and it is out of the agreement, which ends when fewer than two are left in it; a member of an institution that will not fight keeps its seat and pays the same. A war already being fought calls on nobody new, so a game from before this rule is not swept into its old wars.
- **War weariness** (`world.warWeariness`: `[{ country, value }]`, 0 to 100). `withTurnWeariness` moves every country at war by what the turn did to it: `WEARINESS_A_YEAR` (8) for the time, `WEARINESS_PER_SHARE_CALLED` (400) for the share of its people its armies took net of those who came home (the land war's manpower ledger), `WEARINESS_ALL_GROUND_LOST` (60) for the share of the regions it held that changed hands to an enemy, `WEARINESS_BLOCKADE_A_YEAR` (25) by a blockade's pressure, less `WEARINESS_GROUND_TAKEN` (12) for ground taken; never more than `WEARINESS_PERIOD_MOST` (35) in one period. At peace it falls by `WEARINESS_PEACE_A_YEAR` (30). Past `WEARY_FROM` (50) it tells on a country's armies exactly as a blockade does (`wearyShortage`, up to 0.5; `frontTurn.js` joins the two with `shortagesTogether` into the `shortageOf` the engine is handed).
- **Peace on terms** (`peaceTerms.js`). Terms are the ground (`as held`: each side keeps what it holds, so what was taken is ceded; `restored`: every region goes back to whose it lawfully was) and reparations (`{ payer, receiver, share, years }` or none). How a war stands for a country (`standingOf`) is the share of the other side's regions it holds less the share of its own the other side holds, read from `regionSovereigntyOverrides`, which lists exactly the regions held by one country and lawfully another's (`warAndPeace.js groundReader`; the denominators are counted on the map by `frontApply.js regionHoldingsOf`). `termsOffered`: about even, the old borders and nobody pays; ahead, it keeps what it holds; beaten, it cedes what it lost and pays, the more and the longer the worse it stands (up to `REPARATIONS_SHARE_MOST` 4% a year for `REPARATIONS_YEARS_MOST` 12). `wouldAccept`: terms are worth taking when they are worth no less than what the country expects of fighting on, which is its standing plus `PEACE_HOPE` (0.2) when fresh, its standing when half-weary, and less than its standing when spent. These figures decide nothing any more: they are told to the model as "the game's reckoning" beside the war's other figures (`AI/warStatsPrompt.js`). Terms an AI writes are held by `clampTerms`: the payer is one of the two making peace and the other receives, at most `REPARATIONS_SHARE_CAP` (10%) a year for `REPARATIONS_YEARS_CAP` (20).
  - **Offers** (`world.peaceOffers`: `{ id, warId, from, to, terms, date, round, status, answeredRound?, source?, chatId?, messageId? }`). Made only by an AI or a person, each shown in a diplomatic chat on the message that made it (`GameUI/peacePlacement.js`): a time skip's letter (`diplomaticOutreach[].peaceOffer`, kept by `offerPeace` in `applySimulationResult`, `source: "skip"`, on the letter's own message `msg-peace-<round>-<country>`), a leader's chat reply (`PEACE:offer`, `source: "chat"`), a person's own terms (`proposePeace`, `source: "player"`) and a leader's counter to them (`source: "counter"`). `offerFromAi` checks an AI's: a war between the two, the person's country played, the AI's side nobody's. A new offer between the same two in the same war lapses the last (`withOffer`). `withTurnPeaceOffers` only lapses an offer unanswered for `PEACE_OFFER_STANDS_ROUNDS` (4) or whose war is over: a turn offers nothing itself.
  - **Between two countries nobody plays**: only when the skip says so, a line of its `peaceTreaties` field (`offering | accepting | terms`, `readTreatyLines`), checked by `treatyFromSkip` (they fight on opposite sides, and no person is in that war) and made by `turnWarAndPeace`; a refused one is logged.
  - **A peace made** (`makePeace`): the ground is settled through the event-impact seam (`peaceImpacts`: a `regionTransfers` row a region for `as held`, a `control` back to the sovereign with its `clear_contest` for `restored`, basis `treaty`, only for regions the two sides of THAT war hold of each other's); the war is ended in the ledger with the terms as its note; reparations begin; and the peace is kept in `world.peaceTreaties` (`{ id, warId, title, date, round, from, to, sides, terms, by }`, `by` being `offer`, `proposal` or `settled`, the last twelve). The war's battlefields are closed by the engine at its next run (`syncWithWar`), so until the next turn the map still draws them.
- **A person's answers between turns** (`gameplay.js answerDiplomacy`, one door: `warAndPeace.js playerDiplomacy`): `accept` or `decline` an offer, `honour` or `refuse` a call, or `propose` terms of their own for a war they are in, which wait, open, for the other side's first country's leader to answer in the chat (a side with a person on it is theirs to answer, and is not answered here). The leader's answer rides in its reply, the request the player's message makes anyway: a one-on-one reply's hidden `PEACE:` line (`runtime/diplomaticEnvelope.js`), read by the panel (`gameplay.js answerPeaceInChat`), or a group chat's `peaceAnswers` field, read by `runChatActionBatch` (on the host in a shared game); `warAndPeace.js answerPeaceProposal` accepts (the war ends on the person's terms), declines, counters (a new offer to the person) or offers. Refused while a turn is being generated, since the turn would write over it; written with `mutateWorldState`. A guest's goes to the host as the `peace` request (`multiplayer/game/messages.js`, `host/gameHost.js`), where whose answer it is is the seat's country and nothing the message says. All five keys are in every player's view (`PUBLIC_WORLD_KEYS`).
- **What the story is told** (`AI/peacePrompt.js`, the `[War Weariness, Peace and Alliances]` block, after `[Fronts]` and `[Seas]`; nothing in a world at peace with no alliance in it): that alliances bind and the game enters the allies itself; that peace is the AI's to offer, and how (a letter's `peaceOffer`, a `peaceTreaties` line); every country at war's own war, the players' enemies first (`AI/warStatsPrompt.js buildWarStatsBlock`: weariness, ground, battlefields, supplies, blockades, reparations, allies, calls to arms, offers on the table, and the game's reckoning), the same block a leader's reply, a group chat's turn and the pulse between rounds are given; the offers turned down lately; the peaces made since the last period, to be told as events with no `warUpdates` of their own; the offers and calls that wait for a player, which it must not answer; the reparations running; and who is bound to defend whom. **This reverses a rule**: the `[Wars]` directive, the war ledger's footer, the diplomatic context's footer and the Game Master's rule 11 all said an alliance does not create belligerency; they now say it does only through the game.
- **Not in it:** an attacker's allies are not called (a bond is defensive); a puppet is not bound to its overlord; a peace cannot yet name particular regions; and nothing moves a member out of an institution for refusing to fight.

**Ground held is not ground disputed.** The engine's change of hands is a control operation marked `by: "front"`: it sets who controls the region (`regionOwnershipOverrides`) and keeps whose it lawfully is (`regionSovereigntyOverrides`), and it adds nobody to `regionClaimants`, which is what the map draws stripes for (the same operation written by the story itself is an occupation as it always was, striped in its sovereign's colour). Whoever just lost the region, and its lawful holder, come off its claimants; a dispute with anybody else stands. When a turn's land war is written, `gameState.js withoutBattlefieldDisputes` takes the same claimants off every region a battlefield's sides have taken from each other (`fronts/heldRegions.js`), which cleans a game saved while such ground was still striped.

**The period is fought before its story is asked for.** `simulateTimelineJump` (gameplay.js) calls `AI/frontApply.js forecastTurnFronts` once it has read the game: the engine is run over the days the skip will cover, under the orders that already stand (the campaign's, and what was ordered in the war room), and what came of it goes into the skip's `[Fronts]` block (`AI/frontPrompt.js`): each battlefield as the period leaves it, how many formations each side began with, and what happened on which date. No request is made for it, and nothing is written. The answer's events then tell the war that was fought. When the turn is applied the same run is made again (same seed, same input: the engine's result is the same to the last troop) with the answer's `frontOrders` for those battlefields put at its END (`frontTurn.js planFrontMoments`, `settled`), so they are carried out in the period after. The skip's result says it was asked this way (`result.frontsForetold`), so a turn kept and applied later is applied the same way. Only on a battlefield that first opens in the answer is an order carried out from its event's date; its fighting was told to nobody, so its record has no `brief.told` and the next skip tells it. With nothing to fight beforehand (no battlefield being fought, a skip of hours, a calendar the game cannot count days on) the skip is asked as it was before any of this and the engine runs after it. A change of hands rides on an event that tells of its war (bound to it by `warId`, or with both sides among its `combatants`): the first of its day or later, else the last before it.

Before each run of the engine `AI/frontPlans.js turnPlanned` writes the turn's plans onto the battlefields where a war is being fought: an Operation of a player's own that is `active` sends the nearest troops not already under a hand order (once), and a side nobody plays digs in the troops it has near a movement its agents have shown it. What those agents carried off is also told to the simulator, in `[What Agents Report of the Fronts]`, only when there is something to tell.

`world.scenarioFronts[]` (`runtime/fronts/scenarioFronts.js`) is a scenario's list of the fronts its games begin with: `{ name, sides: [[names], [names]], war, troops: [n, n], stance: [word, word], generals: [[names], [names]] }`. It is one of `TEMPLATE_WORLD_OVERRIDE_KEYS`, so a new game carries it; the first time the game is entered the engine is run over no days to build the battlefields (`gameplay.js maybeOpenScenarioFronts`), the wars they are fought in are written into the ledger, and the list is cleared, which is the mark that it has been done. It is never sent to a guest of a shared game.

#### Wars and Fronts Pt.2 (lab): how a scenario's wars are fought

`world.warSettings` (`runtime/warSettings.js`) is the scenario's own rules for its wars: `{ mechanics, era, menPerCounter, manpowerShare, muster }`. `mechanics` turns the front engine's newer mechanics on or off one by one (`fatigue`, `weather`, `terrain`, `walls`, `muster`, `military`, `air`, `supply`, `attrition`); one the scenario says nothing of is **on** (`warSettingsOf`). The engine itself takes them as `input.mechanics` and treats anything but a literal `true` as off (`runtime/fronts/mechanics.js`), so every engine test that is not about them runs exactly as it always did. `era` (0 to 3, or null) sets the era outright, for a scenario with a calendar of its own (`unitMotion.js eraOf` reads a year of any length besides); `menPerCounter` and `manpowerShare` are the scenario's defaults for every country; `muster` is its default mustering curve, two points `[share of the army, days]`.

Each morning of a battle's day (`runtime/fronts/dawn.js`) what the day makes of every troop is set as three numbers the fight and the march multiply by: `punch` (attack), `guard` (defence) and `legs` (pace), each exactly 1 with nothing on. The evening, before the day's books close, is what the day did to it.

- **Fatigue** (`fatigue.js`): a troop's fatigue (0 to 1) rises with the day's march (a full day at its era's pace adds 0.05) and fighting (0.035 attacking, 0.015 attacked), falls on a day of rest (0.07; more dug in, less short of supply, hardly at all cut off), and leaves a spent troop 65% of its attack, 85% of its defence and 60% of its pace. Kept a letter a troop in `brief.carry.tired`. A troop that did not advance the day before (it took no ground and made no attack: `dawn.js` marks it each evening) fights `STILL_EDGE` (8%) harder the next, in attack and defence alike, so holding a stretch is worth something. And with it troops dig in faster and deeper and their works hold better (`STRONG_WORKS`: a holding troop digs 0.06 a day to 0.7, a dug-in one defends at 2.5 and loses 0.35 of what it would, and an assault on troops in their works costs the attacker up to 2.5 times its losses; 0.04, 0.5, 1.6, 0.55 and no extra cost without the mechanic), so that attacking everywhere costs more. On 100 arena wars (`tools/strategy-nn`, every mechanic on) always advancing went from beating the scripted staff in 61 of them to beating it in 32 (+25.0 a war to +10.6, SE 7.5: a few lopsided wins still carry its average).
- **Each country's military figures** (`runtime/militaryStats.js`; what they do, `runtime/fronts/military.js`): `quality`, `technology`, `land`, `sea`, `air` (0 to 100, 50 is what every country was before; an arm at 0 is none at all), `manpowerShare`, `cavalryShare`, `siegeShare`, `menPerCounter`, `weariness` and `muster`. The scenario's author gives them in `polityOverrides[key].military` (or `groups[key].military`); the game keeps its own in the country's backend sheet, `countryStats[key].military`, which stands over the author's field by field; the AI rates a country with none in the request that already reads its backend when it comes into conflict with the player (`Game/AI/conflictBackends.js`). A country's last men, fewer than a counter's, are raised as a counter at part strength. A country that goes to war with no weariness yet in the game's `world.warWeariness` goes in at its own `weariness` (`runtime/warWeariness.js wearinessGoingIn`): its armies feel it from that period, and the game's figure moves on from there.
- **Mustering** (`runtime/mustering.js`, `runtime/fronts/muster.js`): a war that begins after the game did raises each country's levies along its curve, `days(p) = A(e^(Bp) - 1)` through (0, 0) and the two points, handed to the engine as a table of the share mustered on each day. The side that began the war begins at the first point of its own curve; units on the map are there from the first day. What is owed is kept in `brief.carry.levy`, hidden from the other side.
- **Seasons and weather** (`weather.js`): a battlefield's climate by latitude, its season by the month (turned round south of the equator), and four-day spells of weather drawn from the campaign's own seed: pace, attack, fatigue, cold and heat for troops short of supply, and whether aircraft fly. At sea a storm cuts the chance fleets meet and halves a blockade. Clear skies are the likeliest weather of every season of every climate (`WEATHER_ODDS`, from 40% in the tropics' wet season to over 80% in a desert autumn), and of every season of the real world's zones but the three great wet seasons (the Amazon's rains, India's monsoon, South-East Asia's wet season, each still clear three days in ten): about six of the world's zones in ten are clear on a day, and never fewer than a quarter. A season's cold, heat and slowness (its `effects`) are felt on its clear days all the same.
- **Climate zones** (`world.climateZones`, `climate.js`): a designer's own areas, each with its seasons (day of the year to day of the year, a weather mix and effects) and dated events, blending into each other across the map over `blendKm` and between seasons over `transitionDays`. A zone has one weather at a time, the whole of it, and it fits the weather of the zones beside it (`climate.js zoneWeathersOn`, `WEATHER_NEIGHBOURS`: snow is never beside heat, a blizzard only among snow and frost; the larger zone keeps its weather and the smaller redraws among those that fit): every battlefield whose middle is in it fights in that weather, and the turn writes each zone's weather on the day it lands as `world.zoneWeather` (`{ date, zones: [{ id, state, season }] }`, `runtime/zoneWeather.js`), which the map draws as patches of weather in the zones' own shapes (`Game/Map/weatherPatches.js`), with no word of the season or the weather on it: the advisor is told each zone's season and weather today and those of the battlefields the player fights on (`Game/AI/advisorWeather.js`, in its own system prompt), to answer when asked.
- **Frozen water** (`world.freezingRegions`, `world.frozenRegions`): water a designer marked as freezing freezes in its zone's winter (or a polar or continental one where no zone reaches), as the turn's middle day finds it. Frozen, troops cross it at a third of the pace, a front opens across it, and a fleet in it is frozen in; thawed, troops on it get off as they can.
- **Terrain** (`world.terrainAreas`, `arena.js`): ground a designer made harder to cross, level 0 to 10, its speed scaled by `(10 - level) / 10`; level 10 is a wall that is no part of its region. It acts on troops only: the game's map does not draw it (the Workshop does).
- **The real world's defaults** (`runtime/worldGeographyDefaults.js`): a scenario on the built-in basemaps (no `world.background` of its own, as Modern Day) is fought on the real world's continent-wide climate zones (32, with their own seasons: Siberia's long winter, the Indian monsoon, the Sahara's heat) and its hard ground (the great ranges, the marshes, the jungles, the sand seas and the roadless north, level 3 to 9), wherever its author painted no zones (or no terrain) of their own (`climateZonesOf`, `terrainAreasOf`).
- **Fortified lines** (`world.fortifications`, `walls.js`): walls the side opposite the owner may not cross until it breaks them, assaulting rather than going round; each day of assault wears the stretch before it by its level (level 10 never), breaches are kept as kilometres along the line and written back to the world after a turn (`withFrontFortifications`). The owner's troops fight 15% better a level from behind a standing stretch. A line being built (`building: { since, days }`, the War Room's Fortify) is not there until it is finished. A country builds lines of level 3 to 9, and only on its own territory, every kilometre of it on land it holds (read from the regions' own shapes, `runtime/regionLocator.js`); a line nobody passes, level 10, is a scenario designer's alone, drawn in the Workshop.
- **Air** (`air.js`): air wings of a country fighting on a battlefield, within their era's reach, contest its sky each morning; the side that holds it attacks and defends harder and slows the other's columns. Their losses come back once a wing in `unitChanges`.
- **Attrition** (mechanic `attrition`; `fronts/weather.js weatherLoss`, `fronts/attrition.js`, `runtime/attrition.js`): harsh weather and a hard climate wear down every troop out in them, supplied or not: `ATTRITION_WEATHER` (0.25) strength a day for each point of cold or heat (a blizzard 1, frost 0.6, a Siberian winter's ground 1.3 more), up to twice that spent (`ATTRITION_TIRED`), 0.6 of it dug in, up to twice it for a side short of what it needs (a blockade, its weariness, its war resources: `battle.short`), besides what a troop short of supply or cut off already lost. Each morning and evening count, for each country, its formation-days out, those in harsh weather (`ATTRITION_HARSH_FROM` 0.8 or worse) and what attrition (the weather and being cut off) took; the battle's brief says it in formations' worth (`brief.attrition`, "Attrition:" in what the story and the generals read) and the run returns `attrition` `[{ name, lost, men, troopDays, harshDays, days }]`. After the turn it weighs on weariness (`WEARINESS_ATTRITION` 150 for the share of its army lost, `WEARINESS_HARSH_A_YEAR` 90 for its days in harsh weather: a month of a hard winter is 7.5) and on war resources (`RESOURCES_HARSH_A_MONTH` 20), and `world.attrition` `[{ country, lastMen, lastFormations, warMen }]` keeps it while the country is at war, for the Military card and the advisor.
- **War resources** (`world.warResources`: `[{ country, value }]`, 0 to 100, a country not in it full; `runtime/warResources.js`, mechanic `supply`): what a country fights with besides its men. Spent by advancing (each evening `dawn.js` counts each country's formations at war and those that took ground or attacked; a month in which all of them did, every day, spends `RESOURCES_ADVANCE_A_MONTH` 60, half of them half that; holding spends nothing) and by every fortified line of its being built (`RESOURCES_FORTIFY_A_DAY` 0.2 a day until it stands, so a longer or stronger line, which takes longer, costs more: the War Room's Fortify plate says how much). Refilled over time by its economy, in peace as at war: `RESOURCES_REFILL_A_MONTH` 15 a month at the rate `economyRate` gives, 1 for an ordinary country (the square root of what its forces have a head against the middle of the known countries, which counts its budget and debt in, or its treasury alone with none to compare; times 1 + its GDP growth / 20; less `RESOURCES_BLOCKADE_CUT` 0.6 of any blockade's pressure; between 0.25 and 2). The Military card says how much a month. Moved after each turn with weariness (`Game/AI/warAndPeace.js`, from the turn's `effort` and the lines being built). Under `RESOURCES_SHORT_FROM` 40 a country's armies are short as a blockade leaves them (up to `RESOURCES_SHORTAGE_MOST` 0.6 with nothing left, joined with blockade and weariness in `frontTurn.js`), and its military power is up to 30% less (`militaryPower.js`); the Stats pane's Military card shows it.

| `lastJumpMode` | `string` | `""` | Mode of the most recent jump (`jump`/`auto`/…). |
| `lastJumpSummary` | `string` | `""` | One-line summary of the last jump. |
| `lastJumpTargetDate` | `string` | `""` | Target date the last jump advanced to. |

## 3. `normalizeWorldState` — the single normalizer

`normalizeWorldState(world)` (`src/runtime/gameState.js`) is called on **every** read and write of `world.json`, so no downstream code has to defend against missing/malformed fields. Behavior:

1. Spread defaults then the raw doc: `{...WORLD_DEFAULTS,...nextWorld, … }`. Unknown fields (scenario extras) survive; known fields are then overwritten by their normalized versions.
2. Rebuild the maps with blank-key/blank-value filtering: `regionOwnershipOverrides`, `polityOverrides`, `regionClaimants` (≤4), `internationalReputation` (clamped ints), `countryTags` (via `normalizeTagList`).
3. Normalize the arrays: `units`, `pendingUnitOrders` (pruned against the just-normalized `units`), `markers`, `actionSuggestions`, `simulationHistory`, `consolidatedHistory`, and singletons `activeInteractive`, `interactiveOffer`, `historyDocument`, label config, `notes`, `language`, `simulationRules`, `startingTimelineText`.

`writeWorldState` normalizes, calls `enqueueContentStrings(polityOverrides)` to translate edited names on write, then `writeJson(JSON_URLS.world, …, { pretty:true })`.

**Namespace caution:** `countryTags`, `internationalReputation`, `polityOverrides`, and `colors` are all keyed by country **NAME verbatim**. An earlier version uppercased `countryTags` keys only, so a single `change.code` could land under two keys (`countryTags["RUSSIA"]` vs `internationalReputation["Russia"]`) — harmless while owners were uppercase GADM codes, a silent desync once owners are names. Keep the casing consistent.

## 4. `isPolityLandless` — "does this polity hold territory?"

`isPolityLandless(world, code)` (`src/runtime/gameState.js`) is the single source of truth for "landless" (a government-in-exile, movement, or stateless person), used by both the AI prompt (`buildPlayerPolityRegionsText`) and the flag resolvers (a landless polity must NOT borrow the code-derived country flag). The subtlety: owning a region via an override = has land; but a scenario that ships **no** `regionOwnershipOverrides` at all means every polity owns its country through the base map tiles (a stock modern map), which is NOT landless. It reads `regionOwnershipOverrides`, `regionSovereigntyOverrides` and `polityOverrides` straight off the world and folds owners through `createOwnerResolver(buildOwnerAliasMap(...))`; it never calls `normalizeWorldState`, because the UI asks it on every world change.

## 5. AI "impacts" — the mutation vocabulary

Every event may carry an `impacts` object (`normalizeEventImpacts`, `src/runtime/gameState.js`) whose eleven arrays are the ONLY way the AI mutates world state: `actionIds`, `createdChats`, `markerOps`, `polityChanges`, `projectOps`, `regionClaims`, `regionControlOps`, `regionTransfers`, `reports`, `spyOps` and `unitOps`. Each is independently normalized and invalid entries are dropped. (`spyOps` used to be the one family read off the raw event and never normalized, so a reloaded campaign could not replay espionage from `events.json`; it is normalized like the rest now, and still APPLIED after `resolveEspionage` by `applySpyOps`, so an agent placed this turn is not also caught this turn.)

| Impact array | Element normalizer | Applied by | Effect on `world.json` |
|---|---|---|---|
| `regionControlOps` | `normalizeRegionControlOp` → `{op: contest\|control\|clear_contest, regionId, fromCode, actorCode\|toCode\|claimantCode, clearAll?, wholeCountry?, note}` | `applyPolityAndTerritoryImpacts` | De-facto control without a legal change: `contest` adds a contender to the stripes, `control` makes `toCode` the controller (the previous controller and the lawful sovereign become claimants, the sovereign anchored in `regionSovereigntyOverrides`), `clear_contest` removes one claimant (or all with `clearAll`, never the displaced sovereign). Proposed by the simulator and by `nativeTerritoryDirector.js`; resolved through the same geography resolver as transfers, bounded by current control. |
| `regionClaims` | `normalizeRegionClaim` → `{regionId,claimantCode,drop,note}` | `applyPolityAndTerritoryImpacts` | Appends to / removes from `regionClaimants[regionId]` (de-duplicated case-insensitively; the key is deleted at zero). Applied **before** `regionTransfers`, so a region claimed and handed over in the same jump ends settled rather than striped. Until this existed nothing but the map editor and the cheats panel could raise a dispute, so a unilateral claim had nowhere to go but a project. A claimant the world does not know is founded as a landless polity rather than written as a bare name. Plain region names are resolved to ids beside the transfers (`resolveRegionTransfers`); a claim that matches nothing is dropped, never failed. |
| `regionTransfers` | `normalizeRegionTransfer` → `{regionId,toCode,fromCode,regionName,note,basis?}` | `applyPolityAndTerritoryImpacts` | A change of LEGAL sovereignty: `regionSovereigntyOverrides[regionId] = toCode`, and `regionOwnershipOverrides[regionId] = toCode` too unless a third party physically holds the region, in which case the lawful sovereign stays visible as a claimant. A clean hand‑over clears the region's claimants. |
| `polityChanges` | `normalizePolityChange` → `{code,name,color,aliases[],note,reputation,tags}` | inline loop | Upserts `polityOverrides[code]`; also writes `colors[code]` (§7), `internationalReputation[code]`, `countryTags[code]`. A polity can also come into being without any entry here: territory given to a name the world does not know (a transfer's `toCode`, a control op's `toCode`, a contest's `actorCode`, a live claim's `claimantCode`) founds it as an active record with a colour of its own (`polityFounding.js` `foundPolityIfUnknown`; the AI resolver adds the create explicitly, this is the safety net). Stock country names and names already on the map are never founded this way. An `operation: "dissolve"` is refused while the polity still holds or is sovereign over mapped territory; otherwise the record stays (status `dissolved`), its stats, tags, reputation, intelligence and colour go, its standing agreements end, it leaves every side of every war it fought in (a war left with nobody on one side ends on the event's date, its sides kept for the record), and its units and their orders leave the map. |
| `unitOps` | `normalizeUnitOp` → `spawn\|move\|strength\|remove` | `applyUnitOpBatch` | Rewrites `world.units`. |
| `groupOps` | `normalizeGroupOp` (`groups.js`) → `{op: create\|update\|dissolve\|take\|release, name, newName?, description?, color?, regionIds[], note}` | `applyGroupOps` (`groups.js`), after the event's territory has moved | `create` founds a group; `update` changes its description, colour or name (re-keying its area); `take` puts regions in its area (taking them from any other group); `release` gives them back (all of them when `regionIds` is empty); `dissolve` erases it and its area. Lenient where the intent is plain: an `update` or `take` naming a group nobody has creates it; a `release` or `dissolve` of an unknown group does nothing. A game holds at most 64 groups (`MAX_GROUPS`): a create past that is refused, recorded in `changes` as `{op: "refused", reason: "limit"}` and logged, and the Groups GM tool says so instead of reporting success. Moves no border. |
| `markerOps` | `normalizeMarkerOp` → `build\|remove` | `applyMarkerOps` | Rewrites `world.markers`. |
| `projectOps` | `normalizeProjectOp` → `create\|update\|milestone\|close\|remove` | `applyProjectOps` (via `releaseProjectCompletionEffects` first) | Rewrites `world.projects`. **Ending a project keeps it:** `complete`/`cancel`/`fail` (plus the aliases `finish`, `abandon`, `shelve`) all resolve to one `close` op that sets a closed status and leaves the entry on the board under the Closed view — success marks pending milestones `done` and forces 100%, anything else marks them `missed` and preserves the progress actually reached. Only `remove`/`delete`/`drop` erase, which is for an entry that should never have been opened. `cancel` used to alias to `remove`, so the most natural way for a model to say "we gave up on this" silently deleted it instead of recording it. Matches by id, then case-insensitive name; an op against a project that does not exist is **dropped**, never auto-created. A `create` naming a project already on the board is folded in as an **update that merges only the fields the op actually carried**, so a chatty turn can neither fill the board with duplicates nor reset what it failed to restate. That merge is driven by a `provided` field list recorded at normalize time (a JSON-safe array, because normalized ops are persisted in `events.json` and replayed by the staged reveal): once an op is normalized, every field is populated, so there is otherwise no way to tell `progress: 0` from "progress was not mentioned". Before this, a jump that merely mentioned a running operation reset `ongoing` to false, `progress` to 0, `status` to active, `secrecy` to public, emptied `tags`, and demoted an operation to a project. `tags` follows the `countryTags` rule — an array replaces wholesale, absent means unchanged. A project carrying `onComplete` effects releases them on whichever op finishes it — a `close`, an `update` to status complete, a `create` restating it as complete, or an op aimed at an entry opened or renamed earlier in the same batch: `releaseProjectCompletionEffects` runs the batch through `applyProjectOps` and collects each transition it latches, so the release and the latch cannot disagree. The non-event door (`applyProjectOpsToWorld`) holds such a completion instead: the entry stays open, the rest of the op lands, and its id comes back in `deferredProjectIds`. |
| `createdChats` | `normalizeCreatedChat` (a thread entry that keeps its `openingMessage` and `speaker`) | turn writer (`gameplay.js`) | New diplomacy threads pushed into `chat.json` (not `world`). The opener is what `buildGeneratedChat` turns into the thread's first message; the chat normalizer used to drop both fields, so no chat an event opened was ever opened. |
| `actionIds` | string list | turn writer | Which queued actions this event resolves. |

**Why the land moves — `basis`.** A transfer, and a `regionControlOps` control flip, may say why (`runtime/territoryBasis.js`). `treaty`, `annexation`, `unification`, `independence` and `occupation` move the map. `claim`, `threat` and `raid` do not: `applyPolityAndTerritoryImpacts` screens all three arrays first (`screenTerritoryBasis`), turning a `claim`‑basis entry into a `regionClaims` entry for its receiver — the region goes disputed instead of changing hands — and leaving a `threat` or a `raid` out. A claim over a whole country (`wholeCountry: true`) is refused rather than striped across every province. The field is carried through normalization **only when present**, so a transfer written before it existed round‑trips byte‑for‑byte, and **an entry with no basis is applied exactly as before**. The turn validator runs the same screen earlier and tells the model what it did (the [application receipt](ai-overview.md#the-application-receipt-what-salvage-did-told-to-the-next-turn)); the screen here is the net for impacts that never meet it, and it is idempotent.

### `normalizePolityChange` semantics

- `reputation`: parsed and clamped to `[0,100]` int, else `null` ("unchanged").
- `tags`: `Array.isArray` → `normalizeTagList`; otherwise `null`. This distinction is load-bearing — the AI sends the COMPLETE new tag list, so `[]` means "this country now has no defining tags" (must drop them) while `null`/undefined means "unchanged". `applyEventImpactsToWorld` deletes the key on `[]` and sets it on a non-empty list.

### `applyUnitOpBatch` — pure

Takes the units and their standing orders and returns both (`{ units, orders }`). `spawn` (marks `source:"ai"`) pushes; `move` sets `lng/lat/regionId`, `status:"moving"`; `strength` clamps and marks `defeated` at ≤0; `remove` filters by id. Ops on unknown ids are silently ignored; the final list drops any unit with `strength ≤ 0` or `status === "defeated"`.

### `applyMarkerOps` — pure

`build` replaces any existing marker of the same name (case-insensitive) rather than stacking duplicates; `remove` matches by id first, then exact name (the AI usually knows the name, rarely the id).

## 6. `game.json` — the clock (`GAME_DEFAULTS`)

`GAME_DEFAULTS` (`src/runtime/gameState.js`), normalized by `normalizeGameData`:

| Field | Type | Default | Meaning |
|---|---|---|---|
| `country` | `string` | `""` | The player's owner code/name. |
| `difficulty` | `string` | `"standard"` | Feeds `difficultyDirective` in the prompt, and weighs the land war for whoever fights a person's country (§ battlefields, `runtime/fronts/handicap.js`). |
| `gameDate` | `string` | `""` | Current in-game date (`YYYY-MM-DD`; a year before AD 1 carries a leading minus and counts backwards with no year zero, so `-0218-03-01` is 1 March 218 BC — see `src/runtime/gameDates.js`), advanced each jump to `result.stopDate`. |
| `startDate` | `string` | `""` | Scenario start date. |
| `language` | `string` | `"English"` | UI/content language. |
| `round` | `int > 0` | `1` | Turn counter, `+1` each jump (`gameplay.js`). |

`canonicalizeDateString` repairs `gameDate`/`startDate` from loose formats (`"2016-12-31T00:00:00.000Z"`, `"December 31, 2016"`, `"-218-03-01"`) back to the canonical form (`normalizeGameDate`). Without it, the jump's date arithmetic rejects the value and every jump computes `target == origin`, freezing the clock while the model re-simulates the past. **Every parse, step, difference, comparison and display of a game date goes through `src/runtime/gameDates.js`** — BC years are negative, there is no year zero, the arithmetic is astronomical inside, and comparing two date strings is wrong for BC (`-0218` sorts before `-0300` as text, yet 218 BC comes after 300 BC). Prose dates (`"Third Age 3019"`) don't parse and pass through untouched, on the lenient validation branch.

## 7. `colors.json` — the palette (a sibling, not a world field)

Colors live in a separate asset (`code → [r,g,b]`), not inside `world.json`. `applyEventImpactsToWorld` takes `colors` as an input and returns the mutated palette alongside the world: when a `polityChange` carries a 6-hex `color`, it is parsed to `[r,g,b]` and written to `nextColors[change.code]`. The turn writer persists both in the same `Promise.all` (`gameplay.js`). A colors write invalidates the memoized `getNationColors` cache and dispatches `oh:colors-updated` so the map repaints mid-session without a reload (`assets.js`).

## 8. `applyEventImpactsToWorld` — folding impacts into state

`applyEventImpactsToWorld({ colors, events, world })` (`src/runtime/gameState.js`) is a **pure** function returning `{ colors, world }`. It clones the inputs, normalizes the world and the events, then for each event applies (in order): region transfers → polity changes (name/color/reputation/tags + palette) → unit ops → marker ops. It does NOT persist — the caller writes. Two callers:

1. **The turn writer** — `applySimulationResult` (`src/Game/AI/gameplay.js`). It builds the next world (clearing `activeInteractive`, choosing a skip's `interactiveOffer`, merging `lastJump*`, and the new `simulationHistory` head), calls `applyEventImpactsToWorld` with the generated events, optionally compacts history, then persists everything in one `Promise.all`: `writeActionsState`, `writeChatsState`, `writeEventsState`, `writeGameData`, `writeJson(colors)`, `writeWorldState`. It then captures a rollback snapshot of the pre-jump state (`captureRollbackSnapshot`,).
2. **The staged reveal** — `src/Game/GameUI/time.jsx`. As a turn's events are revealed one at a time, it re-applies impacts up to the last revealed event onto `stagedBase.world` and calls `setWorldStateOverride(stagedWorld)` / `setUnitsOverride(...)` so the map shows the world as of that event. It passes `colors: {}` because it only needs the world, not the palette. When staging ends (or on unmount) both overrides are cleared to `null`.

## 9. State distribution: three stores, no panel polls

No panel fetches a runtime document on its own timer any more. Three stores hold the live state, and all three are driven by the canonical write events `writeJson` dispatches (`assets.js`-): `oh:world-updated`, `oh:game-updated`, and `oh:runtime-json-updated` for every mutable runtime asset. Updates are pushed, not polled. A writer that normalized the document before saving it (`writeWorldState`, the turn commit) sets `normalized: true` on the event (`writeJson`'s `normalized` option, a `publishJsonWriteBatch` entry's `normalized`), and the runtime store applies it without normalizing it again. `writeJson` also puts the text the saved document was parsed from on such an event (`text`), and the runtime store compares it with the text its held document came from instead of deep-comparing the two: equal texts are a no-op write, different ones a change. The turn commit has no per-document text, so its world is still deep-compared. The one remaining timer is a 60-second backstop for a writer no event can reach.

### The map store: `src/Game/Map/useWorldState.js`

A singleton that holds `world.json` for all map consumers. It bootstraps once from the already-warmed asset cache and updates only when a canonical write announces itself. The 90-second safety poll it used to run was removed because it could interrupt otherwise idle map interaction.

| Piece | Location | Behavior |
|---|---|---|
| `sharedState` / `publishedState` / `subscribers` | - | One world object, one derived object, a `Set` of subscriber callbacks. |
| `bootstrap` | | `readJson(JSON_URLS.world, { force: false, clone: false })` on first subscribe. On error it publishes `{}` rather than leaving consumers unpainted. |
| `onWorldUpdated` | | `oh:world-updated` carries the saved world in `event.detail.world`; the store adopts that object directly, with no read. |
| `onActiveGameChanged` | | A save switch drops `sharedState`, the override and the published object, then bootstraps again from the new save's `world.json`. |
| `overrideState` / `setWorldStateOverride` |, | Staged-reveal override. `effectiveState = overrideState ?? sharedState`. Canonical updates keep landing underneath, and clearing to `null` snaps consumers back to live state. |
| `getWorldStateSnapshot` | | Read-only accessor of the effective state (peer of `unitsController.getUnits`). |

### The HUD store: `src/runtime/runtimeStore.js`

One store and one subscription list for all six mutable runtime documents: `game`, `world`, `events`, `actions`, `chat`, `intercepts`. It replaced ten independent 5-second `force: true` intervals across `time.jsx`, `actions.jsx`, `chat.jsx`, `projects.jsx` and `settings.jsx`.

| Piece | Location | Behavior |
|---|---|---|
| `SOURCES` | | Per key: the `gameState.js` reader and the matching normalizer. The store always holds normalized documents. |
| `subscribeRuntime(key, fn, { select, seed })` | | Adds a subscriber. With `select`, `fn` is called only when that selector's output changes, compared with `deepEqual`. Without one, only when the document's own reference changes. `seed` is the slice the caller last rendered, so a change landing between a render and its subscription is not swallowed. |
| `applyValue` | | Normalizes, deep-compares against the current document, and publishes only on a real difference. A poll that found nothing new notifies nobody. A write applied as it is that carries its JSON text is compared by text instead when the held document has one too (a long campaign's world: a fraction of a millisecond against tens), and the entry keeps that text for the next write. |
| `openChannel` | | A `BroadcastChannel` carrying **only the key** of a document this tab wrote. Other tabs of the origin share one save and see no `window` event from it; posting the value instead would structured-clone a multi-megabyte world into every listening tab on every write. A receiving tab marks that key `stale` and re-reads it, or defers if it is hidden or has nobody subscribed. |
| `tick` / `syncTimer` |, | The 60-second backstop (`RUNTIME_BACKSTOP_MS`), running only while at least one key has subscribers and the tab is visible. A tick reads only the keys that are marked stale or whose last write is older than the backstop, so in an ordinary session it finds nothing and issues nothing. It exists for a writer no event reaches: a save edited on disk while the app runs. |
| `onRuntimeJsonUpdated` | | A same-tab write is authoritative on arrival: the store takes `event.detail.value` and marks that key fresh, so the next tick skips it. In an ordinary session almost every update arrives this way and costs no request. |
| `isStaleGameRead` | | A read that comes back behind the published `(round, gameDate)` is refused, and the whole batch with it, since world and events belong to that same stale turn. `game` therefore rides along with every batch. This is the invariant that used to live in `time.jsx`'s `gameStampRef`. |
| `onRolledBack` | | A rollback is the one write that legitimately moves the clock backwards, so `oh:rolled-back` (dispatched by `rollBackToSnapshot`) clears the stamp and re-reads. |
| `onActiveGameChanged` | | Same reset as the map store: every document is dropped and re-read for the new save. A read still in flight from the previous save is not joined: the switch bumps a generation, clears the pending reads, and a result from before the switch is dropped when it lands, so the old save's round never becomes the stamp the new save's reads are refused against. |
| `primeRuntimeValue(key, value)` | | Publishes state the caller already holds (a finished turn, a restored bundle) without a round trip. `time.jsx` uses it where it used to call `setGameData` / `setEvents` / `setWorldState`. |
| `refreshRuntimeState(keys)` | | An explicit read, for the moment a panel opens. |

`countryStats` and `countryStatsHistory` are the one exception to all of this: the stats worker writes `world.json` from off-thread and `primeCountryStatsWorkerCommit` patches the same-tab caches narrowly rather than re-broadcasting the world, so those two fields only become current here on a backstop read. Read them through `readCountryStatsBundle`.

React consumers use `useRuntimeState(key, select, depsKey)` (`src/runtime/useRuntimeState.js`). Pass `depsKey` when the selector closes over something that can change without the document changing, as `projects.jsx` does for `isPolityLandless(world, playerCountry)`.

The practical rule for a new panel: subscribe to the narrowest slice you can name. `actions.jsx` takes `{ country, gameDate, round }` off `game.json` and re-renders for nothing else; `projects.jsx` takes `world.projects` and `world.polityOverrides` separately, so a unit move does not touch the board.

### Content-compare / referential-identity guard (`useWorldState.js`-)

`useWorldState` derives a small object of the fields the map cares about (`worldState`, `worldKnown`, `customRegions`, `customCities`, `basemap`, `background`, `regionOwnershipOverrides`, `regionClaimants`, `polityOverrides`, `markers`, `cityRenames`, `cityPopulations`, `labelFont`, `labelHaloColor`, `labelTextColor`) and, if it is **content-equal** to the previous derived object, RETURNS THE PREVIOUS OBJECT REFERENCE. This keeps `useMemo`/`useEffect` consumers from re-running when nothing meaningful changed. Comparison strategy:

- Scalars (`basemap`, label config, booleans): `===`.
- `regionOwnershipOverrides`: `areEqualShallow`, key count plus per-key `===` (values are strings).
- `background`, `regionClaimants`, `polityOverrides`, `markers`, `cityRenames`, `cityPopulations`: `areEqualStructured`, a recursive content compare. Their values are fresh arrays/objects on every canonical update, so reference equality would churn; the payloads are small. `EMPTY_MARKERS` is a stable `[]` so a marker-less world never churns the memo.

`worldState` itself is the raw world object (replaced whenever a write lands), but the sibling derived fields drive the map layers and are identity-stable.

### The units store: `unitsController.js`

`src/Game/Map/unitsController.js` is the third store and follows the same shape: `startUnitsSync` ref-counts subscribers, bootstraps once, and then listens for `oh:world-updated` and `oh:game-updated`, republishing `world.units` to its own pub/sub. Its own 5-second `world.json` + `game.json` poll is gone.

The player's only mutations are **deploy**, **disband** and **request orders**. Manual movement and manual combat were removed, so where forces go and what happens when they meet belongs to the AI and to `advanceStandingOrders`. `commit` does a read-modify-write of `world.units` **preserving the rest of world state** (`{...world, units: nextUnits }`), guarded by a `busy` flag so an incoming update does not clobber a mid-commit write, and resolves to `null` when the write failed. `deployUnit` (the Forces panel's placement and the advisor's) and `disbandUnit` (the unit card's Disband) change the units and the action queue as one change (`commitWithActions`): the queue first, then the units, and the queue put back if the units could not be saved, so a Deploy request never stands for a unit that is not on the map and a unit never leaves it with no order behind. Both resolve to `{ ok }` or `{ ok: false, error: ORDER_NOT_SAVED }`, which the card, the Forces banner (a deploy that failed stays armed, saying so) and the advisor show; `requestUnitOrders` resolves to whether its order was written, and the card keeps the typed text when it was not. A deploy carries a `unitRevert` of `{ unitId, remove: true }`; a disband queues a **Disband order** whose `unitRevert.restore` is the whole unit, so deleting it before the jump puts the formation back (`normalizeUnitRevert` in `gameState.js`), without the standing order it had: that went with it when it left the map, so it comes back idle with no `orderId`. Disbanding a unit still `pending` withdraws its Deploy request instead and queues nothing. Both kinds of entry are settled by the engine after the jump (`actionNeedsEvent`), not left waiting for an event to cite them. `revertUnitOrder` keeps its `lng`/`lat`/`status`/`pendingOrderId` branches for actions queued by the old manual-order UI that are still sitting in existing saves. It exposes its own `setUnitsOverride`/`getUnits` mirroring the world-state override for staged reveals.

A turn reads `world.json` when it starts and writes it back whole when it lands, so while one runs (or is held for a retry) `deployUnit`, `removeUnit`, `disbandUnit`, `updateUnitAdmin`/`placeUnitAdmin` and `revertUnitOrder` write nothing (`unitsLocked`; `deployUnit` returns `null`), and the Forces panel's **Place on map**, the unit card's **Disband** and the Actions panel's ✕ on an order that moved a unit are disabled with *A turn is running. This can be changed once it ends.* `requestUnitOrders` is not locked: it only queues an action, and the turn reads the queue again before writing it (`mergeActionsAtCommit`, `src/runtime/turnCommit.js`).

## 10. Country tags — `src/runtime/countryTags.js`

A dependency-free module (imported by the editor, the game, and the server) that owns the two rules both halves must agree on: how a tag list is normalized and which source wins.

| Export | Location | Purpose |
|---|---|---|
| `MAX_TAGS` / `MAX_TAG_LEN` |, | 8 tags, 32 chars each. |
| `TAG_SUGGESTIONS` | | Open-vocabulary suggestions (`socialist`, `authoritarian`, `nato-aligned`, …) so common cases converge on one spelling. |
| `normalizeTagList(list, opts)` | | Trim, collapse whitespace, cap length, drop blanks, dedupe case-insensitively, cap count. Non-strings dropped (a stray number means a palette `[r,g,b]` leaked in). |
| `resolveCountryTags(baseTags, world, country)` | | The tags in force NOW for one country: the AI's live `world.countryTags[name]` if it has ever set one, ELSE the author's `tags.json` list. **Not a merge** — a revolution that dropped "socialist" must not have it restored by the scenario file underneath. Keyed by country NAME verbatim. |
| `resolveAllCountryTags(baseTags, world)` | | Every tagged country, live winning over author, for the world summary the model reads. Emits keys verbatim (no uppercasing — see the desync note). |

Author starting tags come from `getNationTags` (`assets.js`, the scenario's `tags.json`); live changes land in `world.countryTags` via `polityChanges.tags` (§5/§8). Political World generation reads a library scenario rather than the active game, so the Politics panel downloads that scenario's own `tags.json` and passes it as `baseCountryTags` (`buildScenarioPoliticalGenerationInputs` → `geopoliticalWorldGenerator.js`), where the power and membership prompts and the tag-implied regime character go through `resolveCountryTags`. See [Country tags](world-state.md).

## 11. Read / write API surface (`gameState.js`)

| Function | Notes |
|---|---|
| `readWorldState({force})` | `readJson(world)` → `normalizeWorldState`. |
